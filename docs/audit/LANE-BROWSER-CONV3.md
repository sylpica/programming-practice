## §12 環境要因の証拠（未確認の理由）

1. **Chromium 起動即死（SIGTRAP）の窓**: 11:2x のスモークテストと、
   VM 再起動（12:19 頃、uptime リセットを確認）直後の 12:20〜12:41 は
   起動・実行が可能で、その窓で §1〜§5・§8〜§10 の確認が取れた。
   しかし 12:42 以後は起動自体が持続的に失敗した。生 CLI
   （`chrome --headless --dump-dom about:blank`／ヘッドレスシェル）でも
   終了コード **133（Trace/breakpoint trap）**・出力ゼロで、12:42 から
   13:41 まで約1時間にわたり継続した（間隔を空けて繰り返し探査した）。軽量化フラグ3種（`--disable-dev-shm-usage`／`--no-zygote
   --single-process`／`--disable-gpu` 等）でも不変、/dev/shm は 794MB・
   使用 0、負荷平均は約1まで低下した時間帯でも再現した。第2回横断ラインが
   記録した環境障害と同型であり、アプリ側の要因ではない（失敗はページ
   要求前）。
2. **対象ビルドの Worker 起動マージン**: 対象（バッチ19）の Worker は
   自明な `print(1)` でも応答まで実測 5,270ms（負荷約21時）を要した回が
   あり、アプリの解析ウォッチドッグ 2,500ms を超えやすい。対照の
   バッチ13納品物は同じ条件で実行完了した（出力「出力print 1」）。
   js ツリーは対象 21MB・565ファイルに対し納品物 3.1MB・71ファイルで、
   レジストリ読込が起動時間を支配している。実機相当の CPU では制限内に
   収まる性質のもので、第2回簡易ラインも「実質的欠陥とは数えない」と
   記録した観測と同一である。本班の対策として、実行の再試行はページ
   再読込でなく実行ボタンの再クリックで繰り返す方式（第2回 A3 班の
   成功パターン）に切り替え、12:33〜12:35 の窓で上記6件＋2件の実行完了を
   得た。
3. **分離した子プロセスの固着**: exec セッションから切り離した
   子プロセス（http.server 等）は、親セッション終了後に「接続は受け付ける
   が応答しない」状態に固着する事象が繰り返し起きた（生ソケットで
   接続成功・受信 EOF を確認）。このため配信サーバとハーネスは同一
   exec 呼び出し内に閉じて実行する方式に切り替えた。results.json が
   一度 0 バイト化した事故もこの過程で起き、合格6件の記録は
   `harness4.log` のログ行とスクリーンショットから復元して
   `results.json` に再記録した（各エントリに復元元を明記）。
