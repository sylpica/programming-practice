## 5. 追加課題: UI.Vision の trace refs 照合は A3班の ImageJ 欠陥と同型か

### 5.1 機構の比較（結論: 生成側の機構は同型ではない）

- **ImageJ（A3班の欠陥）**: `js/types/imagej/index.js` の simulate が、各ステップの used（実際に呼ばれた関数名）を trace の refs へ変換する際、モジュール内の基礎カタログ `reference` だけで照合していた。高度専用関数は**生成側で基礎カタログにより落とされていた**。
- **UI.Vision**: trace refs の生成側にカタログ照合は存在しない。共有エンジン（js/core/script.js の note／noteError）が、ノードの refs（＝actionProgram が付けた「書かれたままのコマンド名」、elseIf のみ D-5 で正規化済み）と pendingRefs（式内呼び出し名）をそのまま trace へ載せる。チップ解決は app.js の updateUsed が有効カタログ（高度モードでは `definition.__catalogReference`＝合成カタログ）に対して行う。
- 指摘された `js/types/uivision/index.js` 458行・466行の `reference.some(...)` は **scan 側**の照合である。458行は基礎名の完全一致の近道で、高度名は `advancedByLower`（大小無視の正規名表）で解決され、466行以降のフィルタで `__catalogReference` 在席時のみ通る（簡易モードで高度名が出ないゲート）。trace refs の生成とは無関係である。
- 実測（正規形）: 高度専用コマンド executeScript／forEach／do／repeatIf、高度テンプレート3件（assert 系・csv 系・do ループ）の trace refs に高度名が全て現れ、有効カタログでチップ解決できることを確認した（測定 M1〜M4・M6）。**正規形では ImageJ 型の欠落は起きない。**

### 5.2 しかし同系統の別欠陥を実測で検出（CONV2-A1-01）

実測の過程で、高度コマンド名の**大小文字違いの綴り**に限って、実行後チップから高度コマンドが落ちることを確認した。

- 仕様前提: 高度コマンド名の解決は製品仕様どおり大文字小文字を区別しない（index.js 冒頭の明記）。実行側はハンドラ照合・停止照合（canonPre）・高度構造コマンドの classify（B1A-03）の全てで `advancedByLower` により正規名へ寄せ、scan も同じく正規名へ寄せる。エラー文面も正規名を挙げる。
- 欠落の機構: ノード refs だけが原文綴りを保持し、app.js のチップ解決（resolveReferenceName）は大小区別の完全一致のため、大小違い綴りで書かれた高度コマンドは**実行できるのに実行後チップ（スコープ「表示中のパス」）に現れない**。scan（スコープ「コード全体」）には正規名で現れるため、表面間の表示矛盾になる。
- 全数実測: 高度コマンド全108名について、大文字形で実行したとき **108/108 が実行到達**（ハンドラ実行、または正規名を挙げた名前つき停止／失敗）し、その全件で trace refs は原文綴りのみを保持してチップ解決から落ちた。正規形では 108/108 が refs に現れ解決できる。代表形: `EXECUTESCRIPT`／`ExecuteScript`（実行され出力も正しいがチップ落ち）、`FOREACH`／`Do`／`REPEATIF`、`CSVSave`（カタログ名 csvsave へ解決できない）、`GOTOIF`（停止文面は正規名 gotoIf を挙げるがチップ落ち）。
- 対照（基礎コマンド）: 基礎コマンドの実行 dispatch は大小区別が設計どおりであり、`STORE` のような大小違いは実行されず正直に停止する（チップ矛盾は生じない）。cmd 側はパーサがコマンド名を正規化してから refs を付けるため大小で挙動が変わらない（SET／ECHO → refs は set／echo）。cmd の一部ステップ（findstr／pushd 等）が refs を付けないのは大小に依らない既存設計で、本欠陥とは無関係。
- 分類: 欠陥類型＝表示矛盾（実行・scan・エラー文面は正規名で一致するのに実行後チップだけが落とす）。D-5（elseIf の refs 正規化）・RG-653（C#／JS の実行後チップ欠落）と同系統。根本原因は ImageJ の「生成側の基礎閉じ」とは異なるため、A3班の欠陥と**同型ではない**が、独立した新規の実質的欠陥として数える。重大度 P2（実行結果そのものは正しい）。
