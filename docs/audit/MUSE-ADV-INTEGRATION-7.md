## 2. 欠陥の内容と切り分け（RG-681）

- 症状： precache 集合のみを配信するとアプリが起動しない（`#macroType` の option が成立しない）。モップアップ班の切り分けでは、不足分を足す条件C（名前表2件のみ）でも次層の静的ファイルが 404 になって起動せず、静的閉包の不足38件を全て足した条件Bでは2.0秒で option 16件が成立し、失敗リクエスト0・エラー0だった。
- 機械照合（統合側で再現）： 入口（js/app.js／js/worker.js）からの静的 import 閉包は113ファイル、そのうち precache 未収載は38件。内訳は各種別の advanced-engine／semantics-advanced、VBA・R の reference-advanced-names、R の functions-advanced／names-advanced 一式、VBA の constants-advanced／functions-advanced、PowerShell の engine-advanced 一式など。
- 機構： `scripts/precache.mjs` と `sw.js` が共有するファイル名パターン（「-advanced を含む .js」）が、遅延読み込みされる項目データ本体だけでなく、静的 import される起動必須ファイルまで「ランタイムキャッシュ任せ」に分類していた。オンラインでは network-first で取得できるため無症状だが、sw.js の activate が世代交代時に旧世代のランタイムキャッシュを削除するため、新世代の初回起動をオフラインで行うと、起動必須ファイルが取得できずランタイムキャッシュも空で、簡易モードでも白紙になる。
- 未検出の理由： `precache --check` は生成器との整合しか見ておらず、「静的閉包 ⊆ precache」という観点の検査が従来ラウンドの実施範囲に入っていなかった。フルツリー配信のブラウザ確認は全て合格してきたことと矛盾しない。
- 対象外： 現行公開ビルド d2f2198 は高度モード統合前のため高度ファイル自体が無く、本欠陥の対象外。

## 3. 修正の設計

- 生成器（scripts/precache.mjs）： 入口2ファイルから静的 import とリテラルな動的 import（`import("./engine.js")` 等のエンジン読み込み）を辿る閉包を算出する。閉包は114ファイル（静的113＋ImageJ engine.js）。precache 収載集合＝シェルファイル＋閉包＋js 配下の非 .js ファイル＋icons。遅延集合＝残りの js ファイル451件を PROGRAMMING_LAZY_ASSETS として生成物へ併記する。世代ハッシュには収載ファイルの内容に加えて遅延集合のファイル名を含める（集合の増減で世代が変わり旧ランタイムキャッシュが破棄される。内容の鮮度は network-first が担う）。
- sw.js： 遅延判定はリクエストパスのスコープ相対形が遅延集合に属するかで行う。分類の正本は生成器に一本化され、両者の分類は生成物を通じて機械的に一致する。ADVANCED_CACHE の世代結びつけ（R-9）、network-first、正常応答のみキャッシュ（D-6）、オフライン時の正直な失敗は全て不変。
- SP-21 の維持： ローダーが項目データ本体として宣言するファイル（manifest の referenceParts／templatesFile／glossaryFile、manifest の無い種別はローダーの既定ファイル）は全て遅延集合側にあり、precache には入らない。生成器は、宣言データファイルが起動閉包に混入していたら生成自体を失敗させる（静的 import でデータ本体を取り込む再発を CI 以前に止める）。実測でも、簡易モード初期ロードでの遅延ファイル要求は0件だった（§6）。
- 二重到達の扱い： cmd／UI.Vision／C#／JavaScript の advanced-engine や PowerShell の engine-advanced 群など19ファイルは、ローダーの宣言（engineFile）と静的 import の双方から到達する。起動必須である以上 precache 側を正とし、遅延集合からは除かれる（振り分けは一意）。
