## 角度1：コメントの扱いの全表照合（約92プローブ → 新規3件）

### R19-N1（P2・新規）C／C++ の行コメント末尾バックスラッシュ（行スプライス）を字句解析が処理せず、次行が実行される

- 再現：`// comment \` の次行に置いた文がアプリでは実行され、出力が **999** になる。実 gcc／g++（実機照合）ではバックスラッシュ＋改行は翻訳フェーズ2の行スプライスとして処理され、次行もコメントになるため出力は **42**。
- 対照：C# はスプライスしない仕様どおりアプリも 999 で正しい（C系で一律に壊れているのではない）。
- 根本原因：C／C++ の字句解析に行スプライス（行継続）の段階が無く、`//` コメントが行末で無条件に終わる。
- 受け入れ条件の目安：C／C++ で `//` コメント末尾の `\` が次行をコメントとして取り込むこと。パス列挙・実行結果が実コンパイラと一致すること。

### R19-N2（P2・新規）AutoHotkey のコメント規則が言語固有でなく、共有トークナイザの規則のままになっている

- 公式一次情報：AutoHotkey v2 公式ドキュメント（autohotkey.com/docs/v2/Language.htm）— 行コメントの `;` は「行頭にあるか、直前に空白／タブが必要」。ブロックコメントの `/*` は「行頭（空白・タブを除く）にある場合のみ」で、`*/` を省略した場合はファイル末尾までコメントとして有効。
- 再現（3表面、同根）：
  - (a) 直前に空白のない `;comment` をアプリはコメントとして受理する（実物ではコメントにならない）。
  - (b) 式の途中の `/* */` をアプリはコメントとして処理し **42** を返す（実物では `/*` が行頭に無いためコメントではない）。
  - (c) 行頭の未閉じ `/*` をアプリは「コメントが閉じられていません」でエラーにする（実物では末尾までコメントとして有効で、エラーにならない）。
- 根本原因：AHK エンジンがコメント処理を共有トークナイザ（C系規則）に委ねており、AHK v2 固有のコメント規則が実装されていない。
- 受け入れ条件の目安：`;` の空白要件、`/*` の行頭要件、未閉じ `/*` の EOF までの有効性が公式仕様どおりになること。

### R19-N3（P3・新規）CloudFormation でテンプレート先頭行の `#` コメントが Python ハンドラ経路へ誤って振り分けられる

- 再現：YAML／JSON テンプレートの **1行目が `#` コメント**だと Python ハンドラ経路に誤判定される。YAML では虚偽の「SyntaxError：文の終わり方が正しくありません」、JSON ではハンドラ側の NameError になる。本文中のコメントや先頭の空行では発生しない。
- 根本原因：テンプレート種別（通常テンプレート／Python ハンドラ）の判定が先頭行の `#` に引きずられている。
- 受け入れ条件の目安：先頭行コメントのある通常テンプレートが通常経路で処理され、ハンドラ判定はハンドラ固有の特徴でのみ行われること。

### R19-N4（P3・新規／RG-10 家族の別表面）Power Automate／UI.Vision のモデル入力 `null` で生の JS エラーが露出する

- 根本原因：モデル入力の検証が `null` を弾く前にプロパティ参照しており、例外がそのまま表示される。RG-10（入力検証がアプリ自身の言葉でない表示になる）の根本原因と同系で、記録済み表面に無い新規表面として数える。
- 受け入れ条件の目安：`null` 入力でも他の不正値と同じアプリ自身の言葉の検証メッセージで停止すること。

### R19-N5（P3・新規／RG-10・RG-63 家族の別表面）CloudFormation の不正 YAML で js-yaml の生エラー（英語＋入力ダンプ）が露出する

## 角度3：入力欄への敵対的モデル値（約187プローブ → 新規1件）

正しかった表面・観察（抜粋）：

- Python は全値で型どおりの TypeError／正値。JavaScript は全値で実 JS どおり。AutoHotkey は非数値に正直な TypeError、`"1e3"` は 1001 で正。Power Automate は数値以外を正直なエラーにする。CloudFormation は Fn::Transform の Parameters とハンドラモードの model.event で再実施し、全値が忠実に伝播、不正な fragment 型はアプリ自身の言葉の TypeError／KeyError で正直に停止。
- VBA：`"1e3" + 1` → 1001、`True + 1` → 0 は実物どおり正。モデル値 null は Empty として扱われ `+1` → 1 だが、シート入力欄からは null に到達できないため観察に留める。
- UI.Vision：モデル文字列は忠実に伝播。null が "null" と出力されるのは観察に留める。
- ImageJ：pix 値 "abc" の連結 "abc1" は、モデル側の不正値に対する ImageJ 意味論の忠実な適用として観察に留める。非数値は「実行時に決まる値」扱いで正直。
- Power Apps：数値文字列の `+` は RG-12 の既知表面のため数えない。`Value("1e3")` の変換エラーは実 Fx 未確認のため観察。
- C# の Console.ReadLine はモデルの input 値によらず常に「実行時に決まる」扱いで、設計どおり（観察）。

### R19-N6（P2・新規）R のデータフレーム／レコード値への二項演算が NaN と単一の FALSE を捏造する

- 再現（モデル変数のデータフレーム値 df に対し）：
  - `df + 1`、`df * 2`、`df - 1`、`1 + df` は全て `c(NaN)` を返す。
  - `df == 1`／`df > 1` は単一の `c(FALSE)` を返す。
  - 実 R（Rscript 照合済み）は要素ごとのデータフレーム演算・比較（データフレーム／論理データフレーム）を返す。
- 同根の横断確認：モデル変数の素のオブジェクト `{a: 1}` への `+ 1`、モデル CSV 由来のデータフレームでも同じ捏造になる。対照として `df + "a"` は正直にエラーになる。
- 隣接観察：`sum(df)` は正直にエラーになる（実 R は 10 を返す）。捏造ではないため本件に含めず観察として記録する。`list()` は正直な未対応宣言のため、コード由来のリストは存在しない。
- 根本原因：R エンジンの二項演算評価がデータフレーム／レコード型の値を数値化に失敗したまま NaN／FALSE を合成しており、型を指す停止にも要素演算にもなっていない。
- 受け入れ条件の目安：データフレーム値への算術・比較が実 R どおり要素演算になるか、データフレームであることを指す正直な停止になること。NaN／単一 FALSE の合成が起きないこと。

## 角度4：型×比較演算子の強制変換マトリクス（約87プローブ＋横断24 → 新規4件、候補1件）

実ランタイム全数一致（新規ゼロの部分）：

- JavaScript 21件（node で要点照合）、Python 13件、R 13件（Rscript で要点照合：`TRUE == "1"` → FALSE、`2 > "10"` → TRUE、`NA == 1` → NA）、C 6件は、エンジンと実物が全数一致した。
- VBA：文字列×数値の直接比較は構文名を挙げた正直な未対応宣言で停止するため数えない（先例どおり）。`True = -1` は値が正しく、小文字 "true" 表示は RG-04 の既知表面。`Null = Null` → "Null" で正。
- AutoHotkey：`"a" > 1` の TypeError は、本ラウンドで公式 v2 ドキュメント（Variables.htm の演算子表「関係演算子の入力は数値として比較され、数値でも数値文字列でもなければ TypeError」）と照合し、実仕様どおり正しいことを確定した。
- C++：コピー初期化した文字列の比較（`s == "a"` true、`t < "9"` true、`s == "A"` false）は g++ と全数一致。`std::string("a")` の関数形式構築は「キャストのこの形式は未対応」と分類して停止する（コピー初期化は動作）— RG-06 家族の観察として記録するに留める。

### R19-N7（P3・新規／RG-05 群への追加）C# の `'a' == 97` が false になる

- 再現：`'a' == 97` をアプリは false とする。実 C# は char が int へ暗黙に昇格するため true。
- 台帳との関係：RG-05（C# の char・型混在の型規則不備）と同根で、再現表面が統合元に無いため新規の元項目として数え、RG-05 群に帰属させる。
- 受け入れ条件の目安：char と整数の比較が実 C# どおり昇格して評価されること。

### R19-N8（P3・新規／RG-05 群への追加）C# の `true == null` が無言で false になる

- 再現：`true == null` をアプリは無言で false とする。実 C# はコンパイルエラー CS0019（bool と null に等値演算子は無い）で、そもそも実行できない比較である。
- 台帳との関係：N7 と同じく RG-05 群への追加項目。
- 受け入れ条件の目安：成立しない型の組み合わせの比較は、型を指す原因で停止すること（無言の真偽を返さないこと）。

### R19-N9（P3・新規）C++ の std::string × 数値の比較が無言で真偽を返す

- 再現（本ラウンドで横断確認）：`s == 1` → 0、`s != 1` → 1、`1 == s` → 0、`s < 1` → 0 と、両順序・複数演算子で無言に真偽が返る。実 g++ ではいずれもコンパイルエラー（std::string と int の比較演算子は存在しない）。
- 対照：同じエンジンで `c == 97`（char）は 1 で正しく、`s == "a"` も正しい。壊れているのは文字列×数値の組み合わせだけ。
- 根本原因：C++ エンジンの比較評価に「その型の組み合わせの演算子が存在するか」の検査が無く、不成立の比較を false 方向に合成している。
- 受け入れ条件の目安：std::string × 数値の比較が、型の組み合わせを指す原因で停止すること。

### R19-N10（P3・新規）AutoHotkey の等値比較で空文字列が 0 に化ける

- 再現（本ラウンドで横断確認）：`"" = 0` → 真、`0 = ""` → 真、`"" == 0` → 真、`"" != 0` → 偽、`" " = 0`（空白のみ）→ 真。対照として `"0" = 0` → 真（数値文字列なので正）、`"a" = 0` → 偽、`"" = 1` → 偽は正しい。
- 一次情報：AutoHotkey v2 公式ドキュメント — 関係演算子は数値／数値文字列でなければ TypeError、等値演算子はどちらかが非数値なら文字列として比較する（Concepts の「数値文字列は必要な場合に数値として解釈される」）。空文字列は数値文字列ではないため、実物では `"0"` と `""` の文字列比較になり false。空白や非数値を 0 とみなさないのが v2 の設計（数値演算では TypeError になる旨も公式明記）。
- 根本原因：AHK エンジンの等値変換が、空文字列（と空白のみ文字列）を数値 0 に変換してから比較している（JS 流の変換の混入とみられる）。
- 受け入れ条件の目安：`"" = 0`／`"" == 0` が false、`"" != 0` が true になり、数値文字列（`"0" = 0`）の真は維持されること。

### 候補（不算入）：Power Fx の `Blank() = 0`／`Blank() = ""` が false になる

- 実測：`Blank() = 0` → F、`Blank() = ""` → F、`0 = Blank()` → F、`Blank() <> 0` → T、`Blank() = false` → F（対照：`Blank() = Blank()` → T、`1 = 1.0` → T は正）。
- 嫌疑：実 Power Fx では Blank が比較相手の型の既定値（数値なら 0、文字列なら ""、真偽なら false）に変換されて比較され、いずれも true になると目される。Microsoft Learn の Blank 関数の記事には「厳密な blank 判定には `Value = Blank()` を使う（IsBlank は空文字列も含む）」という記述があり、Blank と他型の等値が緩く扱われる設計思想とは整合する。
- 不算入の理由：Microsoft Learn の演算子記事・データ型記事・Blank 関数記事を当たったが、`Blank() = 0` が true になるという明示的な一次記述を本ラウンドでは確定できなかった。実 Fx ホストでの実行確認が取れるまでは欠陥として数えない。修正側で実ホスト確認のうえ裁定されたい。
- 関連観察：`true = 1` → F、`"a" = 1` → F も、実 Fx では型エラーになると目されるが未確認のため観察に留める。
