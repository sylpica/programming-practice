## 新規欠陥

### R14B-N1（P2）JavaScript／AutoHotkey：入れ子配列リテラルが `[[`／`]]` の隣接で汎用エラーになる

- 再現（JS）：`let m = [[1, 2], [3, 4]]; console.log(m[0][1]);` → 「式を解釈できません：[[」で停止（パス0件）。AHK：`a := [[1, 2], [3, 4]]` も同一。
- 根本原因：共有スクリプト字句解析が `[[` と `]]` を単一トークンとして扱うため、配列リテラルの最初または最後の要素が配列リテラルだと壊れる。切り分け（兄弟表面を同作業内で全数確認）：
  - 失敗：初期化子・代入・式文・引数・カンマの後（`[0, [[1]]]`）・深さ3（`[[[1]]]`）・書き込み位置（`m[0][0] = 9` の前に初期化で停止）。末尾だけ空白（`[[…] ]`）は `[[` で、冒頭だけ空白（`[ […]]`）は「] が必要です」で失敗。
  - 成功：両端に空白を入れた `[ [1, 2], [3, 4] ]`、要素が変数 `[a, a]`、push で構築した二次元配列、中間に置いた `[1, [2, 3], 4]`。
- 二次元配列は JS／AHK 教材の基本形であり、対応している構文（配列・入れ子自体は空白形で動作）が最も普通の綴りでのみ壊れ、原因表示も構文名を挙げない。生成ファズでも JS 60件がこの1点で全滅した。なお Python（別エンジン）の入れ子リスト、R の `[[ ]]` 添字、Power Fx の入れ子レコードは正常であることを対照確認した。

### R14B-N2（P2）JavaScript／AutoHotkey／Power Apps：式の途中改行が全般に失敗し、見えない改行トークンが原因表示になる

- 再現（JS）：`let xs = [1,\n  2];` → 「式を解釈できません：\n」（原因表示が改行そのもの）。`let x = (1 +\n  2);`、`let s = "a" +\n  "b";`、`xs[\n  0\n]` も同型。AHK の括弧内・配列内の改行、Power Apps の `Set(x, 1 +\n  2)` も同一。
- 実 JS／AHK v2／Power Fx はいずれも括弧内・演算子の後の改行を通常の空白として扱う。長い式を改行して書く整形は教材・実コードの常套であり、共有スクリプト基盤を使う3種類で一律に、しかも学習者に見えない文字を原因として停止する。
- 同根の既知表面：R では R9-N9（行末演算子の継続が空トークンの原因表示で停止）として既報。本角度の新規分は、JS／AHK／Power Apps の表面と、括弧・添字内という R9-N9 が扱わなかった範囲である。対照確認：Python（括弧内改行は正常）、ImageJ（式の改行は正常）、C 系（文が ; 終端で改行自由）はこの根の影響を受けない。

### R14B-N3（P3）R：長さ1の演算結果だけ `c(5)` と表示され、同じ値のリテラル表示と食い違う

- 再現：`x <- 2 + 3` の最終状態と `print(x)` は `c(5)`、`x <- 5` は `5`。実 R では両者は同一の長さ1ベクトルで表示も同一。
- 兄弟表面（16件で境界確定）：二項演算（+ − * / ^）、コロン `5:5`、単項マイナス、比較（`c(TRUE)`）は全て c() 形。リテラルと、スカラーを返す関数（sum／mean／length）は裸の表示。演算結果への添字 `x[1]` の表示も c() 形。内部のスカラー／ベクトル型区分が表示に漏れており、値そのもの（length・添字・後続演算）は正しいため P3 とする。

### R14B-N4（P3）VBA：行継続 `_` が未対応で、継続行の先頭トークンを原因として停止する

- 再現：`x = 1 + _`＋改行＋`2` → 次行の先頭を名指して「この構文は説明に対応していません：2」で停止。2段継続、文字列連結 `& _`、呼び出し `MsgBox _` の全位置（計4件）で同型（原因は継続行の先頭トークン「2 + _」「cd」「hello」等に付け替わる）。
- 行継続は VBA の基本記法。宣言の対応・未対応のどちらにも記載がなく、原因表示も継続という構文を名指さない。なお `_` のない通常の改行（文の終端）としての扱いは実 VBA どおりで問題ない。
