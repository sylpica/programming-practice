## 第1章 全体像と不変条件

1. **エンジンは単一である。** 種類ごとのエンジン（パーサ＋シミュレータ）はモード別に分けない。モードで変わるのは次の3点のみである。
   1. リファレンスの収録範囲
   2. 名前解決の対象カタログ（コード練習ビューの使用中チップ・検索・名前解決が対象とする項目集合）
   3. テンプレート・用語集の表示範囲
2. **同じコードの実行結果はモードで変えない。** 高度モードで実装した意味論はエンジンとしては単一のものになる。モード切替によって、あるコードのシミュレーション結果が変わることは契約違反である。
3. 簡易モードで高度専用関数を書いた場合は「カタログ外の名前」として、現行の未定義関数の扱い（正直な注記つき）と同じに扱い、黙って通さない（計画書 1.1-2、F-03）。
4. **IPA擬似言語（id: `pseudo`）は差分の対象外である。** 両モード同一・完全実装済みのため、高度ファイルを持たない。`pseudo` のディレクトリに高度差分ファイルを置いてはならない。
5. 高度差分は簡易モードのカタログに一切影響しない。簡易モードで使う基礎カタログは、差分ファイルの有無・内容によって変わらない。

> 根拠：計画書 1.1（A-1）、1.4。

## 第2章 モード保存

| 項目 | 契約 |
|---|---|
| 保存キー | `programming-practice-mode-v1`（localStorage） |
| 値の形式 | JSON 文字列 `{"mode":"simple"}` または `{"mode":"advanced"}` |
| 既定値 | 簡易モード（`"simple"`） |
| フォールバック | キーなし・JSON として破損・`mode` が未知値のいずれの場合も、例外を出さず簡易モードとして扱う |
| 下書きとの分離 | 下書きキー `programming-practice-v3` とは完全分離する。モード切替で下書きを消さない・変換しない。モード設定のために v3 オブジェクトへ手を入れない |
| API | `js/core/mode.js` の `getMode()`／`setMode(mode)` |

- `getMode()` は `"simple"` または `"advanced"` のどちらかを返す（それ以外の値を返してはならない）。
- `setMode(mode)` に未知値を渡した場合の扱いは本書では定めない（未決・留保 R-6）。
- 高度専用関数を含む下書きを簡易モードで開いた場合、コードはそのまま保持され、該当関数はカタログ外として正直に注記される（第1章 3）。逆方向（簡易→高度）は全項目がカタログ内にあるため無影響である。

> 根拠：計画書 1.2、1.5（A-2）。

## 第3章 ステータスモデル

### 3.1 状態は3値、`status` が正

リファレンス項目の状態は、次の3値のいずれかであり、データの単一フィールド **`status`** が正である。表示面ごとに状態を持つ二重管理をしてはならない。全表示面は `status` から描画する。

| `status` の値 | 意味 | エンジンの挙動 |
|---|---|---|
| `"supported"`（対応） | 意味論を実装し一次情報で検証済み | 通常にシミュレーションする |
| `"unsupported"`（未対応） | 範囲外・原理的に再現できない・極小意味論の名指し停止（U-44(2)） | 黙って通さず、理由を述べて正直に停止する（F-03） |
| `"unverified"`（未検証） | 項目はあるが意味論を一次情報で確定できなかった | 原則として正直に停止する。ラベルのみ未対応と区別する（A-10）。誤った値を返す実装を「未検証」と称して出さない |

### 3.2 基礎項目と高度項目の違い

- **既存の基礎項目は `status` を持たない。** 基礎項目の状態は、既存フィールド `supported`（真偽値）から次の規則で導出する。
  - `supported === false` → `"unsupported"`
  - それ以外（`true`、または欠落） → `"supported"`
- **高度項目（`referenceAdvanced` の各項目、および `referenceOverrides` で状態に触れる項目）は `status` の明記が必須である。** `status` のない高度項目、`status` が3値以外の高度項目は契約違反である。
- 高度項目に旧来の `supported` 真偽値を併記して状態を表してはならない。状態の入力は `status` に一本化する（合成後の項目がどちらのフィールドで決まったのかを曖昧にしないため）。

### 3.3 「未確認」は状態ではない

- 「未確認」（インベントリ段階で存在自体が未確定）の範囲には**項目を作らない**。画面に出さない。監査文書と台帳にのみ記録する。
- したがって `"unconfirmed"` のような第4の `status` 値は存在しない。高度ファイルにそのような値を書いてはならない。

### 3.4 表示対応

| `status` | テキストタグ | バッジ |
|---|---|---|
| `"supported"` | （なし） | 「シミュレーション対応」 |
| `"unsupported"` | 「未対応」 | 「参照用 · 操作は未対応」 |
| `"unverified"` | 「未検証」 | 「参照用 · 意味論は未検証」 |

- 色だけに頼らず、テキストタグ／バッジの文面と aria サフィックスで区別する（現行の参照のみ項目の表示方式の拡張。現行コードでは `js/app.js` の `referenceOnlyMark`／`refArticle` が `supported === false` の項目にタグ「未対応」と aria サフィックス「（参照用 · 操作は未対応）」を付けている）。
- 状態の変更（未検証→対応、未対応→対応）は台帳（RG）に記録し、変更理由（一次情報の根拠）を残す（計画書 4.3）。

> 根拠：計画書第4章（U-45、A-10）。

## 第4章 項目形状

高度ファイルに書く項目は、**種類定義 `definition` に載る正規化後の形状**（以下「正規形」）で書く。種類ごとの生データ形式（例：Python の `js/types/python/reference.js` の `REFERENCE` が持つ `summary`／`pitfalls`／`doc` 等のフィールド名、ImageJ の `js/types/imagej/reference-data.js` の `sig`／`desc`／`ret` 等）は `index.js` 内で正規形へ変換される前段の形式であり、高度ファイルの形式ではない。高度ファイルに生データ形式で書いてはならない。

### 4.1 リファレンス項目（正規形）

現行の基礎項目の実物（`js/core/data.js` の `rows()` が生成する形、`js/content.js` の `reference`、`js/types/pseudo/reference.js` の項目、および各種類の `reference-details.js` が `Object.assign` で補う項目）に基づく。

| フィールド | 型 | 必須／任意 | 内容 |
|---|---|---|---|
| `name` | string | 必須 | 項目名。照合キー（第6章）。カタログ内で一意でなければならない |
| `category` | string | 必須 | 分類名 |
| `syntax` | string | 必須 | 構文・シグネチャ |
| `description` | string | 必須 | 説明文 |
| `example` | string | 必須 | 使用例（コード） |
| `caution` | string | 必須（空文字列 `""` 可） | 注意点。無ければ空文字列。空の場合は画面に注意要素を描画しない（現行の `refArticle` の挙動） |
| `supported` | boolean | 基礎項目のみ | 基礎項目の状態入力（第3章 3.2）。高度項目では使わない |
| `status` | string（3値） | 高度項目では必須／基礎項目では持たない | 状態（第3章） |
| `returns` | string | 任意 | 戻り値の説明。現行では `reference-details.js` が補い、画面では「戻り値：…」として表示される |
| `source` | string | 任意 | 一次情報の URL（`https://`）。現行では `reference-details.js` 等が補い、画面では「公式資料」リンクになる |

- 上記以外のフィールドを高度項目に足すことは、本契約では認めない。種類固有の追加情報が必要な場合は、勝手にフィールドを増やさずコーディネーターへ相談すること（未決・留保 R-7）。
- 例（高度項目の最小形）：

```js
{
  name: "exampleFunc",
  category: "文字列",
  syntax: "exampleFunc(value)",
  description: "……",
  example: "exampleFunc(\"a\")",
  caution: "",
  status: "unsupported",
  returns: "……",
  source: "https://…",
}
```

### 4.2 テンプレート項目

基礎テンプレート（`js/content.js` の `templates`、各種類の `additional-templates.js`、`js/types/pseudo/templates.js`）と同じ形状とする。

| フィールド | 型 | 必須／任意 | 内容 |
|---|---|---|---|
| `id` | string | 必須 | テンプレート ID。**全種類・基礎と高度を通して全体で一意** |
| `title` | string | 必須 | 表題 |
| `code` | string | 必須 | テンプレートのコード |
| `intro` | string | 必須 | 解説文 |
| `refs` | string[] | 必須 | 参照するリファレンス項目の `name` の配列 |
| `level` | string | 任意 | 難易度ラベル（現行は「基礎」「実践」「応用」等。省略時は registry の既定付与に従う。高度分では明記を推奨する） |
| `model` | object | 任意 | 種類モデルの上書き（現行の `additionalTemplates` が既定モデルを複製して差し込む方式がある。使う場合は基礎テンプレートと同じ流儀に限る） |

### 4.3 用語集項目

- 基礎の `definition.glossary` の正規形は **[語, 定義] のペアの配列**である（`js/content.js` の `glossary`、`js/types/pseudo/glossary.js` の `GLOSSARY` がこの形。Python のように生データがオブジェクト形式の種類でも、`index.js` でペアへ変換されて定義に載る）。
- 高度分も同じくペアで書く：`[[word, definition], ...]`（word／definition ともに string）。

> 根拠：計画書 1.3、1.4。項目形状の実物確認はベース bba3b26 の上記ファイルによる。

## 第5章 差分ファイルの配置と形式

### 5.1 配置

高度差分は、種類ごとに `js/types/<id>/` 配下に置く（`<id>` は registry の種類 id）。基礎ファイル（`index.js` 等）と同居させるが、ファイル名で明確に区別する（第7章の precache 除外パターンもファイル名に依存する）。

### 5.2 ファイル一覧と形式

#### (a) `advanced-manifest.js`（任意）

その種類の高度ファイル構成を宣言する。エクスポートは次の1つ。

```js
export const advancedManifest = {
  referenceParts: string[],   // reference part ファイル名の列挙（読み込み順）
  templatesFile: string|null, // null は「高度テンプレートなし」
  glossaryFile: string|null,  // null は「高度用語集なし」
  engineFile?: string|null,   // 任意。高度エンジンフックのファイル名
};
```

- ファイル名は `js/types/<id>/` からの相対名で書く。
- **manifest が無い場合の既定**：`referenceParts` は `["reference-advanced.js"]`、`templatesFile` は `"templates-advanced.js"`、`glossaryFile` は `"glossary-advanced.js"` とみなす。既定ファイルが存在しない場合は「追加なし」として正常に扱う（第7章の `missing`）。
- manifest に明示したファイルが存在しない・読み込めない場合は既定ファイルの不存在とは扱いが違う（第7章の `failed`）。「無いのが正常」なファイルは manifest に書かず、既定に任せること。

#### (b) reference part ファイル（既定名 `reference-advanced.js`）

エクスポートは次の2つ（どちらか一方だけでもよい。無い側は空として扱う）。

```js
export const referenceAdvanced = [ /* 追加項目（第4章 4.1 の正規形＋ status 必須） */ ];
export const referenceOverrides = [ /* 既存基礎項目への上書き定義 */ ];
```

- `referenceAdvanced`：その種類に**新規追加**する項目だけを入れる。基礎に既にある項目の複製を入れてはならない（第6章の重複規則）。
- `referenceOverrides`：既存基礎項目への上書き定義。**`name` で照合し、`name` 以外のフィールドを差し替える。`name` 自体の変更は不可**である（改名は override ではできない）。状態だけを変える場合もこの仕組みを使い、該当フィールド（導出元の `supported` に代わる新しい状態は `status` で指定する）を含むオブジェクトを書く。
- 分割：reference part は複数ファイルに分割してよい（例：Python 標準ライブラリのようにモジュール群単位）。分割する場合は manifest の `referenceParts` に全ファイルを列挙する。列挙順が合成時の追加順になる（第6章）。

#### (c) `templates-advanced.js`

```js
export const templatesAdvanced = [ /* 追加分のみ（第4章 4.2 の形状） */ ];
```

- 基礎テンプレートの複製・改変は入れない。追加分のみである。

#### (d) `glossary-advanced.js`

```js
export const glossaryAdvanced = [ /* [word, definition] のペア。追加分のみ */ ];
```

#### (e) `advanced-engine.js`（任意、予約フック）

- manifest の `engineFile` で指定する。エクスポートしうる関数は次の1つである。

```js
export function applyAdvancedEngine(definition, merged) { /* … */ }
```

- エンジンの関数テーブル拡張は、このフック経由でのみ行う。**エンジン本体にモード分岐を持ち込まない。** 種類の `index.js` や共通エンジンへ「高度モードなら〜」という条件分岐を書くことは契約違反である。
- これは予約フックであり、機構段階では未使用の種類があってよい（フックを持たない種類が大半でも構わない）。フックの具体的な使い方の初例は B1 ブロックで確定する（未決・留保 R-3）。

### 5.3 ファイル形式の共通規則

- いずれの高度ファイルも ES モジュールとし、上記の名前付きエクスポートを持つ。既定エクスポート（default export）は使わない。
- 高度ファイルから基礎ファイルを変更・再定義する副作用（基礎項目オブジェクトの直接書き換え等）を持たせてはならない。基礎への作用は `referenceOverrides` の宣言経由に限る。

> 根拠：計画書 1.3（A-11）。エンジン拡張の置き場については計画書の記述との差異を未決・留保 R-2 に記録した。

## 第6章 合成規則

合成は `js/core/catalog.js` の `mergeCatalog(base, advanced)` が実施し、その挙動はテストで固定される。`base` は種類定義の基礎カタログ（reference／templates／glossary）、`advanced` は第7章のローダーが返した差分である。

1. **基礎の順序を保持する。** 合成後の並びは、基礎項目が基礎の順序のまま先に並び、高度の追加項目がその後に続く（reference は `referenceParts` の列挙順、各ファイル内は配列順）。基礎項目の並び替えはしない。
2. **override の適用**：`referenceOverrides` は `name` が一致する基礎項目に適用し、`name` 以外のフィールドを差し替える。**存在しない `name` への override は契約違反**として `problems` に記録される（黙って無視しない）。
3. **reference の name 重複**：`referenceAdvanced` の `name` が基礎と重複する、または `referenceAdvanced` 内で重複する場合は、**契約違反として `problems` に記録され、先行側が残る**（基礎に同名があれば基礎側、高度内では先に現れた側）。意図的に基礎項目を変えたい場合は重複でなく `referenceOverrides` を使うこと。
4. **templates の id 重複**：`templatesAdvanced` の `id` が基礎または高度内で重複する場合は、同様に契約違反として `problems` に記録され、先行側が残る。
5. **glossary の同語**：`glossaryAdvanced` の語が基礎に既にある場合は**基礎側が優先**され、高度側の定義で既存の説明を書き換えない。同語の存在は警告として `problems` に記録される。
6. **状態の確定**：合成後の全項目は `status` を持つ。基礎項目は第3章 3.2 の規則で `supported` から導出し、override が `status` を指定した場合はそれで置き換える。高度追加項目は自身の `status` をそのまま使う。
7. **契約違反（`problems`）の扱い**：`problems` は監査で検出される。**違反のある差分は出荷しない。** ローダーの読み込み失敗（第7章の `failed`）とは別物であり、「読み込めたが契約に反する」場合はこちらに記録される。

> 根拠：計画書 1.3、1.4、4.3。なお規則3は計画書 1.3 の記述との差異を含む（未決・留保 R-1）。

## 第7章 ローダーAPI・読み込みとキャッシュ

### 7.1 `loadAdvanced(definition)`

`js/core/advanced-loader.js` の `loadAdvanced(definition)` は **Promise** を返し、解決値は次の形である。

```js
{
  referenceAdvanced: [],   // 全 reference part の referenceAdvanced を列挙順に連結したもの
  referenceOverrides: [],  // 同上（referenceOverrides 分）
  templatesAdvanced: [],
  glossaryAdvanced: [],
  engineModule: null,      // engineFile が指定され読み込めた場合はそのモジュール、無ければ null
  loaded: [],              // 実際に読み込めたファイル名
  missing: [],             // 存在しなかった既定ファイル名（追加なしとして正常）
  failed: [],              // 読み込みに失敗したファイル名（manifest 明示分等。下記）
}
```

- **missing と failed の区別**：
  - ファイルが存在しない**既定ファイル**（manifest が無い場合の既定名、および manifest で `null` とされた区分）は `missing` に入り、追加なしとして正常に動作する。
  - **manifest に明示されたファイル**の読み込み失敗は `failed` に入る。この場合、アプリは**基礎カタログのみで動作**しつつ、モード開示行（第8章）に**読み込み失敗の注記**を出す。黙って高度モードのふりをしない。
- **キャッシュ**：読み込み結果は種類ごとにメモリキャッシュされる。同じ種類の高度差分を繰り返し動的 import しない。
- 読み込みのタイミングは遅延読み込みとする。その種類を高度モードで初めて開いたときに読み込む（全種類分を起動時に読み込まない）。

### 7.2 precache からの除外

- 高度差分は precache に**入れない**。`scripts/precache.mjs` は、次のパターンに一致するファイルを precache 対象から除外する。
  - ファイル名が `advanced-manifest.js`
  - ファイル名が `advanced-engine.js`
  - ファイル名に `-advanced` を含む `.js` ファイル（例：`reference-advanced.js`、`templates-advanced.js`、`glossary-advanced.js`、分割した reference part）
- したがって高度ファイルの命名は上記パターンに従わなければならない。パターンに一致しない名前の高度ファイルを置くと precache に混入し、契約違反になる（チェックリスト (g)）。

### 7.3 Service Worker の扱い

- Service Worker（`sw.js`）は高度差分へのリクエストを **network-first** で扱い、成功時にランタイムキャッシュ **`programming-practice-advanced`** へ保存する。
- これにより、読み込み済みの高度差分はオフライン再訪でも使える。更新はオンライン時にネットワーク優先で伝播する。
- 基礎アセットの cache-first 方式（現行 `sw.js` の挙動）は変更しない。network-first の対象は高度差分のパターンに一致するリクエストのみである。

> 根拠：計画書 1.3（A-11、U-10／U-28 のランタイムキャッシュ方針）、1.5（SW 更新時の旧版破棄は F-09 の再測定項目）。

## 第8章 モード開示文・件数・フィルタ・到達性

### 8.1 モード開示文（モード選択 UI に常時表示）

モード選択時にトグルの直下へ常時表示する。文面は次のとおり固定であり、ブロックチームが言い換えてはならない。

- 簡易モード選択時：
  > 簡易モード：よく使う関数を中心に収録しています。全ての関数が実装されているわけではありません。網羅的な収録は高度モードにあります。
- 高度モード選択時：
  > 高度モード：各言語・ツールの関数を網羅的に収録しています。項目ごとに「対応／未対応／未検証」を表示します。

- 高度差分の読み込み失敗時（第7章の `failed` がある場合）は、この開示行に読み込み失敗の注記を追加する。

### 8.2 件数表示と状態フィルタ

- リファレンスビュー先頭に、種類別に「対応 X 件／未対応 Y 件／未検証 Z 件」を表示する（X／Y／Z は合成後カタログの `status` 別実数）。
- 状態フィルタ（全て／対応のみ／未対応／未検証）を提供する。

### 8.3 到達性（F-02）は全状態に適用する

- 検索・チップ・個票の到達性（F-02）は、対応・未対応・未検証の**全状態の項目**に適用される。未対応・未検証だから検索に出さない、チップにしない、という扱いは完全性の欠陥である。
- コード内で使われた項目が未対応／未検証なら、使用中チップにも同じ状態タグを付け、クリックで個票（理由つき）を開けるようにする。実行時は第3章のとおり正直に停止する。
- F-02 の機械照合は、基礎・高度の両カタログに対してそれぞれ回せる形を維持する。

> 根拠：計画書 1.2（U-43）、4.2、1.3（F-02）。

## 第9章 テンプレートに関する追加規則

- テンプレートのコードが未対応項目に**黙って依存してはならない**（第5章チェックリスト (f)）。教材として未対応・未検証項目に触れる場合は、解説文（`intro`）でその旨を明示する。
- 高度テンプレートは高度モードでのみ表示される。基礎テンプレートは両モード共通で不変である。用語集も同様に、高度分は高度モードでのみ表示され、基礎の説明を書き換えない（第6章 規則5）。

> 根拠：計画書 1.4、4.2-4。

## 第10章 種類の追加について

- 種類一覧は registry（`js/types/registry.js`）のデータ駆動であり、機構は種類数を固定しない。簡易16種／高度17種のような**モード間の種類数の差**を機構は許容する。
- Power Automate の分割（U-47）で高度モードに新種類「Power Automate（クラウド）」（WDL 式関数）が追加される件は、当該ブロック（B2）の作業であり、**本機構の契約範囲外**である。既存種類「Power Automate（デスクトップ）」は不変に残す。
- ただし新種類も本契約の差分形式に従う。すなわち、新種類が高度モードでのみ現れる場合でも、その基礎定義と高度差分の関係、`status` の付け方、合成・読み込みの規則は本書のとおりとする。具体的な落とし込み（新種類の基礎層をどう置くか）は未決・留保 R-5 に記録する。

> 根拠：計画書第3章、決定記録 U-47（J-1 推奨案＝分割を承認）。

## 第11章 ブロックチームのチェックリスト

差分を出す前に、各ブロックは次を全て確認すること。1つでも満たさない差分は出さない。

- (a) 全高度項目に `status` を付けたか
- (b) `name`／`id` の重複がないか
- (c) override の対象（`name`）が実在するか
- (d) F-02 の存在＋到達性を基礎・高度の両カタログで機械照合したか
- (e) `supported`（`status: "supported"`）とした項目がエンジンで実際に到達・実行できるか
- (f) テンプレートが未対応項目に黙って依存していないか
- (g) precache に高度ファイルが混入していないか

## 未決・留保

機構段階で決めていないこと、および計画書・確定仕様の間で検出した食い違いを、正直に記録する。ここに書かれた事項を、ブロックチームが推測で埋めてはならない。不明な場合はコーディネーターへ確認すること。

- **R-1（計画書との食い違い：name 重複時の優先順位）**：計画書 1.3 は「合成規則（名前の重複時は高度側の状態・文面が優先）はテストで固定する」と書く。一方、確定仕様の合成規則は、重複を契約違反として `problems` に記録し先行側（基礎側）を残すとし、基礎項目の意図的な変更は `referenceOverrides` 経由に一本化している。本書の第6章は確定仕様に従って書いた。計画書本文の当該文の改訂要否はコーディネーターの判断事項として留保する。
- **R-2（計画書との食い違い：エンジン拡張の置き場）**：計画書 1.3 は「エンジンの関数テーブル拡張は、種類の `index.js` が基礎＋高度の両テーブルを合成する形」と書く。確定仕様は拡張の経路を `advanced-engine.js` の `applyAdvancedEngine(definition, merged)` フックに一本化し、エンジン本体へのモード分岐の持ち込みを禁じている。本書の第5章は確定仕様に従って書いた。`index.js` 側で合成のために最低限必要な配線の範囲は未確定であり、B1 の初例で確定する。
- **R-3（engineFile フックの具体的な使い方）**：`applyAdvancedEngine` の引数 `merged` の正確な形（合成済みカタログそのものか、関数テーブルを含む構造か）、フックの戻り値の扱い、フックが例外を投げた場合のフォールバックは、機構段階では決めていない。初例は B1 ブロック（UI.Vision RPA／コマンドプロンプト）で確定し、本書へ追記する。それまではフックを使わずに済む差分を原則とする。
- **R-4（種類単位の高度専用表示の詳細）**：種類ごとに高度モードでだけ見せる表示（例：種類別の注記文、分割した reference part ごとの見出し）の詳細は決めていない。第8章の件数表示・状態フィルタ・開示文が契約で固定する表示の全てであり、それ以外の高度専用表示は各ブロックが勝手に足さない。
- **R-5（新種類「Power Automate（クラウド）」の基礎層の置き方）**：U-47 の新種類は簡易モードに存在しないため、「基礎カタログ＋高度差分」という二層構造のどちら側に新種類の項目群を置くか（基礎定義のみで完結させるか、基礎は空に近くし全項目を高度差分に置くか）は決めていない。B2 着手前にコーディネーターが確定する。
- **R-6（`setMode` の不正値・保存失敗時の扱い）**：`setMode(mode)` に未知値を渡した場合に例外とするか無視するか、および localStorage への保存が失敗した場合（容量超過等）の扱いは決めていない。`getMode()` 側のフォールバック（第2章）で利用者影響は簡易モードへの帰着に留まる。
- **R-7（リファレンス項目の拡張フィールド）**：第4章 4.1 の表に無いフィールド（例：Python の生データにある `args` や `expected` に相当する情報）を正規形の任意フィールドとして追加するかは決めていない。現行画面が表示するのは `returns` と `source` までであり、それ以外の情報は当面 `description`／`caution` の文面に含める。
- **R-8（`mergeCatalog` の戻り値の正確な形）**：合成結果と `problems` をどのような形で返すか（戻り値オブジェクトのプロパティ名等）は、機構実装時にテストとともに固定する。本書では「合成済みカタログが得られ、契約違反は `problems` として収集・参照できること」までを契約とする。
- **R-9（ランタイムキャッシュの版管理）**：ランタイムキャッシュ `programming-practice-advanced` について、高度差分ファイルの版が上がった場合に旧版を破棄する具体手順は決めていない（計画書 1.5 が F-09 の再測定項目への追加を求めている段階）。network-first のためオンライン時は常に最新が優先されるが、オフライン時に旧版が残る期間の扱いは F-09 再測定で確定する。
