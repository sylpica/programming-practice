## 角度1：無言の打ち切り総点検（work/r5-truncate.mjs、約40ケース）

方法：全13種類について、上限が存在しうる箇所（パス数 2000、手順数 600、ループ反復 100、式・ブロックの深さ 64、処理数・時間、ソース長、文字列・配列の大きさ）を狙った入力を種類ごとに作り、結果の `truncated`／`reasons`／trace 内の上限注記／明示エラーのいずれかで告知されるかを検証した。

### 告知つき（正常）を確認したもの
- **パス数上限**：JavaScript の独立 if×11（2,048 通り）→ 2,000 パスで打ち切り＋`reasons: パス数の上限`。ImageJ の未知分岐×25 → 143 パス＋打ち切り告知（フォーク上限 24 の仮定埋め＋時間上限）。CloudFormation の処理数上限（リソース 6,000 件）→ トップレベルエラー「変換の探索上限で停止しました」。CFN のパス数上限はコード上 `truncated`＋`reasons: 変換経路の上限` を確認（ハンドラ分岐による状態爆発の動的再現は、未知値を注入する手段がなく未実施）。
- **手順数上限（trace 600）**：JavaScript／R／AutoHotkey／C の 700 文コード → trace 内注記「手順数の上限で説明を停止しました」＋reasons。VBA も reasons で告知（下記観察）。ImageJ は独自上限（ステップ省略注記＋Log 出力 200 行上限＋注記つき）。
- **ループ反復上限（100）**：JavaScript／R／AutoHotkey／C／C++／C#／UI.Vision の 150〜100,000 回ループ → 「ループ上限で説明を停止しました」＋reasons。VBA の For 500 回 → 「100回で表示を打ち切りました。ループは続く可能性があります」＋reasons。ImageJ の 10,000,000 回ループ → 100 回で打ち切り注記＋truncated（ハングなし、12ms）。Power Automate の 150 要素 For each → 同様に上限注記。PowerApps の ForAll（Sequence(150)）→ 上限に当たらず全件処理し、合計 1,136,275 が正しい。
- **深さ上限**：式の入れ子 100（JavaScript）→ 明示エラー「式の入れ子が深すぎます」。PowerApps の If 入れ子 70 → 解析時に同エラー。VBA のブロック入れ子 70 → トップレベルで明示停止。C／C++／C# の既知条件ブロック入れ子 70 → 単一パスがエラーパスとして可視化（失われる兄弟パスが存在しない）。CloudFormation の JSON 入れ子 3,000 → 明示エラー「JSONの入れ子が深すぎます」。
- **Python 固有上限**：while 20,000 回 → 「説明の上限：繰り返しが多いため…」の diag 注記が trace と出力欄に出る。range(150000) の反復 → truncated＋reasons＋注記。再帰（f(n)=f(n+1)）→ 「関数の呼び出しが深くなりすぎたため、ここで止めます」と注記して停止（ハングなし）。`"a" * 300000` → 「文字列の繰り返しが大きすぎるため、結果は省略します」と注記。for 5,000 回 → 「（2回目から 4999 回目までの手順は省略しました。変数の最終状態は下の「最終状態」に出ます）」と要約し、最終結果 5000 は正しい。
- **その他**：C の巨大配列宣言（`int a[10000000];`）→ 明示エラー「配列長が不正または上限を超えています」。JavaScript の再帰関数定義は未対応の明示停止（JS の掲載範囲にユーザー定義関数がない）。JavaScript の文字列倍々（2^20＝約 105 万字）→ 値・長さとも正しく処理。

### R5-N1（P2・新規）：C# の else-if 連鎖でパスが無言欠落する（R4-N1 と同根・別経路）
再現（work/r5-cs-chain.mjs）：`string s = Console.ReadLine();` の後に else-if を連ねる。
- 64 条件＋else：**65 パス完全**（x=1〜64 と else の x=-1 がすべてある）。
- 65 条件＋else：**65 パスと表示されるが内訳が違う**。x=1〜64 の 64 パスと「ブロックの入れ子が深すぎます」というエラーパス 1 件のみで、**x=65 のパスと else（x=-1）のパスが欠落**。`truncated=false`、`reasons=[]` で、欠落の告知は一切ない。
- 機構は R4-N1 と同じ（else-if が otherwise 内の入れ子として共有実行器 executeProgram の深さ上限 64 を消費し、上限超過がパス内エラーに変換されるため打ち切りとして記録されない）。R4-N1 の対象は JavaScript／R／AutoHotkey だったが、C#（c-family のパーサ＋共有実行器）でも同じ無言欠落が起きることを本ラウンドで新規に検出した。なお C／C++ は、コード単体では未知条件を作る手段がなく（標準入力の未知値は C# の Console.ReadLine のみ）、既知条件の連鎖では単一パスがエラーパスとして可視化されるため、この無言欠落は再現しない。
- 判定理由：要件第4章「未表示のパスがある場合はその旨を表示」に反する無言欠落で、R4-N1 と同じ P2。

### 観察（欠陥でない）
- VBA の手順数上限は trace 内に注記がなく、trace が 600 件で静かに止まる。ただし結果の reasons（「手順数の上限」）が立ち、画面の打ち切りバナー（reasons 表示）に使われるため、ユーザーへの告知はある。同種の他エンジン（trace 内注記＋reasons 併記）と比べると表記が一段弱い。
- Python の while 上限（MAX_ITERS）は diag 注記が trace・出力に出る一方、結果の `truncated` が false のまま（range 反復のケースでは true になる）。バナーは出ないが画面内の注記で告知されるため無言ではない。
- Python の `list(range(200000))`（MAX_RANGE=100,000 超）は、注記なしで変数が「実行時に決まる：値」（不明値）になる。文字列繰り返しのケースには明示注記があるのと対照的だが、不明値化そのものがこのアプリの「決まらない値は捏造しない」契約どおりの正直な表現であり、値の打ち切り（途中で切れた値の提示）ではないため欠陥としない。
- JavaScript で約 105 万字の文字列を作ると、最終状態に文字列全文（1,048,576 字）が無制限に表示される。打ち切りではなく過剰表示であり、Python の 20,000 字＋「…」という上限と一貫性はないが、情報の欠落ではないため観察に留める。

## 角度2：ナレーション表記の一貫性（work/r5-narration.mjs）

方法：全88テンプレート＋値ナレーション用コーパス（Boolean／null 系／ベクトル・配列／文字列などを代入・出力する小コードを種類別に追加）の trace・出力・最終状態を文字列化し（計 2,397 文字列）、種類ごとに「その言語の正規表記と矛盾する外国記法」のパターンで走査した。生ヒット 79 件を全件裁定した。

### R5-N4（P3・新規）：VBA の Boolean 値が小文字 true／false で表示される
再現（work/r5-bool-display.mjs）：`Dim b As Boolean`＋`b = True`＋`MsgBox b`。
- 出力（MsgBox）が **"true"**（実 VBA は "True"）。
- trace が「b ← true」「MsgBox に true を出力します」、最終状態も "true"。
- 宣言直後の trace は「b は boolean の変数です：false」— 初期値の表示も小文字で、型名も実 VBA の "Boolean" ではなく小文字 "boolean" になっている。
- テンプレートには Boolean 変数を扱うものがないため第4ラウンドの走査では表面化せず、通常のユーザーコードで即座に当たる。値の意味は一意で誤解は生じにくいため P3。機構は VBA エンジンの display() が JS の真偽値をそのまま文字列化していること。

### R5-N5（P3・新規）：PowerApps の Blank が「null」とナレーションされる
再現：`Set(n, Blank()); Notify(Text(n))` の trace が「**n に null を設定し**、表示数式を再計算します」。Power Fx に null という値・用語はなく、ユーザーが書いた Blank() の結果を別言語の用語で説明している。最終状態の変数 JSON でも `"n": null` と出る（こちらはモデル JSON 表現の一部だが、trace の説明文はアプリ自身の言葉である点が問題）。意味は通じるため P3。

### R5-N6（P3・新規）：R の NULL が小文字「null」と表示される
再現：`u <- NULL; print(u)`。
- trace「u に null を代入します」、**出力「null」、最終状態「null」**。実 R では NULL（大文字）であり、`print(NULL)` の表示も "NULL"。
- R4-N3 は「trace 代入ナレーションでベクトル・論理値が JS 記法になり、出力・最終状態の R 記法と矛盾する」という欠陥だった。本件は同根（共有 formatValue の JS 記法）だが、NULL については**出力・最終状態も含めて全表面が小文字**であり、R4-N3 の「出力・最終状態は正しい」という前提が成り立たない別表面のため、新規として数える。
- あわせて R4-N3 の範囲確認：数値ベクトル・スカラーの代入ナレーション（`total に [\n 1\n] を代入します` 等、r-loop／r-index／r-frame／r-filter-loop）も同じ JS 配列表記であり、R4-N3 の記述どおり同根・同表面として扱う（新規に数えない）。data.frame の代入ナレーション内でも列の論理値が「true／false」で出る（r/corpus の data.frame 例）— これも R4-N3 と同根。

### R5-N7（P3・新規）：C# の bool が trace・最終状態で小文字、出力と矛盾する
再現（work/r5-bool-display.mjs）：`bool b = true; Console.WriteLine(b);`。
- 出力は **"True"**（正しい。WriteLine 側で変換している）。
- しかし trace は「b を bool として用意します：**true**」「標準出力へ出します：**true**」、最終状態も "true"、`b（bool、有効）：[ true ]` と JS 記法のまま。
- 同じ画面内で出力（True）と説明・最終状態（true）が矛盾する、R4-N3 と同じ類型。C++ では小文字 true が正規表記なので欠陥ではない（c-family 共有の formatValue が C# の表記に追従していないことが原因）。C# テンプレートは通常の bool 変数を扱わないため従来の走査で表面化しなかった。P3。

### ヒットしたが欠陥でないと判定したもの
- ImageJ の最終状態に出る画像プロパティ JSON 内の `"thr": null` 等：モデルデータそのものの JSON 表示であり、第4ラウンドの裁定（ドメイン構造の表示は漏れでない）と整合する。
- CloudFormation のハンドラ呼び出し trace に出る Python repr の event 表示（`'params': {}` 等）：ハンドラは Python であり、その引数表示として内部的に一貫している。`None` の混入ではなく Python 表記そのもの。
- PowerApps のコントロール状態 JSON 内の `"Text": null`：モデル JSON の表現であり、ナレーションではない（R5-N5 は trace の説明文を指す）。
- JavaScript の NaN／undefined、Python の True／False／None、R の TRUE／FALSE／NA の出力などは各言語の正規表記どおりで、混入なし。AutoHotkey／ImageJ のコーパスでも外国記法の混入は見つからなかった。
- 既知残件 R4-N4（VBA input の「false or」）は本走査でも再現したが、再報告しない。
