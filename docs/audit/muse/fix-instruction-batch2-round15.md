## 0. 前提と全体ルール

- 対象：同梱の `consolidated-residual-register.md`（以下「台帳」）のうち、第15ラウンド由来の次の範囲のみ。新規グループ RG-42〜RG-48 の7グループ（9件）と、既存グループへの追加表面 RG-04（R15-N13）、RG-06（R15-N4／N5／N8／N9）、RG-07（R15-N10）、RG-14（R15-N15）の7件。合計16件（P2 ×5、P3 ×11）。各項目の再現手順は台帳の「統合元」（findings-round15-solo.md＋項目ID）を参照すること。再現コードと期待挙動は同梱の findings-round15-solo.md に全部ある。
- 第4ラウンド対象（RG-01〜RG-41 の当初分）は本バッチの対象外。第4ラウンドの節目で確定した実装・宣言とは矛盾させないこと（詳細は §5）。
- 進行順序：ローカルで全修正を終える → 再検証 → 節目の1回で配信する。配信ルールの詳細は §6 に従うこと。
- `PROGRESS.md` は修正の節目コミットの中に同梱して更新すること（単独 push 禁止）。監査対応レポートは `docs/audit/CODEX-R5.md` に新規作成し、RG ごとの処置（実装した／正直な未対応に格下げした／第4ラウンドで解消済みだった／理由付きで保留した）を表で示すこと。ユーザーが自分で検証する必要のない形で、検証結果（テスト件数、再現コードでの確認結果）を具体的な数値で報告すること。
- フロントエンドの実装に触れる場合は Modern Web Guidance（GoogleChrome 公式スキルパック）の導入を試み、関連ガイドを参照すること。導入の成否（環境制約で不可の場合を含む）を報告に含めること。ただしベンダー実施ベンチマーク由来のガイドであり、従来の監査基準・共通UIルール（スクロールを減らす／文字の切れを作らない／説明文は下の方へ）が優先する。

## 1. 修正の大原則（監査の裁定から。第4ラウンドと共通）

1. **誤った値の捏造と、虚偽の原因表示は不可。** 実装できない構文・機能は、構文名・機能名を挙げた「未対応」の正直な宣言で停止し、宣言（DEVELOPMENT.md の対応・未対応リストと台帳の扱い）を実装と一致させること。正直な未対応化は劣化ではなく、受理可能な修正として扱う。
2. **受理して捨てる経路を作らない。** 引数・構文・節を受け取って無言で無視する実装は、新たに作らないこと。既存の該当経路はこの原則で改める。本バッチでは特に、文字列リテラルの内容を書き換える前処理（RG-42）と、他ダイアレクトの構文の無言受理（RG-43）がこの原則の対象である。
3. **表示は言語の正規表記に合わせる。** trace・出力・最終状態の3表面で矛盾させない。実在しない表示形式を作らない。
4. **横断的な基盤の共通化を優先し、第4ラウンドの基盤を踏襲する。** RG-43（ダイアレクト分離）は、第4ラウンドで RG-06／07／08 向けに共通化した「未対応を正直に宣言する」仕組みと、種類ごとの字句・文法定義の上に実装すること。RG-04 の追加表面（-0.0 の符号）は、第4ラウンドで種類別化した値整形の中で直すこと。個別パッチの積み重ねで表面ごとに食い違う実装にしないこと。

## 3. 再検証の要求（多角検証）

修正後は、修正した側自身が次の角度で再検証し、結果を数値で報告すること（Muse 側の独立再監査も別途行う）。

1. **ブラインド再導出**：答え（期待挙動）を見ずに、各言語の一次資料（公式ドキュメント・マニュアル・実物ソース）から期待値を再導出し、実装と照合する。特に RG-43／45／47 は実物（実 R、実 AutoHotkey v2 の仕様、Node／gcc の字句規則）との照合を必須とする。
2. **実コンパイラ・実ランタイム照合**：C／C++／Python／JavaScript は実コンパイラ・実ランタイムで、R は実 R で、修正対象の再現コードを実物でも実行して一致を確認する。
3. **テストの全量実行**：既存テスト全件を実行し、失敗0を確認する。失敗を隠すためのテスト削除・緩和はしない（テストを変える場合は理由を CODEX-R5.md に明記）。
4. **実ブラウザ実地**：公開前のローカルビルドで、13種類の教材テンプレート全件の実行・パス切替・チップ・解説リンクを実際に操作し、第4ラウンドまでの受け入れ条件（RG-28／29／37 等）が維持されていることを確認する。375px 幅と広幅の両方で、文字の切れ・はみ出しがないことを確認する。
5. **ファズ／境界**：今回修正したパーサ・字句解析の周辺（ダイアレクト混在の演算子・制御文、エスケープ、リテラル形式、NaN／-0.0 の境界）をランダム・境界入力で叩き、新たな誤値・虚偽原因・無言消失が出ないことを確認する。特に RG-43 の修正が、本来の所有ダイアレクト（R の `<-`、AutoHotkey の `:=`／Loop、Power Fx のブロックコメント）を壊していないことを横断確認すること。
6. **再現コードの回帰確認**：本バッチの対象16件の再現コード全件について、修正後に再実行し、結果（動作／正直な停止／正しい値）を CODEX-R5.md の表に RG 単位で集計して示すこと。あわせて、第4ラウンド対象135件の再現コードについても、今回触れた基盤（字句解析・値整形・R エンジン）に関わる範囲で回帰がないことを確認し、確認範囲と件数を明記すること。

## 4. 収束条件

- 修正と再検証の後、Muse 側が**新しい角度を含むフルラウンド**（従来の角度に加え、少なくとも1つの新規の角度）を実施し、**新規の実質的欠陥がゼロ**であることをもって収束とする。片側だけの判定で収束としない。
- 収束に至らなかった場合は、新規指摘を台帳に追加したうえで、次節目で同じ手順を繰り返す。
- 任意の積み残し（収束に必須でない残件）が新たに出た場合は、実施せず、内容と「任意のため実施しない」旨を報告すること。

## 5. 第4ラウンドとの関係（矛盾させないための注意）

- 本バッチは第4ラウンドの節目コミットを起点とする。第4ラウンドで導入・変更された基盤（未対応宣言の仕組み、値整形の種類別化、種類ごとの字句・文法定義、宣言リスト DEVELOPMENT.md の記載）がある場合は、その方針と実装様式を踏襲し、別系統の仕組みを新設しないこと。
- RG-43（ダイアレクト分離）は RG-06／07／08 の基盤と密接に関連する。第4ラウンドの修正で既にダイアレクト別の分離が部分的に入っている場合は、それを拡張する形で実装すること。
- RG-45（R の NaN）と RG-03（R の NULL）は欠損値の扱いとして一貫させること。RG-47（データフレームの [[）の修正では、第4ラウンドまでの R の添字・ベクトル操作の正挙動を壊さないこと。
- 着手前の再確認で「第4ラウンドで解消済み」と判定した項目は、その根拠を CODEX-R5.md に項目ごとに残すこと（Muse 側の照合対象になる）。

## 6. 配信ルール（承認カードを増やさないための確定ルール）

- **節目一括**：配信は節目単位にまとめ、書き込みコールは最小構成とする。push-files 1回（全ファイル集約）＋必要な場合のみ PR 作成1回・マージ1回。小さい修正の逐次配信はしない。
- **付随書き込みの禁止**：PR の本文・タイトル編集、状態トグル（CI 再実行目的を含む）、Issue／PR コメントの連投、余分なブランチの作成・削除はしない。必要な変更は次の push に同梱するか、作成時に一括で済ませる。
- **バースト実行**：配信の書き込みは短時間に連続して実行し、終わったら次の節目まで書き込みを出さない。
- **報告の必須記載**：配信の報告には **「使った書き込みコール数：N件」** を必ず含めること。
- **PROGRESS.md**：節目コミットに同梱して更新する（単独 push 禁止）。再開時の状態把握は PROGRESS.md とリポジトリの状態から行えるように保つこと。
- **監査対応レポート**：`docs/audit/CODEX-R5.md` を新規作成し、配信に同梱する。
