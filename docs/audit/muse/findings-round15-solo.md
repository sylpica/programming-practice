## 角度1：パーサのコードリーディング監査（母数：列挙158箇所／到達プローブ51件）

方法：`js/core/script.js`（1,169行）と `js/core/c-family.js`（1,240行）を読み、throw／unsupported／api.fail の発生箇所を grep で全数列挙した（script.js 46行、c-family.js 112行、計158行）。そのうち汎用・虚偽表示になりうる箇所と、ダイアレクト分岐の無い共有処理（トークナイザの演算子表、statement／simple の共有実装、C系 parse() の前処理）を狙って到達入力51件を実行した。

正直だった到達例（欠陥でない）：未終了ブロックコメント「コメントが閉じられていません」、呼び出しの閉じ括弧欠落「) が必要です」、配列の閉じ欠落「] が必要です」、式先頭のカンマ「式を解釈できません：,」、JS での `int x = 3;`「未対応：…：int」、C での `checked`「未対応：…：checked」、R の右代入 `->`「未対応：…：->」、未知エスケープ「未確認の文字エスケープ」（カテゴリを名指すため観察に留める。角度2参照）。

### R15-N1（P2）：C系前処理が文字列リテラル内の `std::` を無言で削除する

- 根本原因：`js/core/c-family.js` の `parse()` が、#include／using 行でない全行に `line.replace(/std::/g, "")` を無条件適用する。文字列リテラルの内容も対象になる。
- 再現（同根の全表面を洗った）：
  - C++：`std::cout << "std::ok" << std::endl;` → 出力は **"ok"**（実物は "std::ok"）。
  - C++：`std::cout << "a std:: b"` → 出力 **"a  b"**。
  - C：`printf("std::ok\n");` → 出力 **"ok"**。
  - C#：`string s = "std::ok"; Console.WriteLine(s);` → 出力 **"ok"**。
- 無言の誤出力であり、学習者が気づけない。P2。

### R15-N2（P2）：他ダイアレクトの代入演算子 `<-`／`:=` が JS／C系に漏れる

- 根本原因：トークナイザの演算子表と `ScriptParser.simple()` の代入演算子リスト（`=`／`<-`／`:=`／複合代入）がダイアレクト無条件。`<` と単項マイナスを詰めて書いた比較が、R の代入演算子として最長一致で奪われる。
- 再現（同根の全表面を洗った）：
  - JavaScript（文位置）：`let x = 5; x<-1; console.log(x);` → **x が 1 に書き換わる**（実 Node は比較式として評価し x は 5 のまま）。
  - JavaScript（条件位置）：`if (x<-1) {…}` → 「エラー：) が必要です」（実物は false 分岐）。
  - JavaScript（宣言右辺）：`let y = x<-1;` → 「未対応：…：宣言の区切りが必要です」。
  - C（宣言右辺）：`int y = x<-1;` → 「エラー：式を解釈できません：<-」（実 gcc は y=0）。
  - C（条件位置）：`if (x<-1)` → 「エラー：) が必要です」。
  - Power Apps：`Set(y, x<-1)` → 「エラー：) が必要です」。
  - AutoHotkey：`y := x<-1` → 「エラー：式を解釈できません：<-」（実 AHK は比較）。
  - `:=` の別表面：C `x := 5;` と JavaScript `x := 5;` がどちらも**無言で代入として実行**される（両言語に `:=` は無い）。
- R の `<-` と AHK の `:=` 自体は正しく動作する。壊れているのは他ダイアレクトへの漏れで、無言の値書き換えを含むため P2。

### R15-N3（P2）：C系が R／AHK の制御文を継承して無効なコードを実行する

- 根本原因：`ScriptParser.statement()` の `repeat`／`Loop`／`next` 処理にダイアレクト判定が無く、C系パーサもそのまま使う（JS だけが明示的に弾く）。
- 再現（同根の全表面を洗った）：
  - C：`Loop 2 { x++; }` → 無言で実行され x=2 を出力する（C に Loop 文は無い）。
  - C++：`repeat { x++; if (x >= 2) break; }` → 無言で実行され 2 を出力する。
  - C#：`Loop 2 { x++; }` → 無言で実行され 2 を出力する。
  - C／C#：while ループ内の `next;` → continue として無言で実行され、反復結果が変わる（実物は未宣言名のコンパイルエラー）。
- 存在しない構文を「動いた」ことにしてしまうため P2。

### R15-N4（P3）：C系の前処理行の認識が狭く、正規の行が無関係なトークンを名指す

- 根本原因：`parse()` の前処理が「行頭から `#include <...>` の形で終わる行」と「`using namespace std;`／`using System;` で終わる行」だけを空白化し、それ以外は通常のパーサに落ちて無関係なトークンを名指す。
- 再現（同根の全表面を洗った）：
  - `#include<stdio.h>`（空白なし、正規の C）→ 「未対応：この構文は説明に対応していません：#」。
  - `#include <iostream> // I/O`（末尾コメント）→ 同じく「#」を名指す。
  - `using namespace std; // ns`（末尾コメント）→ 「未対応：…：namespace」。
  - `using std::cout;`（正規の using 宣言）→ 「未対応：…：cout」。
- いずれも学習者が直すべき箇所（行の形式そのもの）を指していないため P3。

### R15-N5（P3）：sizeof の未対応形がキャスト扱いの虚偽表示になる

- 再現：C++ `sizeof(int*)` → 「未対応：この構文は説明に対応していません：キャストのこの形式は未対応です（ポインタ・参照・修飾型等）」。sizeof の話をしているのに「キャスト」と表示される。
- 別表面：`sizeof(struct Foo)` → 同じくキャスト扱いの表示。
- 別表面：`sizeof(unsigned long long)`／`sizeof(long long)` → パスエラー「未対応：未対応のsizeof対象です」。long long は標準の型で、モデルの long は 64 ビット設定もあるため、対象名を挙げない汎用表示は不正確。
- 根本原因：`parseSizeof` が型パターンを認識できないと false を返し、式パーサが `(` を見て parseCast に進む設計。sizeof(変数)／sizeof(式) は正常動作を確認した。

### R15-N6（P3）：R で `/* */` がコメントとして無言で除去される

- 再現：`x <- 4 /* 2 */ + 1` → **x = c(5)** として無言で実行される。R にブロックコメントは存在せず、実 R では `/*` は除算と乗算の演算子列であり、この式は構文エラーになる。
- 根本原因：共有トークナイザが `/* */` の除去をダイアレクト無条件で行う。Power Fx は公式にブロックコメントを持つため対象外とし、R のみを数える。P3。

### R15-N7（P3）：AutoHotkey のバッククォート制御エスケープが文字に化ける

- 再現：`MsgBox "x`ay"` → 出力 **"xay"**。同様に `` `b ``→"b"、`` `f ``→"f"、`` `v ``→"v"。
- 実 AutoHotkey v2 の Escape Sequences（公式）では `` `a ``=ベル（0x07）、`` `b ``=バックスペース（0x08）、`` `f ``=フォームフィード（0x0C）、`` `v ``=垂直タブ（0x0B）。
- 根本原因：共有トークナイザの AHK エスケープ処理が n／r／t だけを変換し、それ以外は「文字そのもの」を返すフォールバックになっている。エラーにならず値が静かに変わるため P3。

### R15-N8（P3）：C／C++ の隣接文字列リテラル連結と接頭辞リテラルが虚偽原因で停止する

- 再現：C `printf("ab" "cd\n");` → 「エラー：) が必要です」。実 C は翻訳フェーズで連結され "abcd" を出力する。
- 別表面：C++ の cout チェーン内 `"ab" "cd"` → 「未対応：この構文は説明に対応していません：<<」（<< は対応済みのはず）。
- 別表面：C `printf("%s\n", u8"hi");` → 「エラー：) が必要です」（u8 接頭辞が式として解釈できない）。
- 根本原因：式パーサにリテラル同士の並置（連結）と接頭辞つきリテラルの扱いが無く、後続トークンを不足・未対応と誤認する。

### R15-N9（P3）：C++／C# の raw 文字列が虚偽・汎用の原因表示で停止する

- 再現：C++ `std::string s = R"(a\nb)";` → パスエラー「NameError：未定義の名前：R」。raw 文字列という構文名も、未対応の宣言も出ない。
- 別表面：C# `string s = """a\nb""";` → 「未対応：この構文は説明に対応していません："」と引用符1文字だけを名指す。
- 対照：C# の逐語文字列 `@"..."` は `@"` と構文の開始を名指すため正直な停止として数えない。

### R15-N10（P3）：Power Fx の文字列補間が汎用エラーで停止する

- 再現：`Set(n, 3); Notify($"n={n}")` → topErr「エラー：式を解釈できません：$」。
- Power Fx の文字列補間は Microsoft 公式に機能として存在する（Power Platform Blog「Power Fx: String interpolation」）。アプリの対応・未対応リスト（js/types/powerapps/index.js の support）に記載が無く、停止メッセージは汎用の解釈エラーで、学習者には「$ が書けない」に見える。R11-N1（C# 補間）と同型だが種類が別のため別表面として数える。

## 角度3：数値の極端値 第2弾 — 伝播の追跡（母数：42件）

方法：-0、非正規化数に近い極小値（1e-320、5e-324）、NaN、±Inf を生成し、加減乗除・比較・等価・論理・表示への伝播を追った。第6・7ラウンドの「表示形式」ではなく伝播そのものが対象。実物照合：CPython／Node／gcc／g++ をローカル実行（Python 6スニペット、C／C++ 3プログラム、Node 1件）。R は公式マニュアルで裁定。

実物と一致した主な伝播（欠陥でない）：

- JavaScript：-0 の逆数 -Infinity、=== 0、NaN の全比較 false、5e-324 / 2 = 0 まで Node と完全一致。
- Python：1.0 / -0.0 と (-0.0) ** -1 の ZeroDivisionError、-0.0 の表示と == 0.0、Inf - Inf = nan、1e-320 の非正規化数と 1e10 除算での 0 への丸め、NaN の真値性まで CPython と一致。
- C／C++：NaN 比較（== で 0、!= で 1）、1 / -0.0 の符号判定は gcc／g++ と一致。
- C#：NaN の ==／< が False、1.0 / -0.0 = -Infinity、1e-320 > 0 は仕様どおり。
- R：NA の比較 = NA、NaN の算術 = NaN、Inf - Inf = NaN、-0 == 0 = TRUE、is.na(NaN) = TRUE は公式どおり。
- AutoHotkey：-0.0 = 0 の成立、1.0 / -0.0 の ZeroDivisionError は AHK v2 の規則と一致。
- ImageJ：1 / -0.0 = -Infinity、NaN == NaN が 0（Java 意味論）は実物どおり。
- Power Apps の 1 / -0 = -Infinity と NaN 比較は、0除算そのものの扱いが既知 RG-02 の根であるため新規に数えない。

### R15-N11（P2）：R の NaN が比較・論理演算で NA にならない

- 再現：`print((0/0) == (0/0))` → **c(FALSE)**、`print((0/0) < 1)` → **c(FALSE)**、`print((0/0) != 1)` → **c(TRUE)**、`print((0/0) <= (0/0))` → **c(FALSE)**、`print((0/0) >= 1)` → **c(FALSE)**、論理演算 `(0/0) & TRUE` → **c(FALSE)**、`(0/0) | FALSE` → **c(FALSE)**。
- 実 R（公式 Relational Operators）：「Missing values (NA) and NaN values are regarded as non-comparable even to themselves, so comparisons involving them will always result in NA」。論理演算でも NaN は NA として扱われる。
- 根本原因：R エンジンの二項演算は NA オブジェクトだけを欠損として先行処理し、数値 NaN は baseBinary の JS 意味論（NaN 比較は false、!= は true）に落ちる。条件分岐の材料になる比較で誤った真偽を返すため P2。算術（NaN のまま伝播）は正しい。

### R15-N12（P3）：Python の NaN の自己比較が同一性で True になる

- 再現：`n = float("nan")` の後 `print(n == n)` → **True**（実 CPython は False）、`print(n != n)` → **False**（実物は True）、`print(n <= n)` → **True**（実物は False）。`n < 1` は False で一致。
- 根本原因：Python エンジンの eqVal が「同じオブジェクト同士は等しい」と同一性で先行判定し、float の NaN にも適用される。CPython の == は同一オブジェクトでも値比較であり、NaN は自分自身とも等しくない（`n in [n]` が True なのは in の同一性規則で、アプリも True で一致。混同していない）。
- 同一変数を両辺に置く自己比較でのみ現れるため P3。

### R15-N13（P3）：C系で -0.0 の符号が全表示面から落ちる

- 再現：C `double z = -0.0; printf("%f\n", z);` → アプリ **"0.000000"**、実 gcc **"-0.000000"**。C++ `std::cout << z` → アプリ **"0"**、実 g++ **"-0"**。C# `Console.WriteLine(z)` → アプリ **"0"**（実 .NET は "-0"）。最終状態の表示でも z は "0"。
- 値そのものの伝播（1 / z の符号、z == 0）は正しい。落ちるのは符号の表示だけであり、既知 R6-N3（浮動小数の桁数）とは別表面（符号）のため新規に数える。P3。

### R15-N14（P2）：R の `df[["列"]]` が列ベクトルでなくデータフレームを返す

- 再現：`df <- data.frame(x = c(1, 2), y = c(3, 4))` の後 `print(df[["x"]])` → **"x: c(1, 2)"**（データフレーム表示）。`df[[1]]` も同じ。単一括弧 `df["x"]` と表示が完全に同一になる。
- 実 R：`df[["x"]]` は列そのもの（ベクトル）を取り出す。`df["x"]`（データフレームを返す）との使い分けが [[ の存在意義。
- 下流への伝播（同ラウンドで確認）：`mean(df[["x"]])` → 「エラー：invalid type of argument」（実 R は 1.5）。`df[["x"]] + 10` → **c(NaN)** の無言の誤値（実 R は c(11, 12)）。
- 根本原因：R エンジンの index 読み取りで、データフレーム分岐が `a.double`（[[ かどうか）を見ずに列選択のデータフレーム構築へ進む。ベクトルに対する [[ は正しく要素を返すため、壊れているのはデータフレーム分岐だけ。
- データフレーム操作は R 教材の中核であり、無言の型違い＋下流の誤値・虚偽エラーを生むため P2。

### R15-N15（P3）：R の関数名引数が実在の組み込み関数を「未定義の名前」と表示する

- 再現（同根の全表面を洗った）：
  - `sapply(c(1, 4, 9), sqrt)` → 「NameError：未定義の名前：sqrt」
  - `sapply(c("1", "2"), as.numeric)` → 「NameError：未定義の名前：as.numeric」（as.numeric 自体は対応関数）
  - `lapply(c(1, 2), as.character)` → 「NameError：未定義の名前：as.character」
  - `mapply(sum, c(1, 2), c(10, 20))` → 「NameError：未定義の名前：sum」
  - `tapply(c(10, 20, 30), c("a", "a", "b"), sum)` → 「NameError：未定義の名前：sum」
- apply 系自体が未対応であること自体は範囲外だが、原因表示は「その関数が存在しない」という虚偽になる。引数を値として先に評価し、関数名を変数として引く実装が原因。R14-N9（無名関数式が「) が必要です」）とは別の到達経路（名前つき関数参照）のため別表面として数える。P3。

### R15-N16（P3）：AutoHotkey の `.Length` が大小文字で挙動が割れる

- 再現：`a := [1, 2, 3]` の後 `MsgBox a.Length` → 「エラー：プロパティがありません：Length」。一方 `MsgBox a.length` → **3**（動作する）。文字列 `"hello".Length` も同じく停止する。
- 実 AutoHotkey v2：配列の Length プロパティは公式ドキュメントに明記された組み込みプロパティで、名前の大文字小文字は区別されない。文字列にも同名プロパティがある。
- 根本原因：共有実行器のメンバー読み取りが `length` の完全一致（小文字）でだけ配列長を返し、AHK 側のメンバー解決に大文字小文字の正規化が無い。公式ドキュメントの表記（Length）で書くと止まり、非公式な小文字だけが通る不整合のため P3。制御キーワードの大小区別（RG-32）とは別の機構（実行器のメンバー解決）のため別表面として数える。
