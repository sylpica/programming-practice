## 角度1：言語横断の算術セマンティクス（work/r6-arith.mjs）

実物照合：python3（床除算 -4／剰余 1・-1、`-2 ** 2` = -4、`2 ** 100` の正確値）、gcc（切り捨て -3／-1／1、INT_MAX+1 のラップ -2147483648、%f の 0.300000、'a'+1 = 98／'b'）、g++（cout の 0.3、"abc"+1 = "bc"）、node（剰余の符号、文字列強制変換、MAX_SAFE の精度落ち）はすべて予測どおりだった。

### 一致を確認したもの（抜粋）
- Python：`-7 // 2` = -4、`-7 % 2` = 1、`7 % -2` = -1、`0.1 + 0.2` の全桁表示と `== 0.3` の False、`-2 ** 2` = -4、`"a" + 1`／`"5" + 3` の TypeError（行・原因とも正しい）。
- JavaScript：剰余の符号、`"5" + 3` = "53"、`3 + "5"` = "35"、`"5" - 3` = 2、`"5" * "2"` = 10、`9007199254740991 + 1` と `+ 2` が同じ 9007199254740992 になる精度落ち、`1 == "1"` true／`===` false。
- C／C++：除算・剰余の切り捨て、C の %f（0.300000）、'a'+1。
- C#：`-7 / 2` = -3、`-7 % 2` = -1、`"5" + 3` = "53"、`3 + "5"` = "35"、int 溢れの -2147483648（unchecked 意味論どおり）、`0.1 + 0.2` の全桁表示（現行 .NET と一致）。
- R：`-7 %% 2` = 1、`-7 %/% 2` = -4（床方式）、`"a" + 1` の実物どおりのエラー文、剰余・除算。
- VBA：`-7 Mod 2` = -1、`7 Mod -2` = 1、`-7 \ 2` = -3、`5 / 2` = 2.5、`5 \ 2` = 2、Long 溢れの「オーバーフローしました」で停止。
- ImageJ：`-7 / 2` = -3.5、`-7 % 2` = -1、`"a" + 1` = "a1"。
- AHK：`"5" + 3` = 8。

### R6-N1（P2・新規）：VBA の数値文字列と数値の `+` が型エラーになる
再現：`Sub M()` 内で `Dim x`／`x = "5" + 3`／`MsgBox x` → 3行目「型が一致しません」で停止。実 VBA では `+` の片方が数値文字列なら数値に変換して加算し、結果は **8**（`&` との対比は VBA の基礎事項）。逆順 `5 + "3"` も同じく誤ってエラーになる。
切り分け確認済み：`"5" + "3"` → "53"（連結、正しい）、`"5" - 1` → 4、`"5" * 2` → 10（変換、正しい）、`"a" + 3` → 型が一致しません（実物もエラーで正しい）。つまり `+` の混合型だけが変換規則を欠いている。実在するコードが通らず、誤った原因で止まるため P2。

### R6-N3（P3・新規）：出力の浮動小数表示が実物の桁数と違う
`0.1 + 0.2` の出力が、C++ の cout で **0.30000000000000004**（実物は既定精度6桁で **0.3**、g++ 実測で確認）、VBA の MsgBox で **0.30000000000000004**（実 VBA の文字列変換は15桁で **0.3**）、R の print で **c(0.30000000000000004)**（実 R は既定7桁で **0.3**）になる。共有の数値整形が JS の Number→String をそのまま使うため。値自体は同一で表示だけの問題なので P3。なお JavaScript（全桁が正解）、C# の WriteLine（現行 .NET の最短往復表示と一致）、C の %f（0.300000 で一致）は欠陥でない。

### R6-N4（P3・新規）：C# の文字列連結の出力が "xtrue"
再現：`Console.WriteLine("x" + true);` → 出力 **"xtrue"**。実 C# では bool の文字列化は "True" で **"xTrue"**。R5-N7（trace・最終状態の小文字 true）と同根（c-family 共有の真偽値整形）だが、今回はプログラムの出力そのものという別表面のため新規として数える。P3。

### R6-N5（P3・新規）：VBA の文字列出力に引用符が付く
再現：`MsgBox "abc"` → 出力が **`"abc"`**（引用符つき）。`Debug.Print "abc"`、文字列変数の MsgBox でも同じ。実 VBA の MsgBox／Debug.Print は abc とそのまま表示する。AHK の MsgBox、ImageJ の print は引用符なしで実物どおり。VBA の出力整形だけが文字列を引用符で囲む。値の識別は可能なため P3。

### R6-N12（P3・新規）：Power Fx の `"5" + 3` が型エラーになる
再現：`Set(x, "5" + 3); Notify(Text(x))` → 「数値の型が一致しません」で停止。Power Fx の算術演算子は数値化できるテキストを暗黙に変換する仕様で、結果は **8** になるはず。実ランタイムでの裏取りができていない（VBA の同型 R6-N1 は実 VBA の古典的規則として確実）ため、確信度を明記して分けて記録する。明示エラーで捏造はないため P3。

### 観察（欠陥でない）
- Python の `2 ** 100` は「実行時に決まる：とても大きな整数・この説明では正確に計算しません」と表示され、値を捏造しない（アプリの契約どおりの正直な扱い）。
- C／C++ の符号付き int 溢れと `INT_MIN / -1` は「未定義動作」として明示停止する。実物 gcc はラップ／SIGFPE だが、モデルが UB を明示停止に倒すのは c-error テンプレートの建前どおりで正直な扱い。
- C の `%.17g` は「この printf 書式はモデルで扱えません」と明示停止（未対応の宣言）。
- AHK の整数除算 `//` と `Mod()` は「未対応」と明示停止する（掲載部分集合の宣言どおり）。AHK の `0.1 + 0.2` 表示は実物の書式仕様の確信が持てないため裁定しない。
- R の `2147483647L + 1L` は L 接尾辞リテラル自体が「未対応」と明示され、誤値の提示はない。
- PowerApps の `Mod()` は「説明に対応していません」と明示停止する。

## 角度2：行末・空白・文字コードの堅牢性（work/r6-ws.mjs）

### 正常を確認したもの
- **CRLF**：Python／JavaScript／C／C++／C#／R／VBA／AHK／ImageJ／PowerApps の基本コード＋エラー行つきコードで、LF 版と結果・エラー行が完全一致（貼り付け経路でもエンジン側で処理される）。
- **取り込み経路（decodeFile）**：UTF-8 BOM の除去、CRLF と CR のみの正規化、UTF-16LE BOM、Shift_JIS の復号、対象外拡張子の明示エラー、すべて正常。
- **Python**：タブのみのインデント（入れ子含む）、末尾空白、日本語識別子（`あ = 5` → 5、実 CPython でも合法）、コード先頭の BOM。全角スペース U+3000 と全角数字は実 CPython と同じく SyntaxError（文字を明示）で、エンジンの表示も正直。

### R6-N10（P3・新規）：CR のみの改行を貼ると行・原因が壊れる
CR（\r）のみのコードを simulate に直接渡す（貼り付け経路）と、複数エンジンで改行として扱われない：
- JavaScript：未定義名のエラー行が本来の3行目でなく **1行目** と表示される（エラー自体と原因は正しい）。
- R：全体が1行扱いになり「この構文は説明に対応していません：print」という誤った原因で止まる。
- VBA：全体が1行扱いになり「引数なしの単一 Sub のみ対応」という誤った原因で止まる。
実物の JS では \r も行終端子であり、行番号は LF 版と一致すべきもの。ファイル取り込みでは decodeFile が \r を \n に正規化するため発生せず、対象は貼り付け経路のみ。CR のみのソース自体が往年の形式であることも含め P3。

### R6-N11（P3・新規）：Python のタブと空白の混在インデントを無言で受理する
再現：`if True:` のブロックにタブインデント行と4空白インデント行を混在させると、エンジンは両方を実行する。実 Python3 では TabError／IndentationError（実測：IndentationError）で落ちる。エンジンが見た目の意図どおりに動かすため実害は小さいが、実物では動かないコードが無言で通るため P3。タブのみ・空白のみは正常。

## 角度3：構文エラーバッテリー第2弾（work/r6-errors.mjs、47ケース）

大半は行・原因とも正直だった（Python の括弧・コロン・文字列・関数外 return、JS の const 初期化・文字列・識別子、C 系の型不一致、R の演算子・括弧、PA の未知アクションと Loop の End 欠落、UI.Vision の未知コマンド、AHK の文字列と括弧、ImageJ の空代入と dangling else 等）。問題があったのは以下。

### R6-N2（P2・新規）：PowerApps の空引数が黙って実行される
再現1：`Set(x, ); Notify("a")` → エラーなく "a" が出て、trace は「x に null を設定し」と述べ、最終状態で x は Blank になる。実 Power Fx では構文エラー。
再現2：`Set(x, 1); Set(x, ); Notify(Text(x))` → 既存値 1 が **無言で Blank に消え**、出力は空になる。
再現3：`Notify()`（引数なし）→ エラーなく **"null"** を出力する。実 Power Fx では引数必須で構文エラー。
誤ったコードが、捏造した意味論（空引数＝Blank）で黙って通る。変数が無言で消える再現2を含め P2。

### R6-N7（P3・新規）：VBA のブロック終端欠落で「End Sub の位置が不正」と原因を取り違える
再現：`Sub M()`／`If True Then`／`MsgBox 1`／`End Sub`（End If 欠落）→ 最終行を指して「End Sub の位置が不正です」。Do〜Loop 欠落、For〜Next 欠落でも同文。End Sub を除いた同じコードでは正しく「End If が必要です」（If の行）になることを確認済みで、学習者が直すべき箇所（End If の追加）と異なる場所を責める表示になっている。P3。

### R6-N8（P3・新規）：VBA の `Dim x As` に無関係な原因を表示
再現：`Dim x As`（型名なし）→ 「この構文は説明に対応していません：As New / 固定長文字列」。コードには As New も固定長文字列もなく、実際の誤りは型名の欠落。パーサが別構文の未対応に誤分類している虚偽原因。P3。

### R6-N9（P3・新規）：JSON 構文エラーの原因表示が決め打ちで実態と違う
再現：末尾カンマの JSON（PA／UI.Vision）、途中で切れた JSON（CFN）→ いずれも「JSONのキーは文字列で指定してください」。実際の誤りは末尾カンマや切断であり、キーの書き方ではない。共有 JSON パーサの失敗が単一メッセージに潰れている。行は1行目で、構文エラーであること自体は伝わるため P3。

### 観察（欠陥でない）
- JS の未閉 `{`、R の未閉 `c(` はエラー行が最終行（EOF 位置）になるが、原因表示（} ／ ） が必要）は正しく、実物の「入力の終わり」系エラーと実質同じ。
- Python の `1 = x` は「この形の代入は解釈できません」という未対応形式の表示（行は正しい）。実物は SyntaxError だが、虚偽の原因ではない。
- R の `1 +* 2` は「* が未対応」という表示。問題トークンの指摘としては実質正しい。
- C# の `var = 3;` は var 自体の未対応として明示される（掲載範囲の宣言）。
- **CFN の検証範囲**：`Fn::If` の要素数不足（2要素）と未知の `Fn::Bogus` は、Transform のないパススルー経路では検証されず入力＝変換後としてそのまま出る。実 CloudFormation は検証で落ちるが、このアプリの CFN は変換シミュレーションでありテンプレート検証機能ではないため、欠陥とせず観察に留める。
- PA の不正 JSON も R6-N9 の同じメッセージ（共有パーサ）。

## 角度5：文字列のインデックス／スライス境界（work/r6-strings.mjs）

### 実物どおりを確認したもの
- Python：`s[-1]` = 'c'、`s[3]` の IndexError（行・原因とも丁寧）、`s[1:99]` = 'bc'、`s[-99:]` = 'abc'、空スライス、`s[::-1]` = 'cba'。
- JavaScript：`s[-1]`／`s[3]` がエラーでなく undefined（実物どおり）。
- C：`char s[] = "abc"` の `s[3]` が '\0'（数値 0）として合法に処理され、`s[10]`／`s[-1]`／配列の範囲外は「未定義動作」で明示停止、`s + 1` の %s が "bc"。
- C#：`s[3]` と `s[-1]` が IndexOutOfRangeException で停止。
- VBA：`Mid("abc", 4)` = ""、`Mid("abc", 2, 99)` = "bc"、`Mid("abc", 0)` と `Left("abc", -1)` が実物どおりエラー5の文面で停止。
- ImageJ：`substring("abc", 3)` = ""、`substring("abc", 1, 99)` と開始位置超過は明示エラー（Java の StringIndexOutOfBounds 意味論と整合）。

### R6-N6（P3・新規）：AHK の文形式で1文字の括弧文字列が解釈エラーになる
再現（いずれも文形式＝括弧なし呼び出し）：
- `MsgBox "["` → トップレベル「式を解釈できません：<eof>」で **パス0件**（全体が失敗）。
- `MsgBox "("`、`MsgBox "[" . "x"`、`MsgBox "(" . "x"`、`ToolTip "[" . "x"`、`SendText "[" . "x"` → 同様に失敗（連結形は「式を解釈できません：.concat」）。
- 一方で `MsgBox "[abc"`、`MsgBox "]" . "x"`、`MsgBox "{" . "x"`、関数形式 `MsgBox("[")`、代入 `x := "["` は正常。
つまり文形式の引数が "["／"(" という1文字文字列リテラル（連結の先頭の場合を含む）でのみ、文形式引数の字句処理が壊れる。R3-N1（文形式・単項符号引数）と同じ文形式引数まわりの弱さだが、対象が文字列リテラルという別表面のため新規として数える。あわせて、失敗時のメッセージに内部トークン（`<eof>`、`.concat`）がそのまま出る点（`x :=` の末尾代入でも「式を解釈できません：<eof>」）も同じ欠陥の表面として記録する。正当なコードが全体失敗し、原因表示も利用者には解読できないため P3。

### 観察（欠陥でない＝明示的な未対応）
- JavaScript の `slice`／`substring`／`charAt`（一部）／`at`、R の `substr`、C++ の `std::string` の `at`／`substr`、C# の `Substring`、Power Fx の `Mid`／`Left`、UI.Vision の `storeEval` は、いずれも「説明に対応していません」と明示停止する。掲載部分集合の宣言に沿った正直な扱いで、誤った値や無言の失敗はない。文字列境界の意味論そのものは、対応している範囲（Python／C／VBA／ImageJ／C# の添字）では実物と一致した。
- C++ の `std::string s[3]` は「無効または寿命の切れたポインタの参照」という UB 表示で止まる。実 C++ では s[3] は '\0' が定義済みだが、エンジンは std::string のメソッド自体を未対応としており、文字列モデルへの添字を C 式バッファとして扱った結果の表示。捏造値はないため観察に留める。
- C# の `s[^1]` は「式を解釈できません：^」と構文段階で明示停止する（未対応の宣言として正直）。
- C# の `s[3]` の例外文「配列範囲外です」は、文字列に対しては語が少しずれるが IndexOutOfRangeException という種別は正しい。
