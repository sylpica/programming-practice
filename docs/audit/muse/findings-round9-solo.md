## 角度1：合成プログラムの検証

各種類について4要素以上を組み合わせた新規プログラムを作成し、実行前に予測を記録してから照合した。実物のない種類は公式仕様で裁定した。

### 予測＝実物／仕様と一致した複合（12種類）
- **Python**：関数・ループ・三段分岐・リスト・辞書・split/join・f文字列の複合が実 CPython と完全一致（labels／counts／join の3出力とも一致）。
- **JavaScript**（添字ループ形式）：map 相当をループで書いた複合が予測どおり（"10-24-14-40-6"／"2件 合計64"／"大"）。
- **C**（中括弧形式）：自作の母音カウント（関数定義・strlen は宣言済み未対応のため main 内に展開）が実 gcc の出力と完全一致（"programming: vowels=3 len=11"／"多い"／"合計305"）。
- **C++**（中括弧形式・平行配列）：予測どおり（tea:3／coffee:6／juice:5／合計14／"短い"）。
- **C#**（連結形式）：予測どおり（"合計 215 平均 71"／"最高 Aya 85"／"合格ライン"）。
- **R**（paste／character／ifelse は掲載外で明示停止のため、ループ構築に置換）：予測どおり（valid／76.25／labels／labels[2]="高"／sum=2）。
- **ImageJ**：配列・ループ・分岐・endsWith の複合が予測どおり（合計=64／平均=12.8／最大=25／結果:大／tif=2）。
- **Power Apps**：ClearCollect・Sum・Filter・CountRows・If・連結の複合が予測どおり（"合計305 80以上2"／"優秀"／"2件"）。なお Max はリファレンス掲載外で明示停止（正直な範囲宣言）。
- **Power Automate**：For each 内に If を入れ子にした複合（Increase・%変数% 補間）が予測どおり（"合計 305 最高 90 優秀"）。
- **UI.Vision**：while＋executeScript_Sandbox＋if/else＋echo の複合が予測どおり（"大 100"）。
- **CloudFormation ハンドラ**：辞書操作・items ループ・setdefault・三項分岐の複合が予測どおり（Metadata={Stage:"test", Count:1}、Bucket.Properties.Stage="test"、status="success"）。
- **CloudFormation テンプレート**：Transform（全体、params 空→Stage="dev"）と Fn::Transform（兄弟断片、Stage="prod"）の複合が予測どおり。

### R9-N1（P2・新規）：AutoHotkey の配列が 0-based
再現：`a := [10, 20]` に対し `a[0]` → **10**、`a[1]` → **20**、`a[2]` → IndexError。実 AutoHotkey v2 の配列は 1-based で、`a[1]` が先頭（10）、`a[0]` はエラーになる。エンジンは添字を0始まりで解釈し、**誤った要素を無言で返す**。さらに A_Index は正しく 1-based（Loop 2 で 1、2）であるため、AHK の慣用形 `a[A_Index]` は先頭要素を飛ばし（20 のみ出力）、最終周で IndexError になる。エンジン内部でも規約が矛盾しており、配列を使う複合プログラムが系統的に壊れる。無言の誤値＋中核構文のため P2。

### R9-N2（P2・新規）：VBA の ":" / "," 1文字リテラル
再現（いずれも「式が必要です」で停止）：
- `Debug.Print "結果" & ":" & total`
- `Debug.Print s & ","`（変数＆1文字リテラル、2項でも発生）
- `Debug.Print ","`（引数全体が "," リテラルのみでも発生）
- `s = "a" & ":"`（代入でも発生）、`Debug.Print Len(":")`（関数引数でも発生）
一方、`Debug.Print "a,b"`（長いリテラル内包）、`s = "a" & ": "`（末尾スペース付き）、`s = ","`（代入の右辺全体）は正常。つまり**中身がちょうど ":" または "," の文字列リテラルを被演算子・引数として使うと停止**する（区切り文字とリテラルの混同が疑われる）。":" でラベルを組む・"," で CSV 状に連結するのは VBA の文字列処理の常套形であり、本監査の自然な複合プログラムが2箇所で直撃した。虚偽の原因表示（式は存在する）を伴うため P2。

### R9-N3（P3・新規）：C／C++ の中括弧なし if-else
再現：`if (1) x = 2; else x = 3;` → 「未対応：この構文は説明に対応していません：x」（本体の代入先変数を名指し）。`if (v >= 3) printf("多い\n"); else printf("少ない\n");` → 同様に「printf」を名指し。C++ の cout 版も同様。**if のみの単文（else なし）は C／C++ とも正常動作**し、while の単文本体も動作する。中括弧つき else は正常。else 節だけが中括弧を要求し、原因表示が本体先頭トークンを未対応構文と誤認させる。P3。

### R9-N4（P3・新規）：C／C++ のユーザー関数定義への虚偽の原因表示
再現：`int dbl(int x) { return x * 2; }`（C／C++ とも）→ 「未対応：この構文は説明に対応していません：キャストのこの形式は未対応です（ポインタ・参照・修飾型等）」。コード内にキャストは存在しない。関数定義が未対応であること自体はサポート文に宣言があるが、停止理由が無関係な「キャスト形式」を指すため、学習者は修正方針を誤る。なお `void greet()` の場合は関数名を名指しする表示（「未対応：…：greet」）になり、表示が一貫しないことも確認した。P3。

### R9-N5（P3・新規）：JavaScript のコールバックへの虚偽の原因表示
再現：`a.map(n => n * 2)`、`a.map(function(n) { return n * 2; })`、`a.filter(n => n >= 2)` のいずれも「エラー：) が必要です」で停止。コールバックが未対応であること自体はサポート文に宣言があるが、エラーは構文エラー（括弧不足）を装っており、原因が虚偽。行番号は正しい。P3。

### R9-N6（P3・新規）：C++ の cout チェーン内の三項演算子
再現：`std::cout << (total >= 15 ? "長い" : "短い") << std::endl;` → 「エラー：) が必要です」。R7-N3（関数引数位置の三項演算子の虚偽原因）と同根だが、被演算子位置（<< チェーン）は別表面のため新規として数える。なお C# の `Console.WriteLine(cond ? a : b)` は R7-N3 そのもの（関数引数位置）であり再報告しない。P3。

### R9-N7（P3・新規）：AutoHotkey の for ループへの虚偽の原因表示
再現：`for idx, v in scores { total += v }` → 「エラー：( が必要です」。for は AHK v2 の基本ループ構文だが、エンジンは未対応を括弧不足と誤認させる表示で停止する（サポート文の対応一覧に for はなく、未対応自体は範囲外として理解できるが原因表示が虚偽）。P3。

### R9-N8（P3・新規）：AutoHotkey の `.=` 連結代入
再現：`s .= "x"` → 「エラー：式を解釈できません：=」。`.` 連結（`s := s . "x"` 形式）も `+=` も動作するが、AHK v2 の標準的な連結代入 `.=` だけが解釈不能として停止し、トークン「=」を指す原因表示も実態（演算子未対応）とずれる。P3。

### 角度1の観察（欠陥としない）
- AHK の `.Length` は「プロパティがありません：Length」と明示停止する。実 AHK の Array には Length があるが、配列プロパティはサポート宣言の範囲外であり、無言の誤値ではないため観察に留める。
- AHK の StrSplit／SubStr／StrLen、R の paste／character／ifelse、Power Fx の Max、C の strlen、C++ の size() は、いずれもリファレンス掲載外または宣言済み制限として明示停止した（正直な範囲宣言）。
- C# の文字列補間 `$"..."` は掲載外で、「式を解釈できません：$」と問題箇所を名指しして停止した（原因として実態を指しているため欠陥としない）。

## 角度2：字句レベルの境界バッテリー

約60件（未終了文字列／未終了ブロックコメント／空プログラム／空白のみ／5000文字の長い行／3000文字のコメント行／日本語識別子／式中のコメント／絵文字・NUL バイト・単独 `@`／文字化け文字 U+FFFD の文字列内包）を13種類に投げた。

### 健全だったもの
- **未終了文字列**：全種類で正確な原因と正しい行で停止（Python「文字列が閉じられていません（引用符 " が不足）」、共有スクリプト系「文字列の途中で改行されています」、R「文字列が閉じられていません」、ImageJ「1行目の文字列が閉じていません」等）。捏造出力なし。
- **未終了ブロックコメント**：JS／C／C#／ImageJ で「コメントが閉じられていません」「1行目の /* が閉じていません」と正確に停止。
- **空／空白のみ／コメントのみ**：全種類で静かに処理され、UI では「説明する処理がありません。コードまたはフローを入力してください。」と正直に案内（角度3で実地確認）。
- **長い行**：5000文字のリテラル（Python／JS／VBA）と3000文字のコメント行（JS）は正常処理。
- **日本語識別子**：Python／JS／C／C++／C#／R／VBA／AHK で正常動作。C は実 gcc でも受理（出力 1）され、エンジンと一致。ImageJ は「解釈できない文字「名」があります」と停止したが、ImageJ マクロの変数名は英字始まりの ASCII が仕様であり、エンジンの停止は正確（欠陥でない）。
- **式中のコメント**：Python（括弧内 # コメント→3、実 CPython と一致）、JS／C／C#／ImageJ／AHK（/* */ → 3）は正常。
- **U+FFFD を含む文字列**：Python で正常に出力。クラッシュ（threw）は全件ゼロ。

### R9-N9（P3・新規）：R の行末演算子による式継続
再現：`x <- 1 +\n  2`（コメントなし）および `x <- 1 + # コメント\n  2` の双方が「エラー：式を解釈できません：」＋改行文字（対象トークンが空）で停止。実 R では、式が文法的に未完な行末では次行へ継続して読み、どちらも x = 3 になる有効なコードである。括弧内の継続（`sum(c(1,\n 2))`）はエンジンでも動作するため、行末演算子の継続だけが欠落し、原因表示も空トークンで壊れている。P3。

### 角度2の観察（欠陥としない）
- Python で絵文字をコード位置に置くと「解釈できない文字「�」があります」と、対象文字自体が置換文字で表示される。NUL バイトでは対象文字が改行のように表示される。行と原因の実質は正しいため、文字同定の表示上の不正確さとして観察に留める（JS の絵文字も同様に � 表示）。
- Python の単独 `@` は「式の読み取りに失敗しました（「END」のあたり）」と曖昧だが、特定の虚偽原因を断定していないため観察に留める。
- JS のテンプレートリテラル（バッククォート）は未対応カテゴリで問題箇所を名指しして停止（正直な範囲宣言）。

## 角度3：トレースのステップ実行の整合性（Playwright 実地）

本アプリのステップ操作に相当するパス遷移（|◀ ◀ ▶ ▶| ボタン、番号入力＋移動、並び順変更）とトレース項目クリックを、Python（input 分岐・2パス）と VBA（InputBox＋Select Case・3パス）で実地操作し、エンジンのパスデータ（トレース文・出力・最終状態）と DOM 表示を全件照合した（work/r9-angle3.mjs、19項目中18項目 PASS）。

- 初期表示・next／prev／last／first の遷移先とカウンタ（1 / 2 等）は全件一致。端では first／prev・next／last が正しく無効化される。
- prev で戻るとトレース・出力・最終状態が**完全一致**で復元される。
- 番号ジャンプ：2 は正確に移動。範囲外の 99 は最終パスへクランプされ番号欄も 2 に書き戻される。0 は先頭へクランプ。いずれも破綻なし。
- 並び順（処理が短い順／コードが長い順）へ変更しても**表示中のパス自体は不変**で、カウンタ位置だけが正しく追従する（sortPaths が現在のパス id を保持する設計どおり）。
- トレース項目（L3）をクリックすると、エディタの3行目 `    print("開始")` が正確に選択される。
- 空コード実行時は「説明する処理がありません」と案内される。pageerror は全操作を通じてゼロ。

### R9-N10（P3・新規）：VBA エラーの行番号二重表示
角度2の VBA 未終了文字列を UI で実行すると、ステータス欄が **「3行：3行：文字列が閉じられていません」** と表示される。js/engine.js の字句解析（VBA エンジンが使用）が `fail(\`${start}行：文字列が閉じられていません\`)` とメッセージ内に行番号を含み、app.js がさらに `${line}行：` を前置するために二重化する。共有側 js/core/script.js の同種エラーは行番号を含まないため他種類では発生しない。意味は通じるが表示の欠陥として P3。
