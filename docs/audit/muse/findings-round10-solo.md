### R10-N1（P2）：R のコロン演算子 `:` の優先順位が逆転している

公式マニュアル『An Introduction to R』§2.3 は、`:` が `*` や `-` より強く結合することの比較例として `2*1:15`（＝c(2,4,…,30)）、`1:n-1`（＝(1:n)-1＝0..9）、`1:n+1`（＝(1:n)+1＝2..11）を挙げている。エンジンの結果は3件とも無言で誤値：

- `2*1:15` → `c(2, 3, 4, …, 15)`（エンジンは (2*1):15 と解釈）
- `n <- 10; a <- 1:n-1` → `c(1, …, 9)`（エンジンは 1:(n-1) と解釈。正しくは 0..9）
- `n <- 10; a <- 1:n+1` → `c(1, …, 11)`（エンジンは 1:(n+1) と解釈。正しくは 2..11）

つまりエンジンでは `:` が周囲の算術式全体を取り込む最も弱い結合になっており、実 R と正反対。`n:1`（降順）や単独の `1:n` は正しいため、算術式が隣接したときにだけ壊れる。R のサポート宣言（因子・S3/S4 等の未対応列挙）にコロン優先順位の除外はなく、基本演算の範囲内。公式マニュアル自身の比較例がそのまま誤値になるため P2。なお R の `v <- 2*x + y + 1` の小数表示が全桁になる点は R6 で既知の print 桁数と同根のため新規にしない。右代入 `->` は「未対応：…：->」と正直に停止（欠陥にしない）。

### R10-N2（P2）：AutoHotkey の暗黙の連結で第2オペランド以降が無言で欠落する

AHK v2 では空白区切りの暗黙の連結が文字列構築の典例で、公式 Beginner Tutorial §5a／§6 は `MsgBox "MyVar equals " MyVar "!!"` の形をコードブロック例として掲げている。エンジン（平文スクリプト実行のため従来どおり `model.event = null` の条件）の結果：

- `y := "world"` のあと `x := "hello " y` → x は `"hello "`（y の値が無言で欠落。実 AHK は "hello world"）
- `x := "a" "b"` → x は `"a"`（第2リテラルが無言で欠落）
- `x := "n=" 5` → x は `"n="`（数値が無言で欠落）
- 文の引数位置 `MsgBox "MyVar equals " MyVar "!!"` → 「未対応：この構文は説明に対応していません：MyVar」と、連結対象の変数名を名指して停止（同根の別表面）

明示的な `.` 連結演算子は正常に動くが、代入文での無言の値欠落は学習者が気づけない誤値であり、AHK のサポート宣言は「代入」自体を対応範囲に含むため P2。なお §5 の SubStr 例は「このAutoHotkey関数は未対応です：SubStr」と明示停止（第9ラウンドで確認済みの正直な範囲宣言、新規にしない）、§6b の例の `.=` 停止は R9-N8 と同根のため新規にしない。

### R10-N3（P2）：UI.Vision でテキスト由来の変数がスクリプト評価で文字列化する

UI.Vision 公式ドキュメントの while ページは、while/end で FOR/NEXT を再現するパターンを記載し、条件・式の評価に executeScript_Sandbox を使う旨を明記している。実製品では `${count}` は変数値のテキスト置換で JS に渡るため、`store` で入れた "0" でも `return ${count} + 1;` は数値加算になる。エンジンで公式パターン構成を実行すると：

- `store "0"` のあと executeScript_Sandbox `return ${count} + 1;` → **"01"**（文字列連結）。次周は "011" になり、while 条件 `"011" < 3` が数値11として偽になり **echo は 0, 01 の2回だけ**で早期終了（本来は 0, 1, 2 の3回）
- `times`（固定3回）でも最終値が "0111" になる
- 切り分け：executeScript で `return 0` を返して数値として保存した変数では +1 も while ループ（0,1,2 の echo、count=3）も完全に正しく動く

根本は、テキストとして保存された変数（store／storeText／storeValue 由来）が executeScript／while の式評価で文字列型のまま渡る点にある。製品の典例ループが無言で誤った値・回数になるため P2。

### R10-N4（P3）：C# の中括弧なし if-else が虚偽の原因表示で停止する

Microsoft Learn「Branches and loops」の逐語例（`int b = 3;` に対する中括弧なし if-else）は、エンジンではパスエラー「NameError：未定義の名前：else」で停止する（else は未定義の名前ではない）。1行形 `if (a > 10) Console.WriteLine("big"); else Console.WriteLine("small");` では「未対応：この構文は説明に対応していません：Console」と、対応しているはずの Console を名指す。C# の中括弧なし if 単独（else なし）は正常に動くため、壊れているのは else 側だけ。R9-N3（C／C++ の中括弧なし else）と同族だが、C# は種類が別で原因表示も異なる（より虚偽性が高い）ため、取り決めどおり別表面として新規 P3 に数える。

### R10-N5（P3）：JavaScript の do-while が本体トークンを名指す原因表示で停止する

MDN「Loops and iteration」の do-while 逐語例（結果は 1,2,3,4,5）は、エンジンでは「未対応：この構文は説明に対応していません：{」で停止する（中括弧なし形では「：i」）。JavaScript のサポート宣言は「If / For / While」対応を掲げ do-while を含まないため範囲外自体は宣言済みだが、名指されるのは未対応構文そのもの（do）ではなく本体の先頭トークンであり、学習者には「{ が使えない」という誤った原因に見える。R9-N3／N5／N7 と同じ型の虚偽原因のため P3。

### 観察（欠陥に数えないもの）
- **C（K&R 華氏・摂氏表）**：逐語例は `int fahr, celsius;` のカンマ宣言で「式を解釈できません：,」と停止する。ただし C 系共通のサポート宣言は「多重宣言」を未対応として明示しており、停止箇所の名指しも正確。宣言を分ければ表は gcc の真値と完全一致して完走する（0/-17, 20/-6, 40/4, 60/15 を上限60で確認、本体は16行版でも同一コードパス）。宣言済み範囲外の正直な停止として欠陥にしない。
- **C／C++ の前置 `++i`**：for ヘッダ・単独文のいずれでも「式を解釈できません：++」で停止し、cppreference 例1はこの1トークンで止まる。後置 `i++` は正常。名指されるトークンは正確で捏造はないため、本ラウンドでは観察に留める（基本演算子の形としては目立つ制限なので記録する）。
- **CloudFormation（AWS 公式 Conditions 例）**：既定モデルでも `templateParameterValues` に EnvType="prod" を与えても、最終状態の「変換後」テンプレートは入力と同一で、Conditions／Ref／Fn::Equals／Fn::GetAtt は解決されず、トレースも空。ただしこの種類の宣言範囲はマクロ（Transform／ハンドラ）中心で、リファレンス49件に Conditions 系は無く、「未変換のまま通す」テンプレート（cfn-pass）が型のモデルとして存在する。誤った解決値を捏造しているわけではないため、平文テンプレートの組み込み関数評価は宣言範囲外として観察に留める。
- **Power Apps の StartsWith**：Filter＋StartsWith の公式例は「このPower Fx関数は説明に対応していません：StartsWith」と明示停止。リファレンス未掲載の正直な範囲宣言（欠陥にしない）。
- **Power Automate の Set variable への式文字列**：値に `"%Total% + %Item%"` を渡す形は「式を解釈できません：%」で停止するが、正規の Increase variable による典例が正しく動いており、停止も正直なため観察。
- **C# の補間文字列 `$"..."`**：総和チャレンジ例は `$` を名指して正直に停止（第9ラウンドの観察と同じ扱い）。
- **AutoHotkey のモデル event 要件**：既定モデルは `event: "^!n"` を持ち、対応するホットキーのない平文スクリプトは「モデルのeventに対応するホットキー／ホットストリングがありません」と原因を正確に名指して停止する（従来ラウンドからの踏襲どおり観察）。

## 角度2：実行の独立性と再実行の状態漏れ（新規欠陥ゼロ）

- **A→B 状態漏れ（全13種類）**：プログラムAで変数を定義し、別プログラムB（新規実行）でその名前を参照するテストで、全種類とも漏れなし。大半はBが未定義エラーで正直に停止。VBA のBは `Empty` を表示したが、Option Explicit なしの実 VBA の意味論と一致するため正常。CloudFormation のA側はハンドラ戻り形式の都合で requestId 不一致エラーになったが（テスト設計側の事情）、Bは NameError で正直に停止したため漏れなしと判定。
- **決定性（全13種類）**：同一プログラムの繰り返し実行で、表示内容（パス・トレース・出力・最終状態・エラー）を深い diff で比較し、差分は `elapsed`（実行時間ミリ秒）のみ。
- **共有モデルオブジェクトの非破壊性（全13種類）**：`simulate` は渡されたモデルオブジェクトを変更せず、同一オブジェクトでの2回目も内容同一（elapsed 除く）。
- **パス間汚染**：Python（if 側で `secret=42`、else 側で読む）は else パスが NameError で正直に停止。VBA（Case で設定、Case Else で読む）は Case Else パスが `Empty` を表示し、42 は漏れなかった。
- **UI 水準（代表3種類：VBA／Python／UI.Vision）**：実ブラウザで「実行」ボタンを3回押しても結果表示（ステータス・トレース・出力・最終状態）が完全一致。エラーを入れて実行→元に戻して再実行すると初回と完全一致し、エラー状態の残留もなし。

## 角度3：複数エラーと後方パスのエラーの正直さ（新規欠陥ゼロ）

- **64パス級（Python、独立した input 分岐6つ）**：全組み合わせ中「全部 y」の1パスだけが最終行 L20 で NameError（`boom`）となり、他の63パスは正しい出力で完走。全体エラー（topErr）なし、打ち切りなし。
- **独立2エラー**：別々のパスに L4 の NameError と L6 の ZeroDivisionError がそれぞれ正しく帰属し、安全なパスは完走。
- **同一パスの2エラー**：先に発生する L2 のゼロ除算が報告される（正直）。
- **ループ後半のエラー**：40要素リストへの50回アクセスで、40件の出力を保持したまま L3 で正確な IndexError（番号40の要素はない旨）。
- **VBA の後方パス**：3パスのうち Case Else パスだけが L10「0 で除算しました」で停止し、他2パスは正常。
- **C# の不明入力分岐**：else パスだけが L5 で `missing` の未定義エラー、Y パスは正常。
- **構文＋実行時の併存**：全体が L2 の SyntaxError で停止（正直）。**中間パスのエラー**：合流後の2パスで、エラーパスは L5 の NameError、安全パスは完走。

## 角度4：全13種類の下書き・テンプレート切替マトリクス（新規欠陥ゼロ）

全13種類で実ブラウザ操作「テンプレートA読込→（コード末尾に空行追加で）編集→モデル編集（JSON 種類はテキスト先頭への空白挿入、VBA はセル C5 へ "777"）→テンプレートBへ切替→『なし』へ戻る→テンプレートA再選択」を実施し、全種類で以下が一貫していた（各種類9点、全117点＋一周・再読込の確認）。

- テンプレートAの読込コードは定義データと完全一致し、編集するとテンプレート選択が即座に「なし」へ戻る。
- テンプレートBは pristine なコードに切り替わり、「なし」へ戻すと編集済みコード（freeDraft）がバイト単位で復元され、モデル編集（JSON テキスト／シートセル）も同時に復元される。
- テンプレートAを再選択すると編集は戻らず pristine になる。
- 13種類を一周して戻っても各種類の freeDraft は保持され、再読込後も代表3種類（VBA／Python／CloudFormation）で復元を確認。pageerror は全行程ゼロ。

INT-01 で確認された挙動が、モデル次元（シートセル／JSON テキスト）を含めて全種類に一般化していることを確認した。
