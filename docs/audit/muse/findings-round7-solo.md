### R7-N3（P3・新規）：三項演算子の虚偽の原因表示
再現（JS）：`console.log(1 < 2 ? "y" : "n");` → 「) が必要です」で停止。C／C++／C# でも関数引数位置の `?:` は同じく「) が必要です」になる。括弧は正しく対応しており、真の原因は三項演算子が未対応であること。代入位置では「式を解釈できません：?」と比較的正直な表示になるため、虚偽性は引数位置に限る。いずれの言語でもテンプレート・リファレンスは三項演算子を扱っておらず、明示停止自体は範囲内だが、原因表示が実態と違う（R4-N2 と同じ類型の別表面）。P3。

### R7-N6（P3・新規）：long long の誤読と幻の変数
再現（C）：`long long x = 5; printf("%lld\n", x);` → 最終状態に名前が **"long"** という未初期化変数が生まれ、「変数が宣言されていません：x」で停止する。宣言パーサが2つ目の `long` を変数名として取り込むため。C++ でも同一。`printf("%lld", 9223372036854775807LL)` は「) が必要です」で停止（LL 接尾辞の解釈失敗が真因）。なお `long x` の宣言自体は機能するが printf の %ld／%lld 書式は「未対応」と明示される（その部分は正直な宣言）。実 C／C++ では long long は基本型であり、学習者が最終状態で幻の変数を目にする点と原因の取り違えを欠陥とする。P3。

## 角度2：実物のない言語の演算子・型変換テーブル総点検

VBA／AutoHotkey／R／C#／Power Automate／Power Apps／UI.Vision／CloudFormation／ImageJ について、型ペア×演算子のセルを約80件設計し（暗黙変換、空値・未設定値の演算、型混在比較を重点）、公式仕様の知識と突き合わせた。CloudFormation はマクロのハンドラ（Python）経由の算術が Python エンジンの管轄で角度1の範囲と重なるため、本角度では変換セルの対象外とし、UI.Vision は変数が文字列で式評価は executeScript_Sandbox（実質 JS）に委ねられる構造のため、AHK／PA の式セルで代表させた。

### R7-N1（P2・新規）：R の NULL が 0 のように扱われ誤値を捏造する
実測（エンジン）：`NULL + 1` → `c(1)`／`NULL * 5` → `c(0)`／`length(NULL + 1)` → `1`／`x <- NULL; x + 10` → `c(10)`／`NULL == NULL` → `c(TRUE)`。
実 R：NULL は長さ0のオブジェクトで、`NULL + 1` は `numeric(0)`、`length(NULL + 1)` は 0、`NULL == NULL` は `logical(0)`。エンジンは NULL をスカラーの 0 として算術・比較し、無言・無警告で誤った値を提示する。NULL は R の基本概念であり、値の捏造にあたるため P2。
なお `c(1, NULL)` → `c(1)`、`length(NULL)` → 0、NA の伝播（NA + 1 → NA、NA == NA → NA）、ベクトルのリサイクル（c(1,2,3) + c(1,2) → c(2,4,4)）、%%／%/% の符号、if(NA) の実物どおりのエラーメッセージは正しいことを確認した。

### R7-N2（P2・新規）：C# の char 算術
実測：`'a' + 1` → **"a1"**（文字列連結扱い）／`'a' + 'b'` → **"ab"**／`'a' - 'A'` → 型エラーで停止／`'a' * 2` → 型エラー／`char c = 'a'; int n = c + 1;` → 「数値型が一致しません」で停止。
実 C#：char は数値型として昇格し、'a' + 1 = 98、'a' + 'b' = 195、'a' - 'A' = 32、'a' * 2 = 194、c + 1 = 98。エンジンは char を文字列のように扱い（+ では連結）、それ以外は拒否する。C／C++ のエンジンは正しく 98／195 を出すため C# 側だけの欠陥。誤値の提示を含むため P2。`'a' + ""` → "a"（連結が正しい文脈）は正常だった。

### R7-N4（P3・新規）：C# の 1 == "1" が黙って True になる
`Console.WriteLine(1 == "1");` → "True"（逆向き `"1" == 1` も True）。実 C# では int と string に対する == は適用できずコンパイルエラーになる。コンパイル不能なコードを黙って受理し、型変換されるかのような結果を示す（R6-N11 の無言受理と同じ類型の別表面）。数値同士の昇格比較（1 == 1.0 → True、0.1f == 0.1 → False）は正しい。P3。

### R7-N5（P3・新規）：C# の null 文字列との連結が型エラーになる
`string s = null; Console.WriteLine(s + 1);` → 「演算する型が一致しません」で停止。`1 + s`、`s + true` も同様。実 C# では文字列との + は連結となり、結果は "1"／"1"／"True"（null 文字列は空として扱われる）。非 null 文字列との連結（"a" + 1 → "a1"）は正常なため、null の場合だけの欠落。虚偽の停止として P3。

### R7-N8（P3・新規、留保つき）：Power Fx の = の変換規則
実測：`"abc" = "ABC"` → false／`5 = "5"` → false／`"5" = 5` → false／`5 = "5.0"` → false。
Power Fx の = はテキスト比較で大文字小文字を区別せず（in 演算子の非依存性は公式ドキュメントで確認）、数値文字列とは暗黙変換して比較するのが仕様の理解であり、その場合いずれも true になるはず。ただし Power Fx の実ランタイムがこの環境に無く、= そのものの変換規則を一次資料の文面で完全には確定できなかったため、R6-N12 と同じ留保（実ランタイム未確認）を明記して P3 として記録する。
なお Blank() + 1 → 1（Blank の 0 扱い）、"5" & 3 → "53"、true + 1 の型エラー、"10" > "9" → false は仕様どおりと判定した。Blank() = 0 の真偽は仕様の確定ができず**未確認**（欠陥として数えない）。Mod／Date は説明対応外として明示停止（観察）。

### R7-N9（P3・新規）：Power Fx のゼロ除算と表面の矛盾
`Set(x, 1 / 0); Notify(Text(x))` → Notify には **"Infinity"** と表示される一方、最終状態の x は **null（Blank）** で、表面同士が矛盾する。`Notify(Text(1 / 0))` 単独でも "Infinity"。Power Fx ではゼロ除算はエラー値になるのが仕様で、Infinity が表示されることはない。明示エラーにもならず、表示と状態が食い違うため P3。

### 正常を確認したもの（抜粋）
- **VBA**：True + 1 = 0（True = −1 の古典的規則）、1 = True → False／−1 = True → True、"5" * 2 = 10、"5" − 1 = 4、Empty + 1 = 1／Empty = 0 → True、Null の伝播（Null + 1 → Null、Null = Null → Null）、Mod の符号（−7 Mod 3 = −1）、\ 演算子、1 / 0 のエラー、"abc" = "ABC" → False（二進比較）。いずれも実 VBA どおり。
- **VBA の観察（欠陥でない）**：`10 > "9"` のような数値と文字列の直接比較は「String型と数値型の直接比較（明示的な型変換を使用してください）」と明示して停止する（実 VBA は変換して True を返すが、制限の宣言が正直なため観察に留める）。日付リテラル #…#、&H16進リテラル、IIf は説明対応外として明示停止（観察）。
- **AutoHotkey**（event: null モデルで測定）： "10" > "9" → true（数値文字列の数値比較）、"5" + 3 = 8、1 = "1"／1 == "1" → true、"abc" = "ABC" → true（= の大文字小文字非依存）、"abc" == "ABC" → false（== の区別）、"abc" . 1 → "abc1"、非数値文字列の算術はエラー。いずれも AHK v2 の仕様どおり。整数除算 // と三項 ?: は「未対応」と明示宣言（観察）。"" + 1 はエンジンがエラーで止めるが、実 AHK v2 での空文字列の数値扱いの確定ができず**未確認**（欠陥として数えない）。
- **Power Automate**（JSON フローの %式% で測定）：5 / 2 = 2.5、5 % 2 = 1（% が剰余）、'5' + 3 → "53"（テキストとの + は連結）、10 > '9' → true。全て PAD（Robin）の仕様の理解と一致。
- **ImageJ**："5" + 3 → "53"、5 + "3" → "53"（どちらか文字列なら連結）、7 / 2 = 3.5（整数除算なし）、7 % 2 = 1、1 == "1" → 1、1 / 0 → Infinity、0 / 0 → NaN、true + 1 = 2。全て実物どおり。
- **ImageJ 文字列比較の裁定（欠陥候補の取り消し）**：`"ABC" == "abc"` → 1、`"abc" != "ABC"` → 0、`"B" > "a"` → 1 というエンジンの挙動は、一見 Java の equals の連想から誤りに見えるが、ImageJ Macro Reference Guide §9.2 が「Use the "==", "!=", ">" and "<" operators to compare strings. **Comparisons are case-insensitive.**」と明記しており、**エンジンが正しい**。indexOf／startsWith が区別する（"ABC" の中の "b" は −1）ことも実物どおり。欠陥として数えない。

## 角度3：数値・値の表示形式の体系照合

### R7-N7（P3・新規）：R の Inf が "Infinity" と表示される
`print(Inf)` → "Infinity"、`print(-Inf)` → "c(-Infinity)"、`print(1 / 0)` → "c(Infinity)"。実 R の表示は "Inf"／"-Inf"。値の意味は正しいが表記が JS 式で、R の出力として誤り。R5-N6（NULL の "null" 表示）と同類型の別トークン。P3。なお NA／NaN の表記、通常の数値の c(...) 形式は従来どおり（桁数の問題は既知 R6-N3 の範囲）。

### R7-N10（P3・新規）：C# の double 出力書式
`Console.WriteLine(1e20)` → "100000000000000000000"（実 .NET は "1E+20"）、`Console.WriteLine(100.0 / 7)` → "14.285714285714286"（実 .NET の G15 は "14.2857142857143"）。R6-N3（浮動小数の JS 式全桁表示）と同根だが、C++／VBA／R が対象だった R6-N3 に対し C# は未指摘の別表面のため新規として数える。2.0 → "2" は実物どおり。P3。

### R7-N11（P3・新規）：C# の配列の表示
`int[] a = {1, 2, 3}; Console.WriteLine(a);` → 中身（[1, 2, 3] の整形表示）が出る。実 C# の Console.WriteLine(配列) は Object.ToString() で **"System.Int32[]"** と表示される。学習者が実 C# の出力と異なる表示を目にするため P3（JS の配列表示はブラウザ／Node で正規のテキスト表現が定まらないため観察に留めたのと対照的に、C# は実物の表示が一意に定まる）。

### 正常・観察（抜粋）
- **Python の表示は全面的に正確**：print(1e16) → "1e+16"、print(1e15) → "1000000000000000.0"、print(123456789.123456789) → "123456789.12345679"（repr の最短表現）、混在リスト `[1, 'a', True, None, 2.5]`、辞書の挿入順表示、print(2.0) → "2.0"、print(100 / 7) → "14.285714285714286"。全て実 CPython と一致。
- **JavaScript**：1e20 → "100000000000000000000"（JS の指数切替は 1e21 から）は実物どおり。配列・オブジェクトの console.log は JSON 整形表示（[\n 1,\n 2…]）で、実物の正規テキストが環境依存（ブラウザと Node で異なる）ため観察に留める。undefined 変数の表示も正常。
- **C**：printf("%f", 1e20) → "100000000000000000000.000000" は実物どおり。%g／%e は明示的未対応（角度1）。
- **R の通常数値**（1e16 の全桁表示、100 / 7 の全桁）は既知 R6-N3 の範囲として再報告しない。

## 角度4：テンプレート導入文とコードの対応ずれ総点検
