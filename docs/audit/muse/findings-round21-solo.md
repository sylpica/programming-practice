## 3. 新規欠陥 18件（統合裁定済み）

### 既存 RG の別表面（9件）

**R21-N1（P2／RG-21 の別表面）R `1:3 * 2` が c(1,2,3,4,5,6) になる**（A群 A21-A-02）
- `print(1:3 * 2)` → 実際 c(1,2,3,4,5,6)（1:(3*2) と解釈）。実 R は c(2,4,6)（`:` は `*` より高優先、R 公式「Operator Precedence」）。
- RG-21 の既登録表面はマニュアル例の `2*1:15` 型（コロンの左側に演算子）であり、本件はコロンの右側に乗算がある形という別表面。根は同一（R のコロン優先順位逆転）。

**R21-N2（P2／RG-40 の別表面）C++ std::string と char の演算が全て「型が一致しません」**（A群 A21-A-06）
- `s + 'c'`、`'c' + s`、`s += 'c'` の3表面とも CompileError（実 C++ は abc／cab／abc、cppreference）。string+文字列リテラル、string+string は正常、string+int は実物どおりエラー。
- 根：std::string モデルの二項演算表に char 被演算子がない。

**R21-N3（P3／RG-06 の別表面）C／C++／C# の自己初期化が「未定義の名前：x」の虚偽原因になる**（A群 A21-A-10）
- `int x = x + 1;` が3言語とも NameError「未定義の名前：x」。実 C/C++ では x は初期化子内でスコープ内（未初期化値の使用＝未定義動作）、C# では CS0165 であり、「名前が未定義」ではない。
- 根：宣言の登録前に初期化子を評価し、名前未登録を未定義名に誤分類する。

**R21-N5（P3／RG-04 の別表面）JavaScript の -0 が "0" と表示される**（A群 A21-A-15）
- `console.log(-0);` → 実際 "0"。Node の console.log は "-0" と表示する（実測）。差分ファズ 650件中の2件から検出。
- 根：値表示が String(-0)==="0" の変換に寄り、console 表示の -0 を保持しない。

**R21-N6（P3／RG-04 の別表面）C の printf %f と C++ の cout で Inf が "Infinity" になる**（A群 A21-A-17）
- C `printf("%f", 1.0/0.0)` → 実際 "Infinity"（glibc は "inf"）。C++ cout も同様（実物 "inf"）。RG-04 の既登録の Inf 表面は R（R7-N7）のみで、C 系は別表面。

**R21-N7（P3／RG-04 の別表面）JavaScript の配列内 undefined が文字列 "未設定" として引用符付きで表示される**（A群 A21-A-20）
- `console.log([undefined]);` → 実際 `[ "未設定"]`（文字列リテラルに見える）。スカラーの `console.log(u)` は "undefined" と正しく表示され、同一言語内で表記が割れている。実 Node は要素も undefined と表示。
- 根：コレクション表示の formatValue が undefined を和訳ラベルに置換し、文字列としてクォートまで付ける。

**R21-N10（P2／RG-07 の別表面）式の改行継続の拒否：C系と、行コメントを挟む形**（B群 B21-B02-N1 の裁定後の残存分）
- C `int x = 1 +\n 2;` が不可視の改行を原因として拒否される（c-family パーサの表面。第14bラウンドは「C系は影響を受けない」と対照確認していたが、それは文間の改行であり、式途中の改行継続は未照合だった）。
- 行コメントを挟んだ継続 `let x = 1 + // c\n 2;`（JS）、`x <- 1 + # c\n 2`（R）、C の `// c` 版も同じ改行原因で拒否される（ブロックコメント版は受理されるため、問題は改行トークンの扱いに特定できる）。
- なお JS／R の通常形（演算子の後ろで改行）は R14B-N2／R9-N9 の既登録表面そのものであり、本項目には含めない（§4）。

**R21-N12（P3／RG-11 の別表面）JavaScript の数値区切り `1_000` が虚偽の原因で拒否される**（B群 B21-B06-N1）
- `let x = 1_000;` → 「未対応：宣言の区切りが必要です」。引数位置では「) が必要です」と別の虚偽原因になる（位置依存、兄弟表面3件）。ECMAScript 2021 以降の正式文法で、Node 実物は 1000 を出力。Python 版はアプリでも正しく受理される。
- RG-11 の既列挙（基数接頭辞・先行ゼロ・接尾辞・複合型名）に「区切り」は含まれていないため別表面。

**R21-N17（P3／RG-10 の別表面）Power Apps で現在の画面がモデルにない場合、UpdateContext が生の TypeError を露出する**（E群 E21-N1）
- モデルの `screen` を存在しない名前にすると、UpdateContext で `Cannot read properties of undefined (reading 'context')` が trace と最終状態にそのまま表示される（UI 経路でも実表示を確認）。同じエンジンの Navigate 対象画面の解決には「モデルに画面がありません」という正しいガードがあり、現在画面の解決側だけガードが欠けている。兄弟表面の横断（Set／Navigate／Patch、全種類×5バリアントの生エラー走査528件）で露出はこの1系統のみ。

### 新規根本原因（9件、新グループ RG-78〜RG-86）

**R21-N9（P2／新規 RG-78）C／C++／C# で文・宣言の区切り `;` の欠落を無言受理する**（B群 B21-B01-N1）
- C `int main(){ int x = 5 printf("%d", x); return 0;}` → 正常実行し出力 `5`。宣言間版、C++ 版（`int x = 5 std::cout << x;`）、C# 版でも同型に受理（兄弟表面4件）。gcc／g++ -fsyntax-only は `error: expected ',' or ';' before 'printf'`。
- 根（推定）：c-family.js の文解析が式の終わりを次の文の開始トークンでも暗黙に区切り、`;` の必須検査を持たない。RG-06（拒否側の虚偽原因）とは方向が逆の「無言受理」側であり、RG-36／RG-62（無言受理に独立グループを与えた先例）に従い新規グループとする。

**R21-N11（P3／新規 RG-79）R で同一行の2文を区切りなしに無言受理する**（B群 B21-B01-N2）
- `x <- 1 y <- 2` → x=1・y=2 の両代入を実行。実 R では構文エラー（区切りは改行または `;` が必須）。なお `print(1) print(2)` はアプリも拒否するため、受理が非一貫。
- 根（推定）：R パーサが代入式の終端を後続の識別子でも判定し、文境界を検査していない。

**R21-N13（P2／新規 RG-82）Python round() の負の ndigits で決定的な結果を「実行時に決まる」と誤表示する**（C群 C21-C-01）
- `print(round(1250, -2))` → 実際「実行時に決まる：round の結果」。実 CPython は 1200（公式ドキュメントで負の ndigits も有効と定義、実測で確認）。int リテラル／float リテラル／変数経由の3形式全てで再現し、代入した場合は最終状態も未知化する。アプリのリファレンス項目 round は supported=true で負桁を除外していない。
- 根（推定）：Python エンジンの round 実装が ndigits >= 0 の場合のみ丸めを行い、負の場合は未知値へフォールバックする。兄弟表面の横断（他の決定的関数10件）では未知化は発生せず、round の負桁分岐に限局する。

**R21-N18（P2／新規 RG-86）複数タブの保存競合で、古いスナップショットを持つタブの保存が別タブの下書きを無言で消す**（E群 E21-N2）
- 2タブ実演（6ステップ）：タブ B が Python と R の下書きを保存した後、B の編集を知らないタブ A が保存すると、保存キー全体が A のメモリ内スナップショットで上書きされ、B の R の下書き（A が触っていない種類）まで消える。どちらのタブにも通知・警告はなく、storage イベントの購読もない。
- 根（推定）：`save()` が起動時に読み込んだ drafts 全体＋自タブの変更を単一キーへ毎回丸ごと書き戻す設計で、保存直前の再読み込み・マージも無効化もない。RG-57（単一タブ内の1枠上書き）とは機構が異なるため新規グループとする（単一枠問題が直っても本件は残る）。

**R21-N4（P3／新規 RG-80）R で実行時決定値を含む print の出力が無言で消える**（A群 A21-A-14）
- `x <- runif(1)` の後の `print(x + 1)`、`print(runif(1))`、`print(c(runif(1), 1))` はいずれも出力行自体が消える（エラーなし）。モデル化するなら ImageJ と同様に「（実行時に決まる値）」等のプレースホルダを出すべきで、無言消失は学習者に「print が実行されなかった」と誤認させる。兄弟表面5件（直接・代入・式・ベクトル経由は全滅、分岐条件のみ正常）。

**R21-N8（P3／新規 RG-81）C／C++ のエラーメッセージでカテゴリが二重表示される**（A群 A21-A-21）
- テンプレート c-error／cpp-error で「未定義動作：未定義動作：配列の有効範囲外を読み書きしています」。範囲外・符号付きオーバーフロー・整数0除算・printf 書式不一致・未対応書式（「未対応：未対応：…」）でも再現（母数8件、カテゴリ語で始まる message を持つ全種で二重化。C#・Python のカテゴリ表示は正常）。
- 根（推定）：c-family のエラー生成箇所が message 本体にカテゴリ接頭辞を含めて作り、表示側がさらに category +「：」を前置している。

**R21-N14（P3／新規 RG-83）エディタの Tab 捕捉に脱出方法の案内がなく、キーボード利用者がエディタに閉じ込められる**（D群 R21-D-N1）
- エディタにフォーカスした後は Tab を26回連続で押してもフォーカスがエディタから離れない（Tab はインデントとして消費）。脱出は「Escape を押してから Tab」という隠し仕様（app.js の tabEscape 処理）でのみ可能で、画面のどこにも案内がない（ヒント・注記・ラベルを全数確認）。捕捉は全13種類共通の単一エディタ実装のため全種別に及ぶ。
- RG-37 は「フォーカス順序の実測は未実施（積み残し）」と明記された項目であり、本件はその未実施領域で見つけた別根本原因（キー捕捉＋案内欠落）。

**R21-N15（P3／新規 RG-84）テンプレートのレベル表示が二重になり、1件はレベル自体が矛盾する**（D群 R21-D-N2）
- タイトル文字列自体にレベル語を含む7テンプレート（VBA 2件：cells／if、ImageJ 5件：ij-0〜ij-4）で、UI が別途付けるレベルと二重表示になる（例：選択肢「基礎 · 基礎 · セルに値を入れる」）。さらに ImageJ/ij-3 はタイトル「」相当とレベルメタデータ「実践」が矛盾する（内数1件）。
- 根（推定）：レベル情報の二重保持（title 文字列への内包と level フィールド＋UI 合成の併存）。

**R21-N16（P3／新規 RG-85）パス並び順のラベルが対で不整合で、「コードが長い順」は実際の指標を表していない**（D群 R21-D-N3）
- 選択肢は「出現順／コードが長い順／処理が短い順」だが、実際の並び替えは両方向とも trace のステップ数（app.js の sortPaths）であり、コードの長さではない（全パスでコード自体は同一）。並び替え自体の正確性・安定性は C群 C-16 で検証済み（新規ゼロ）であり、本件は文言のみ。C群が未確定候補として記録した同一事項は本項目に一本化した（§4）。

### 一次資料裁定による棄却 2件

- **A21-A-03（VBA の ^ が右結合になっている）→ 欠陥でない**。第16ラウンドが同一の式 `2 ^ 3 ^ 2` = 512 を一次資料で照合し「VBA の ^ は右結合であり 512 が正しい（Excel の左結合 64 とは異なる）」と裁定して仮説を棄却済み。統合側でも Microsoft Learn「Operator precedence（VBA）」の全文を再確認したが、同ページは ^ の結合性を定めておらず（左から右への評価が明記されるのは `*`／`/` と `+`／`-` のみ）、A群の根拠はこの一般原則からの推論にとどまり、第16ラウンドの言語仕様レベルの裁定を覆す材料はない。よって第16ラウンドの裁定を維持する。
- **A21-A-13（Python の大きな整数 ≥2^53 が「実行時に決まる値」に置換される）→ 欠陥に数えない（観察として記録）**。第16ラウンド角度3が同一の挙動を境界の内外で検証し、「実行時に決まる：とても大きな整数・この説明では正確に計算しません」という明示の限定文言つきで未知化され、誤数値が出ないことを確認済み（宣言モデルとして sound）。A群の再現文自体にも限定文言が表示されており、「無言の置換」には当たらない。ラベル前半の「実行時に決まる」という語が定数に対して厳密でない点は文言上の観察として記録するが、値の誤り・無言の捏造はなく、欠陥には数えない。

## 5. 未確定候補 8件（欠陥に数えない）

1. **Power Fx `Blank() = 0`／`Blank() = ""` の真偽**（A-07）：エンジンは false を返すが、Microsoft Learn 等の一次情報で確定できない。第19ラウンド以来の維持候補。実 Fx ホストでの確認が取れるまで留保し、値を捏造しない。
2. **VBA `Debug.Print` の文字列引用符付き表示**（B群）：実 VBA は引用符を付けないため RG-04 の別表面の可能性があるが、アプリの VBA 表示規約としての意図を確認できなかった。なお MsgBox 側の引用符表示は R6-N5 として RG-04 に登録済みであり、修正側で Debug.Print の扱いを合わせて裁定されたい。
3. **JS の `\uXXXX` エスケープと C# の `System.Console.WriteLine`（完全修飾名）**（B群）：実言語では合法だがアプリは未対応を宣言して停止する。正直な宣言である一方、どちらも頻出形であり、対応範囲の宣言との整合は確認を要する。
4. **ImageJ の `x = 5 print(x);`（セミコロン欠落）の受理**（B群）：ImageJ マクロパーサの文区切りの厳密さを一次情報で確定できなかった。RG-78（C系）とは分離して候補に留める。
5. **Power Fx の ForAll 内 Set の後続消失**（C群）：「未対応」と trace に明示された後、後続の Notify が trace・出力のどちらにも現れずに消える（母数5件）。実 Power Fx で ForAll 内の Set が許されるかを一次情報で確定できなかった。確定すれば「明示後に後続式が無言で落ちる」正直さの欠陥候補になる。
6. **VBA Round の負桁**（C群）：`Round(123.456, -1)` がエラーになる。実 VBA が負の numdecimalplaces を受理するか（受理するなら 120 が正解）を一次情報で確定できなかった。
7. **ImageJ のエラー表示形式**（D群 U-1）：解釈不能コードでもステータスが成功形（「1件のパス · …」）で、エラーは trace 内ステップとしてのみ表示される。エラーを trace ステップとして表すのはエンジン側の表現設計であり、実 ImageJ のエラー表現との照合なしに UI 欠陥とは確定できない。
8. **用語集に検索 UI がない**（D群 U-2）：リファレンスには検索があるため非対称だが、要件に対応する定めがなく、欠陥とは確定できない。
