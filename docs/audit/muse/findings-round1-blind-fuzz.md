## 3. 不一致の詳細と裁定

### 3.1 JavaScript：算術演算子の型強制が未対応（J2）
- 実測：`"5" + 3` → `"53"`（一致）、`1 == "1"` → true、`1 === "1"` → false、`0.1 + 0.2` → 0.30000000000000004（いずれも一致）。しかし `"5" - 3`、`5 - "2"`、`"10" / 2`、`"5" * "2"` はすべてパスエラー「数値の型が一致しません」で停止した。
- 期待（実物 Node で確定）：それぞれ 2、3、5、10。`-` `*` `/` では文字列が数値へ強制変換されるのが JavaScript の基本意味論。
- 裁定：`+` の連結と `==` の強制は実装されているのに、算術演算子だけ C 系言語のような厳密な数値型検査を課している。監査プロンプト R25 が明示する重点「型強制」に真っ向から反する。誤った値を断定はしない（エラーで止まる）ため P1 ではなく P2。

### 3.2 JavaScript：typeof 演算子が使えない（J2）
- 実測：`console.log(typeof 5);` → トップレベルで解析エラー「) が必要です」となり、パスが0件（シミュレーション全体が失敗）。`console.log(typeof (null));` → パスエラー「このJavaScript関数は説明に対応していません：typeof」（typeof を関数扱い）。
- 期待（実物）：`"number"`、`"object"` を出力して正常終了。
- 裁定：typeof は JavaScript の基本演算子であり、リファレンスにも項目がない。括弧なしの通常形式では「構文エラーがある」という誤った主張で全体が落ちるため、学習者を誤導する。P2。

### 3.3 JavaScript：var の巻き上げ（ホイスティング）が未実装（J4）
- 実測：`console.log(x); var x = 5; console.log(x);` → パスエラー「未定義の名前：x」で停止。出力なし。
- 期待（実物）：エラーにならず `undefined` の後に `5` を出力（宣言の巻き上げ）。
- 裁定：R25 が明示する重点「スコープと巻き上げ」の中心概念が再現できない。有効なコードを「未定義の名前」という誤った理由でエラーにする点も誤導的。P2。

### 3.4 JavaScript：TDZ・未定義名のエラー分類が NameError（J5）
- 実測：`console.log(y); let y = 5;` → 実行は正しく停止し先行出力もないが、エラー分類が `"category":"NameError"`、メッセージ「未定義の名前：y」。
- 期待（実物）：ReferenceError（TDZ）。
- 裁定：停止挙動は正しい。ただし NameError は Python の用語であり、JavaScript の学習者に誤ったエラー名を提示する。分類ラベルの相違として P3。

### 3.5 C：文字列・文字リテラルが扱えない（N5）
- 実測：`char buf[6] = "hello";` → パスエラー「配列初期化子が必要です」。`char buf[] = "hello";` → 「配列長を指定してください」。`char buf[3] = {'h','i','\0'};` → 「数値型が一致しません」。要素代入 `buf[0] = 'h';` → 「数値型が一致しません」。いずれの書き方でも文字列を変数に入れられない。
- 期待（gcc で確定）：文字列初期化は C の基礎であり、`printf("%s", buf)` で `hello` と出力される。
- 裁定：R22 が挙げる「文字列」が実質未対応で、semantics の対応範囲記述にも未対応と明記されていない。アプリの C テンプレート3件がすべて整数のみで文字列を避けていることとも整合する（未実装の自覚はあるが未宣言）。明示的に止まるため P1 ではなく P2。

### 3.6 C：sizeof が未対応（N5）
- 実測：`sizeof(a)`（配列）→「この関数は説明に対応していません：sizeof」（演算子を関数扱い）。`sizeof(int)` → 「NameError: 未定義の名前：int」という不適切なエラー。
- 期待：`sizeof(buf)` は 6（要素数×要素サイズ）。
- 裁定：明示的に止まる点は R05 に沿うが、sizeof は C の基礎演算子であり、型名形式のエラーメッセージは誤導的。P3。

### 3.7 C++：参照が宣言できない（G4）
- 実測：`int a = 10; int& r = a; r = 42;` → トップレベルで解析エラー「変数名が必要です」、パス0件（全体が失敗）。
- 期待（g++ で確定）：a が 42 になり出力 `42`。
- 裁定：R23 は「C との差分（参照、クラス、std:: の主要機能）」を C++ の重点としており、参照はその筆頭。semantics の対応範囲にも未対応と書かれていない。誤った構文エラーの主張で全体が落ちる。P2。

### 3.8 C++：std::string の連結ができない（G5）
- 実測：宣言と出力は可能（`std::string s = "ab"; std::cout << s;` → `ab`）。しかし `s += "cd"` と `s = s + "cd"` はどちらも CompileError「演算する型が一致しません」で停止。
- 期待（g++ で確定）：`abcd` と `size()` = 4。
- 裁定：PROGRESS.md は「STL等は未対応」と宣言しており、部分対応（宣言・出力のみ）＋明示停止はその範囲内とも読める。ただしエラーメッセージは未対応ではなく型不一致を主張しており誤導的。P3。

### 3.9 Power Apps：Filter の委任注意
- 実測：Filter のリファレンス項目は `description: "条件を満たす行を抽出します。"`、`caution: ""`（注意文なし）。一方 semantics の対応範囲には「Dataverse接続・委任・自動採番・非同期通信…は未対応です」と明記されており、「全件取れる」と断定する記述はアプリ内のどこにもない。
- 補助実行：600行のデータソースへ Filter → 全600行がコレクションに入った（モデル内データはローカルテーブル扱いのため、実務の委任とは条件が異なる）。あわせて600行規模では手順数上限（600）に達し、後続の Set/Notify が実行されずに打ち切られたが、`truncated=true` と trace の limit 項目（「手順数の上限で説明を停止しました」）で明示されていた（無言ではない）。
- 裁定：期待（ブラインド表 F5）は「委任警告と取得上限の影響を受ける。全件取れると断定してはいけない」。断定していない点と、委任そのものが未対応範囲と宣言されている点は一致。ただし学習者が Filter の項目だけを読んだ場合に委任の注意へ辿り着けない。
- Filter のリファレンスに委任・取得上限の注意文がない。

### 3.10 R：文字ベクトルの mean() がエラーで停止（R5）
- 実測：`NA + 1` → `c(NA)`、`NA == NA` → `c(NA)` は一致（TRUE を返さない点も正しい）。しかし `mean(c("a", "b"))` はパスエラー「invalid type of argument」で停止し、警告も出なかった。
- 期待（CRAN の意味論）：NA を返し、警告「argument is not numeric or logical: returning NA」を出して継続する。
- 裁定：値を捏造はしないが、実物と異なる停止挙動。P3。

### 3.11 CloudFormation：トップレベル Transform のオブジェクト形式が未対応（C5）
- 実測：`{"Transform": {"Name": "AddMetadata", "Parameters": {"Stage": "prod"}}}` と `{"Transform": [{"Name":..., "Parameters":...}]}` のどちらもトップレベルエラー「トップレベルTransformにはマクロ名を指定してください」。動作するのは文字列形式と文字列リスト形式のみ（パラメータなし）。なお Fn::Transform（局所）では Parameters が正しく渡ることを C2 で確認済み。
- 期待（AWS 公式ドキュメント「Transform セクションの構文」）：トップレベル Transform はマクロ名の文字列、リストに加え、Name と Parameters を持つオブジェクト（単体・リスト内）でも指定でき、パラメータがマクロへ渡る。
- 裁定：公式形式の一部が明示エラーで弾かれる対応範囲の不足。成功と偽らないため P3。

## 4. 観察事項（欠陥としない）

- J1：`console.log(values)` の表示が複数行の整形（`[\n 1,\n 2,...]`）で、実物 Node の `[ 1, 2, 3, 4]` と書式が異なる。値（[1,2,3,4]、合計10）は一致。
- R4：空ベクトル `x[0]` の表示が `c()`（実物 R は `numeric(0)`）。リサイクル `c(11, 22, 13, 24)` と負添字 `c(20, 30)` は一致。
- VBA の文字列出力は引用符付き（`"EXCEL"` 等）で表示される。これはアプリの表示規約（型を区別する表示）として一貫しており、値の不一致とは扱わない（V5 はこの規約を踏まえて一致と判定）。
- ImageJ エンジンのエラーオブジェクトには category がなく（undefined）、他エンジンと表示形式が揃わない。メッセージ自体は適切。
- AutoHotkey の空入力では、コードの問題ではなくモデル側の理由「モデルのeventに対応するホットキー／ホットストリングがありません」が表示される。空コードへの応答としてはやや分かりにくい。
- Python の空入力では paths が 0 件（他種は1件の空パス）。結果形状の不整合のみで、誤った断定はない。

## 5. 角度D 投入結果

### 5.1 準備済みサンプルについて（重要な前提）
- `d_path_explosion.py`（ネスト型）は、そのままでは投入できなかった。理由は2つ。(1) サンプルが使う `unknown_input()` はエンジンに存在せず NameError になる（エンジンで未確定入力を表すのは `input()`）。(2) **パス数自体の設計ミス**：各段の else が葉になるネスト構造のパス数は 2^12=4,096 ではなく 13 本である。round1-local §4 の「葉パス 4,096 本」という記述は誤りだった（本書で訂正する）。等価なネストサンプル（input() 使用）で実測しても 13 本・truncated なしとなり、エンジンの列挙が正しいことを確認した。
- `d_path_explosion_seq.py`（連型）は構造上は 4,096 パスで正しいが、未定義の裸の変数 `flag0` 等を使うため NameError になり投入できなかった。
- よって上限検証は、`input()`／`InputBox`／`prompt` を使う等価な連型サンプル（12連＝4,096パス）で代替実施した。

### 5.2 パス爆発（上限2,000・無言切り捨ての禁止）

- Python エンジンだけが、パス上限（2,000）に達する前に探索予算（操作数・時間）で打ち切り、1,681本で止まる。注記は出るが、注記文の「最大2000件までです」と実表示数（1,681件）の間にずれが生じうる。他エンジン（VBA/JS）は上限ちょうどまで列挙した。
- 所要時間は公称の上限（milliseconds=1200）を超えることがある（VBA 3,494ms、Python 2,122ms）。制限はソフトリミットとして働いており、ハングには至らない。

## 6. 追加ファズ結果

- JavaScript の絵文字識別子：`let 🍵 = 1; console.log(🍵 + 1);` がエラーなく実行され `2` を出力した（変数として束縛されることを確認）。実物 JavaScript では 🍵 は識別子に使えず SyntaxError。字句解析の識別子文字種が緩く、実行できないコードを有効として結果を断定する。なお数字開始の識別子（`let 1x`）は正しく弾かれた。
- Python の絵文字識別子は SyntaxError で正しく拒否された（エラーメッセージ内の絵文字が文字化けする軽微な表示問題あり）。
