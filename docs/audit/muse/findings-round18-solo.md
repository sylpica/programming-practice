## 角度1：貼り付け由来の入力文字（162プローブ → 新規5件）

各種類の最小プログラム（決定的な出力を持つ3〜5行）に、BOM 前置／改行混在（CRLF・LF・CR の混在）／全角スペース（U+3000）を区切り位置へ／全角記号／スマートクォート／ゼロ幅スペース（U+200B：先頭・区切り位置・識別子内）／NBSP（U+00A0）／文中 BOM 文字（U+FEFF）を適用し、「正しく動くか、文字そのものを指す正直な原因で止まるか」を検証した。

正しかった表面（抜粋）：
- Python は全変種で文字そのものを名指す正直な停止（「解釈できない文字「　」があります」等）。BOM・改行混在は正しく動作。
- ImageJ も不可視文字・全角文字を文字名指しで正直に停止する。
- JavaScript の全角スペース・NBSP 受理は ECMAScript 仕様どおり（空白として正当）で欠陥としない。文中 U+FEFF の受理も仕様どおり。
- JSON 系（Power Automate／UI.Vision／CloudFormation）の改行混在・BOM・全角スペースは正しく処理され、ZWSP は「JSONの値が不正です」で停止する（RG-10 の決め打ち表示の範囲内として新規に数えない）。

### R18-N1（P2・新規）VBA の字句解析が非 ASCII 文字を識別子に吸収し、貼り付け由来文字が幻の変数になって無言の誤値を生む

- 根本原因：VBA レキサの識別子正規表現が `[\w\u0080-\uFFFF]` を含み、全角スペース・NBSP・ゼロ幅スペース・スマートクォート・全角数字・BOM など、ほぼ全ての非 ASCII 文字が識別子の構成文字として取り込まれる。その結果、貼り付けで混入した文字が「幻の変数名」になり、暗黙変数（Empty）として無言で処理される（RG-24 の暗黙変数フォールバックと組み合わさって無言化するが、字句解析側の取り込みが本件の根本原因）。
- 再現（全て `Sub Main()` 内の最小コード、期待値は 42 または "hi"）：
  - `x =　40 + 2`（= の後に全角スペース）→ 最終状態に幻の変数 `　40=Empty` が現れ、x は **2** になる（出力も "2"）。代入の途中までが別変数に化ける。
  - `x　= 40 + 2`（= の前に全角スペース）→ 幻の変数 `x　=42` が作られ、x は **0** のまま（出力 "0"）。
  - `x<NBSP>= 40 + 2` → 同様に x は **0**、幻の変数 `x =42`。
  - `s = “hi”`（スマートクォート）→ 幻の変数 `“hi”=Empty`、s は空文字列になり `""` を出力。
  - `Debug.Print “hi”` → **"Empty"** を出力。
  - `x = ４２`（全角数字）→ 幻の変数 `４２=Empty`、x は **0**。
  - `Debug.Print x` + ゼロ幅スペース（使用側の識別子内に混入）→ x=42 のはずが **"Empty"** を出力（幻の変数 `x​=Empty`）。
  - BOM 前置 → 「この構文は説明に対応していません：﻿Sub Main ( )」と、対応しているはずの Sub 行全体を名指す虚偽原因で停止する（ファイル取込経路は BOM を除去する js/import.js とも不整合）。
  - 全角スペースを行頭・`Dim` 直後・`Debug.Print` 引数前に置くと停止はするが、原因は行全体のテキスト表示で、文字そのものを指さない。
- 影響：Excel VBA の全入力。Word・Web ページからの貼り付けで最も混入しやすい文字群が、エラーではなく誤った実行結果を生む。
- 受け入れ条件の目安：非 ASCII の空白的文字・引用符・数字が識別子に取り込まれず、文字そのもの（または文字種）を指す原因で停止するか、正しく空白として処理されること。最終状態に幻の変数が現れないこと。

### R18-N2（P3・新規）VBA の CR のみ改行・改行混在が虚偽の原因で停止する（RG-35 の別表面）

- 再現：CR のみ区切りの VBA コード → 「この構文は説明に対応していません：引数なしの単一 Sub のみ対応」で停止する。CRLF／LF／CR 混在 → 3行目付近で「この構文は説明に対応していません：Debug . Print x」と、正常な文を名指して停止する。CRLF のみは正しく動作する。
- 根本原因：VBA レキサが `\r` を行境界として扱わず読み飛ばすため、CR 区切りの行が次の行と結合し、構文全体が別物として解釈される。学習者の Sub の形は正しいのに、その形を名指す原因表示になる。
- 台帳との関係：RG-35（CR のみ改行の貼り付けで行・原因が壊れる）の根本原因と同系だが、記録済み表面は Python であり、本件は VBA の表面として別途記録する。なお本スナップショットでは、Python の CR のみは定義経由の simulate では正しく動作することを確認した（RG-35 の再現経路はアプリの貼り付け経路側の可能性があり、統合側で要確認）。

### R18-N3（P3・新規）共有スクリプト基盤の不可視文字の原因表示が、不可視のまま「構文」として示される

- 再現：JavaScript／R／C／C++／C#／AutoHotkey／Power Apps で、ゼロ幅スペース（U+200B）を先頭・区切り位置・識別子内に入れると、「この構文は説明に対応していません：​」と、原因である文字自体が不可視のまま表示される。学習者からは「対応していません：」の後に何も見えず、空の原因表示と区別できない（過去ラウンドで空の原因表示が欠陥とされたのと同型）。
- 対照：Python／ImageJ は「解釈できない文字「​」があります」と、文字であることを文で伝える形になっており、こちらは正直な停止として扱った。
- 受け入れ条件の目安：不可視文字は U+200B のようなコードポイント表記や「ゼロ幅スペース」等の名称で可視化して原因表示すること。

### R18-N4（P3・新規）R／C／C++ が、実言語ではエラーになる空白的文字を無言で空白として受理する

- 再現と実ランタイム照合：
  - R：`x　<-　40`（全角スペース区切り）と NBSP 区切りが無言で受理され、正しい値 42 を返す。実 R（Rscript で照合）は両方とも `Error: invalid multibyte character in parser` で停止する。
  - C：カンマの後の NBSP、文中の U+FEFF が無言で受理され 42 を返す。実 gcc は NBSP を `stray '\302' in program`、FEFF を `undeclared` としてエラーにする。
  - C++：`<<` の後の NBSP が無言で受理される。実 g++ は `extended character is not valid in an identifier` としてエラーにする。文中の U+FEFF もアプリ側は受理する。
- 位置づけ：結果の数値は正しいが、実言語ではエラーになる書き方を学習者が「正しい」と誤認する。無言受理を欠陥とした過去の裁定（RG-36 の Python タブ・空白混在、RG-11 の先行ゼロ受理）と同型。
- 対象外としたもの：JavaScript の全角スペース・NBSP・FEFF 受理は ECMAScript 仕様どおりで正しい。C# の NBSP・FEFF 受理は、実コンパイラ（Roslyn）が空白として許容する可能性があるため未確定として数えない。AutoHotkey／Power Apps の全角スペース受理は実ランタイム未確認のため観察に留める。

### R18-N5（P3・新規）CloudFormation で先頭のゼロ幅スペースが YAML 経路の生エラーを露出する（RG-10 の別表面）

- 再現：JSON テンプレートの先頭に U+200B を置くと、JSON 判定から外れて YAML として解釈され、ライブラリの生エラー（英語）がそのまま表示される：「end of the stream or a document separator is expected (2:13)」＋入力ダンプ。
- 台帳との関係：RG-10（入力検証がアプリ自身の言葉でない表示になる）の根本原因と同系。記録済み表面は YAML 短縮タグ（R12-N5）であり、本件は「不可視文字による経路ずれ」という別表面として記録する。なお Power Automate／UI.Vision の同入力は「JSONの値が不正です」というアプリ側の言葉で停止した。

## 角度3：非決定要素の宣言一貫性（55プローブ → 新規1件）

乱数・現在時刻・日付を返す構文を種類ごとに実行し、出力・trace・最終状態・パス条件の全表面で「実行時に決まる」未知として一貫するか、決定論的な誤値を捏造しないかを検証した。

正しかった表面（抜粋）：

- VBA：Now／Date（Dim なし）は「実行時に決まる：実行時の現在日時／現在日付」として正しく未知になる。
- Python（random／time モジュール）、C／C++（rand／time）、Power Apps（Rand／RandBetween／Now／Today）、AutoHotkey（Random）、Power Automate（%Rand()%）、UI.Vision（Math.random／Date.now）は、いずれも名前を挙げた正直な未対応で停止し、捏造はない。

- JavaScript の `Math.random()`／`Date.now()` が「未定義の名前：Math／Date」になる問題は、RG-07 の R12-N18（静的メンバーが「未定義の名前」の虚偽原因になる）記録済み表面と同一であり、新規に数えない。

### R18-N6（P3・新規）AutoHotkey の組み込み変数 A_* が全般に「未定義の名前」という虚偽原因で停止する

- 再現：`x := A_Now`、`A_TickCount`、`A_Hour`、`A_Min`、`A_Sec`、`A_MSec`、`A_YYYY`、`A_MM`、`A_DD`、`A_WDay`、`A_NowUTC`（以上が本角度の対象である時刻・日付系）に加え、横断確認した `A_ScriptDir`、`A_WorkingDir`、`A_IsAdmin`、`A_OSVersion`、`A_ScreenWidth` の全16件が「NameError：未定義の名前：A_○○」で停止する。

## 角度4：ループとステップ上限の告知一貫性（47プローブ → 新規3件）

無限ループ相当（while 常真、for(;;)、終了条件のない Loop）と、上限に当たる大きな有限ループ、および直線コードの手順数上限について、全種類で「打ち切りが告知されるか、正直な停止になるか」を検証した。アプリの上限バナー（#limit）は結果の `truncated` が真のときだけ表示される（js/app.js）。

正しかった表面（抜粋）：
- 共有スクリプト基盤（JavaScript／R／AutoHotkey／Power Apps 系）・VBA・ImageJ・Power Automate・UI.Vision の無限／大ループは、`truncated`＋理由（「ループの代表パス・回数上限」「ループ回数の上限」等）で告知され、代表パスとして打ち切られる。直線5000文でも JavaScript／VBA は「手順数の上限」で告知する。
- R の `for (i in 1:1000000)` は「ベクトル長の上限です」と上限を名指す正直なエラーで停止する。
- Power Apps の `Sequence(100000)`／`Sequence(5000)` は「Sequenceの行数が不正または上限を超えています」と上限を名指して停止する。
- Python は range(100000) までとリスト反復10万要素を完全実行し、正しい合計を返す。

### R18-N7（P2・新規）Python で静的に確定した大きな range が象徴化され、到達不可能な「0回パス」が捏造される

- 再現：`total = 0` ＋ `for i in range(200000): total += i` ＋ `print(total)` で、4つのパスが生成される。うち1つは「0回パス」で、ループを1回も回さずに出力 **"0"**・最終状態 total=0 を示す。`range(200000)` は静的に非空であり、この結果は絶対に起こらない。残りは「1回」「2回」の象徴パスと、打ち切られた具体パス。
- 境界：range(100000) までは完全実行（単一パス・正しい合計 4999950000）。range(200000) から象徴化される（境界はその間）。
- 根本原因：反復回数が内部予算を超えると、range が「実行時の対象」として汎用の代表パス群（0回／1回／2回／多数）に切り替わり、静的に確定している回数（と非空であること）が捨てられる。
- 別表面：CloudFormation のハンドラで同じ range(1000000) を使うと、変換後フラグメントに Total=0 を示すパスが現れる（同じ根本原因の CFN 表面）。
- 受け入れ条件の目安：静的に回数が確定したループでは、到達不可能な代表パス（特に0回）を作らないこと。完全実行できない場合は、他エンジンと同様に打ち切り告知つきの代表パスにすること。

### R18-N8（P3・新規）Python の while ループの打ち切りで truncated が立たず、上限バナーによる告知が欠落する

- 再現：`while True: x += 1`（出力なし／出力あり）および `while x < 100000: x += 1` は内部上限で打ち切られるが、結果の `truncated` は false のままで理由も空。アプリの上限バナー（#limit）は表示されない。
- 残る手がかりは最終状態の「（途中で打ち切ったため不明）」と、出力欄の「（繰り返しが多いため、ここから先の出力は省略します）」だけであり、後者は出力のないコードでも表示される（打ち切りの告知としては対象がずれている）。
- 対照：同じ Python でも range の象徴化（R18-N7）では truncated=true＋理由が立つ。他エンジンの while 系は全て truncated で告知する。同一アプリ内で告知の有無がループ形式によって食い違う。
- 受け入れ条件の目安：while 系の打ち切りでも truncated と理由を設定し、バナーで告知すること。

### R18-N9（P3・新規）CloudFormation ハンドラがループ途中で打ち切られると、エラーが「レスポンス形式」に付け替えられる

- 再現：ハンドラ内に `while True` を書くと、単一パスで「ハンドラは辞書形式のレスポンスを返す必要があります」というエラーになる（truncated は false）。ハンドラのコード自体は辞書を返す形になっており、実際の原因は無限ループの打ち切りである。大きな有限ループ（range(1000000)）の打ち切りパスでも同じエラーが付く。
- 根本原因：CFN のシミュレーションが「ハンドラがレスポンスを返さなかった」ことを一律に形式エラーとして報告し、打ち切りによる未帰還と区別しない。
- 受け入れ条件の目安：打ち切りで未帰還の場合は、打ち切りであることを原因として表示すること（形式エラーは、実際に辞書以外を返した場合に限る）。

## 根本原因の群分け（次バッチ向け申し送り）

1. **RG-60相当（R18-N1、R18-N2）** VBA の入力文字処理：字句解析の識別子文字クラスが非 ASCII を取り込むこと（N1）と、`\r` を行境界として扱わないこと（N2）。いずれも貼り付け由来の入力で、無言の誤値・虚偽原因を生む。N2 は RG-35 と同系だが VBA 表面として別記録。
2. **RG-61相当（R18-N3）** 共有スクリプト基盤の原因表示で、不可視文字が不可視のまま示される。
3. **RG-62相当（R18-N4）** R／C 系エンジンの空白受理範囲が実言語より広く、実言語でエラーになる文字を無言で空白扱いする。
4. **RG-63相当（R18-N5）** CloudFormation の入力検証で、経路ずれ時にライブラリ生エラーが露出する（RG-10 の別表面）。
5. **RG-64相当（R18-N6）** AutoHotkey の名前解決に組み込み変数（A_*）の表がなく、実在する名前が「未定義」になる。
6. **RG-65相当（R18-N7、R18-N8）** Python エンジンのループ上限処理：静的回数の喪失による到達不可能な代表パスの生成（N7）と、while 系で打ち切り告知フラグが立たないこと（N8）。
7. **RG-66相当（R18-N9）** CloudFormation ハンドラの未帰還の原因分類（打ち切りと形式エラーの混同）。

その他申し送り：RG-24 の受け入れ条件に「分岐条件の位置で Rnd 等を使った場合に、パスが無言で単一パスに潰れないこと」を含めること。RG-35 については、本スナップショットの定義経由 simulate で Python の CR のみが再現しなかったため、再現経路（アプリの貼り付け経路との差）の確認を含めること。
