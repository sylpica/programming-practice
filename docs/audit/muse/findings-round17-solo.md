## 角度1：複合エラーと部分実行の意味論（30ケース → 新規ゼロ）

全13種類について「有効な文で出力・代入 → 実行時エラー → 後続の文」という複合コードと、エラーが2件あるコードを実エンジンで検証した。確認した意味論は全種類で正しい：

- (a) 最初のエラーが正しい行・原因で報告される。エラー2件のケース（Python の NameError→ZeroDivision、JS の未定義参照×2、R の未定義変数→型エラー、C／C# の0除算→未宣言変数、VBA の0除算→型不一致、Power Fx の未定義名×2、PAD／UI.Vision のファイル・要素なし×2、ImageJ の未定義関数→未定義変数、AHK の未定義変数→0除算）では、すべて実行順で先のエラーだけが報告された。
- (b) エラーより前の出力と変数の最終状態は保持される（例：Python は `a=10` と出力「first」を保持し、エラー後の `c=99` は存在しない。Power Fx は `Set(A, 10)` と `Notify("first")` が残り、エラー後の `Set(C, 99)` は適用されない。UI.Vision は `x=1` と echo「first」が残る）。
- (c) エラー後の文は実行されない（後続の出力・代入が全ケースで現れない）。ループ途中のエラー（Python／JS）では、エラー発生までの反復の出力（0, 1, 2）が保持され、ループ後の文は実行されなかった。
- 言語固有の正挙動も確認：Python は後方に構文エラーがあるとコンパイル優先で何も実行しない（CPython と一致）。ImageJ の `10 / 0` は Infinity で継続（実物の double 演算と一致）。CloudFormation の未知リソースタイプはマクロ変換を素通りする（マクロは検証者ではないため正しい）。未知マクロ名は名前を挙げて正直に停止した（RG-25 の配列形式表面とは別形式の文字列形式でも正直だった）。

観察（欠陥としない）：
- JavaScript では、エラー行より後ろのトップレベル `let c = 99;` が最終状態に「未初期化」で現れる。エンジンの事前走査による宣言の先行登録で、JS のインスタンス化（巻き上げ）意味論として説明可能と判断した。
- C系の「未定義動作」エラーは、内部の message フィールド自体にカテゴリ接頭辞を含むが、UI 側（app.js の errorDescription）に重複防止のガードがあり、画面表示は「未定義動作：整数の0除算です」の単一表示になることをコードで確認した。

## 角度2：セッション状態の分離と下書き復元の状態機械（実ブラウザ24チェック → 新規1件）

実ブラウザで、種類・テンプレートを跨いだ編集・切替・実行・リロード・保存データ破損を操作した。24チェック中23件が裁定どおり：

- 編集するとテンプレート選択は即「自由」になり、未編集テンプレートへの切替はダイアログなしで即時に行われる（全行程でダイアログ0件・pageerror 0件）。
- 編集済みコードは自由枠（freeDraft）に保持され、別テンプレートを見た後でも復元できる（T1）。
- 種類を跨いでも下書き・モデル・実行結果は漏れない（Python の `globals.MARK=42` が R／JS に漏れず、Python に戻ると保持されている。JS の実行も独立）。
- リロード後は種類・コード・モデル・パス位置（js-runtime の 2/2）まで復元される。localStorage には種類別に分離保存される。
- 保存データが破損（不正JSON／drafts が配列・文字列）した場合は、回復キー `programming-practice-recovery-v3` へ原文を退避して既定表示で起動し、エラーにならない。正常な形の保存はそのまま復元される。

### R17-N2（P3・新規）種類ごとの自由下書きが単一枠で、2件目の編集が1件目の下書きを無言で上書きする

- 再現（Python で実測。他種類も同一の保存経路）：テンプレートA（tpl-calc）を編集する → テンプレートB（tpl-branch）へ切り替える → B を編集する → 自由枠を選ぶと、復元されるのは B の編集だけであり、**A の編集はどこからも復元できなくなる**（A の下書きは B の編集開始時点で `save()` の freeDraft 更新規則により無言で上書きされる）。
- 根本原因：`drafts[種類]` が保持する自由下書き（freeDraft）が種類ごとに1枠しかなく、テンプレートを編集するたびに（templateId が空になった保存タイミングで）最新の編集で上書きされる設計。INT-01 裁定（編集済みコードは復元可能な下書きとして保持する）は単一編集では満たされるが、同一種類で2つのテンプレートを続けて編集すると先の作業成果が告知なく失われる。
- 影響：全13種類共通（保存経路は共有）。種類を跨いだ場合は種類別に枠があるため失われない（T2 で確認）。
- 受け入れ条件の目安：同一種類で A・B 両方を編集しても、先の編集が失われない（テンプレート別に下書きを持つ等）か、少なくとも上書きされることが学習者に分かる表示になること。

## 角度3：式の入れ子と規模の資源境界（78プローブ → 新規1件）

深い括弧・右深二項列・関数呼出の入れ子・配列／辞書の入れ子・大量の要素／変数／アクション・巨大文字列・1行の長さなどを13種類で検証した。大半は正直な境界表示だった：

- 共有スクリプト基盤（JS／R／AHK／Power Fx）、C系、VBA は「式の入れ子が深すぎます」、ImageJ は「式や括弧が深すぎて読み切れませんでした」、UI.Vision は「JSONの入れ子が深すぎます」、CloudFormation は「変換の探索上限で停止しました」と、深さが原因であることを正しく表示する。
- 手順数・コード長の上限も告知される（PAD／UI.Vision の大量アクションは理由「手順数の上限」つきで打ち切りを告知。コード全体は100,000文字上限が明示される）。Python の巨大な添字連鎖の出力省略も告知つき。いずれもクラッシュ・例外の露出・無言の誤値はなかった（UI には 2.5 秒の watchdog と Worker 側の例外変換も備わる）。

### R17-N1（P3・新規）Python エンジンで代入文経由の深い式が「文の終わり方が正しくありません」という虚偽の原因で停止する

- 再現：`x = ` の後に括弧を約820段以上重ねた式（800段までは正常に評価される）、右深二項列（3,000段）、関数呼出の入れ子（`abs` 3,000段）、リスト内包表記の要素式——いずれも `SyntaxError：文の終わり方が正しくありません` で停止する。文の終わり方は正しく、真の原因は式の入れ子の深さである。
- 同一エンジン内の不整合：式文・`if` 条件・`print` 引数・`return` の位置では、同じ深さでも「対応外：コードの入れ子が深すぎて、この説明では読み取れませんでした」と正直に表示される。代入文の右辺などを処理する式解析経路だけが深さ診断を持たず、汎用の文末診断に落ちる。
- 兄弟表面の同ラウンド横断：括弧／右深二項／関数呼出／内包表記の4形式で同根を確認。ブロック（`if`）の入れ子は150段でも正常動作し、本件とは無関係。
- 他エンジンとの対照：JS／R／AHK／Power Fx／C系／VBA／ImageJ はいずれも深さを正直に表示するため、本件は Python エンジン固有の表面である。
- 注記：JS の入れ子配列リテラル（`[[` 隣接）の失敗は RG-39 と同一の根本原因・表面のため新規に数えない。

## 角度4：リファレンス・用語集・チップ連携の完全性（全数照合 → 新規2件）

リファレンス441件・用語集80件・テンプレート88件を機械的に全数照合した。次はすべて問題なし（0件）：同名衝突（リファレンス・用語集とも）、空の項目、`related` の解決不能、テンプレート `refs` の未登録指し、実行前チップ（scan）の未登録指し（クリック無反応チップ）、テンプレート simulate の例外。リファレンス画面の一覧・検索からは全441件に到達可能。解説（intro）のインラインリンクから到達できる項目は種類ごとに集計し、未リンク項目もリファレンス画面経由で到達できることを確認した（リンク到達のみを到達性としない）。

残ったのは、実行後チップ（使用中チップ）の消失である。受け側の仕組みは RG-28 と共通（`updateUsed` が未登録の refs を無言でフィルタする）だが、refs 生成側の混入の仕方が RG-28（受け手つきメソッド名 `same.push` 等）とは異なるため、別表面として2群を新規に記録する。なお RG-28 の既知表面（`same.push`、`document.body.appendChild`）は本スナップショットでも未解決のまま検出されたが、既知のため数えない。

### R17-N3（P3・新規）キーワードの refs が使用中チップから無言で消失する（C系・JavaScript）

- trace のステップが refs として言語キーワード（C／C++ の `return`、JavaScript の `const`／`let`／`var`）を記録するが、対応するリファレンス項目が存在しないため、使用中チップに一切現れない。
- 表面：C の全5テンプレート＋C++ の全5テンプレート（`return`）、JavaScript の5テンプレート（`const`／`let`／`var`）。学習者は return や宣言キーワードの説明へチップから辿れない。

### R17-N4（P3・新規）コード内定義名・データ名の refs が使用中チップから無言で消失する

- trace の refs に、リファレンス項目ではない名前——ユーザー定義名やデータの名前——が混入し、チップから無言で落ちる。
- 表面：R のデータフレーム列名 `score`／`bonus`（r-frame、r-frame-select）、C# の自コード定義クラス名・プロパティ名 `Counter`／`Total`／`Value`（cs-object、cs-shared-total）、AutoHotkey の `Value`（InputBox 結果のプロパティ。ahk-loop の2パス）、UI.Vision の `Number`（ui-loop、ui-loop-select）、JavaScript のプロパティ名 `length`／`body`（js-array、js-build-summary）。
- R17-N3 と同根（refs の語彙がリファレンス項目名に揃っていない）だが、生成経路（キーワード注釈／名前解決の混入）が異なるため分けて記録する。
