## 角度1：残り言語の公式カタログ完全性

母数：第13ラウンドで扱わなかった6言語について、公式一覧の主要項目を列挙してプローブした。合計 **407件**（Python 122、JavaScript 96、C 42、C++ 34、R 66、C# 47）。各項目を「正しく動く（実物と一致）／名前を挙げて正直に停止／欠陥」の3値で判定した。実物のある言語（Python／JS／C／C++）は実 CPython／Node／gcc／g++ の出力と機械比較し、R／C# は公式仕様の期待値で判定した。欠陥候補はすべて素の形で再プローブして切り分けた（再プローブ：C 8件、C++ 21件、R 14件、C# 16件、JS 6件）。

### Python（122件）：新規ゼロ
- OK 85件、正直な停止36件。`super` の1件は「未対応：継承・メタクラスは未対応です」と機能名を挙げた明示宣言のため正直な停止と裁定。
- 組み込み関数の未対応はすべて「未対応：組み込みの『名前』はこの説明では解釈しません」、メソッドの未対応は「未対応：str の『名前』は…」と名前を挙げて停止。銀行丸め（round(2.5)=2）まで実物と一致。

### JavaScript（96件）：新規1件（R14-N2）
- OK 11件、正直な停止47件。String メソッドは全項目が名前を挙げて正直に停止（エンジンの文字列メソッド対応は無いが正直）。
- 欠陥候補38件の内訳：アロー関数コールバック9件（filter／find／findIndex／flatMap／forEach／map／reduce／some／every の「) が必要です」）＝ **R9-N5 の再現**。静的名前空間の未対応メンバー27件（Number.*／Math.*／Object.*／Array.*／JSON.* の「未定義の名前」）＝ **R12-N18 の再現**（R12-N18 は Math.PI まで明示的に対象化済み）。
- **R14-N2 (P2) JavaScript: 入れ子配列リテラルが汎用原因で停止する**
  - 再現：`let a = [1, [2, 3]];` → topErr「エラー：] が必要です」。引数位置 `console.log([[1, 2], [3]].length);` → 「式を解釈できません：[[」。`Object.fromEntries([["a", 1]])` も同じ根で停止。
  - 対照：フラットな配列リテラル、レコードを要素とする配列 `[{x: 1}]` は動作する。配列の中の配列だけが汎用原因で止まる。宣言初期化子のリテラル形が虚偽原因で止まる座として R12-N6（レコードリテラル、P2）と同格に P2 とした。

### C（42件）：新規ゼロ
- OK 2件（printf、abs）、正直な停止33件。初期候補7件（strcmp／memcmp／isdigit／isalpha／isspace／div／malloc）は全て切り分けで解消：前5者は私のプローブに含めた三項演算子（R12-N9 既知）起因で、関数単体では名前を挙げて正直に停止。div／malloc も関数単体では名前を挙げて正直に停止し、malloc のキャスト形式は宣言済みの未対応（ポインタキャスト）だった。
- 構造体は `struct Point` のタグ名を挙げて「未対応：この構文は説明に対応していません：Point」と停止するため、宣言済みの未対応と裁定（観察：`div_t d = div(7, 2);` の形では変数名 `d` を名指す表示になるが、div 関数自体は正直に停止する）。

### C++（34件）：新規2件（R14-N3、N4）
- OK 3件、正直な停止21件（std::sort／find／min／max／sqrt／pow／floor／ceil 等は名前を挙げて停止。std::swap は個別宣言では名前を挙げて正直に停止し、初期候補はカンマ宣言＝宣言上対象外の起因だった）。
- **R14-N3 (P2) C++: std::string の有効な添字参照と直接初期化が虚偽の「未定義動作」で停止する**
  - 再現1：`std::string s = "hello"; std::cout << s[1];` → 「未定義動作：無効または寿命の切れたポインタの参照」。s[0]、変数への代入 `char c = s[1];` でも同一。有効範囲の添字は実 C++ では well-defined。
  - 再現2：`std::string s("ab");`（直接初期化）→ 「未定義動作：未初期化の値を読み取っています」で s は未初期化のまま。コピー初期化 `= "ab"` は動作し、`s + "cd"`、cout 出力、`==` も動作する。
  - 兄弟洗い出し：char 配列の添字は正常。範囲外添字 s[9] の UB 表示自体は実物でも UB のため欠陥に含めない。有効範囲だけが虚偽。
  - なお raw の error は category=「未定義動作」かつ message が「未定義動作：…」で始まるが、UI の errorDescription は二重化を防ぐため実画面で接頭辞は二重にならない（ハーネス表示上の見かけであり欠陥ではない。R8 の取り消しと同型）。
- **R14-N4 (P3) C++: 未対応のジェネリック型宣言が虚偽・汎用の原因で停止する**
  - `std::vector<int> v;` → 「NameError：未定義の名前：vector」。`std::set<int>` も「未定義の名前：set」。vector は型テンプレート名であり未定義の変数名ではない。
  - `std::map<std::string, int>`／`std::pair<int, int>` は「未対応：この構文は説明に対応していません：,」とカンマを名指して停止（R13-N9 と同型のトークン名指し）。

### R（66件）：新規2件（R14-N1、N9）
- OK 9件、正直な停止49件。表示形式の相違3件（is.na(NA) → c(TRUE)、as.numeric("42") → c(42)、as.character(42) → c("42")）は、長さ1ベクトルを c(...) で表すアプリ内表記のため欠陥でないと裁定。初期候補の log／dim／names(list) は内側の未対応関数（exp／matrix／list）を名指す正直な停止で、対象関数単体では正直に停止することを再プローブで確認。
- **R14-N1 (P2) R: `c(a = 1, b = 2)` の名前付きベクトルが無言で空ベクトルになる**
  - 再現：`v <- c(a = 1, b = 2)` の後 `print(v)` → `c()`（値が無言で消える。エラーなし）。最終状態も `v=c()`。`v["a"]` → `c(NA)`。名前なし `c(1, 2)` は正常。
  - 名前付きベクトルは R の基礎形であり、無言の誤値（データ喪失）のため P2。付随：`names(v)` が null を返すのは v 自体が空になった帰結であり、names(data.frame) は正常。`names(v) <- ...` の代入形は「未対応：…：代入先」と宣言して停止するため正直。
- **R14-N9 (P3) R: 引数位置の無名関数式が「) が必要です」の虚偽原因で停止する（R12-N23 と同根の別表面）**
  - 再現：`sapply(c(1, 2), function(v) v * 2)` → topErr「エラー：) が必要です」。lapply も同一。
  - 名前付き関数を定義して渡す形は定義行で R12-N23（引数名の NameError）の再現になる。関数式そのものが扱えない根は同じだが、引数位置では別の虚偽原因になるため別表面として数える。

### C#（47件）：新規4件（R14-N5〜N8）
- OK 1件（Array.Length）、正直な停止41件（Convert.*／Math.* のメソッド呼び出し／String のインスタンス・静的メソッドは全て名前を挙げて停止）。文字列の .Length は **R12-N16 の再現**。
- **R14-N5 (P3) C#: 静的フィールド参照が「未定義の名前」で停止する（R11-N3 と同根の別表面）**
  - 再現：`Math.PI` → 「未定義の名前：Math」。`Math.E`、`String.Empty`（「未定義の名前：String」）も同一。メソッド呼び出し形（Math.Abs 等）は「この関数は説明に対応していません：Math.Abs」と名前を挙げるのに、フィールド参照だけが名前空間自体を未定義名と誤認する。R11-N3 は int.MaxValue／MinValue が対象だったため、Math／String の表面を別件として数える。
- **R14-N6 (P3) C#: TryParse の `out` 引数が「) が必要です」で停止する**
  - 再現：`bool ok = int.TryParse("42", out x);`（事前宣言・inline 宣言・out var の全形式）→ 「) が必要です」。`double.TryParse("1.5", out double x)` も同一（兄弟洗い出し済み）。out 引数は C# 教材の頻出形で、原因表示は虚偽。
- **R14-N7 (P3) C#: `new T[] { ... }` 初期化子付き配列生成式が汎用原因で停止する**
  - 再現：宣言位置 `string[] a = new string[] { "a", "b" };` → 「式を解釈できません：]」。`new int[] { 1, 2 }` も同一。引数位置（String.Join）では「) が必要です」。対照：暗黙初期化子 `string[] a = { "a", "b" };` と サイズ指定 `new string[2]` は動作する。
- **R14-N8 (P3) C#: ジェネリック型宣言が汎用・トークン名指しの原因で停止する**
  - 再現：`List<int>`（完全修飾）→ 「式を解釈できません：)」。`Dictionary<string, int>` → 「未対応：この構文は説明に対応していません：,」（カンマ名指し）。`HashSet<int>` → 「式を解釈できません：)」。ジェネリクス未対応の宣言はどこにも無く、原因が型を名指さない。
  - 観察：`new System.Random()` は代入先変数名 `r` を名指して停止 ＝ R11-N10 の再現（新規でない）。`var` 宣言は「この宣言・型推論はモデルで未対応です：var」と名前を挙げて正直に停止する。

## 角度2：入力（実行時に決まる値）の意味論

母数：12種類・約65件の有効プローブ（Python 7、VBA 9、JavaScript 6、C 7、C++ 4、C# 4、R 3、ImageJ 5、AutoHotkey 5、Power Automate 4、PowerApps 3、UI.Vision 2）。CloudFormation はパラメータが具体値モデルであり未確定入力の構文を持たない（Conditions は宣言どおり未評価、R10 で裁定済み）ため対象外とした。各種類で「単一入力の分岐／複数入力の組み合わせ／矛盾しうる条件の剪定／ループ条件／入力同士の比較／文字列化」を確認した。

- 健全だったもの：Python・VBA・JS（prompt）・C#（ReadLine）・R（readline・モデル変数）・ImageJ（getNumber／getString）・AHK（InputBox）・Power Automate（入力ダイアログ）はすべて、独立な2入力で完全な組み合わせのパスを列挙し、矛盾条件（x>10 と x<5 等）では両立しないパスを剪定し、ループ条件では代表パス＋打ち切り理由を明示した。入力同士の比較は全種類で「複数の未確定値・非線形式を組み合わせた比較は未対応です」と名前を挙げて正直に停止。文字列化は出所つきの式表示（例：`実行時に決まる："hello " + 標準入力またはストリーム終端`）になり、値の捏造はなかった。JS の prompt 文字列連結は「未確認：型が未確定の算術・文字列演算」と宣言して停止（正直）。
- C／C++ は設計上「実際の標準入力は読みません」と宣言されており、scanf／getchar は関数名を挙げて、std::cin >> は演算子を名指して正直に停止する。
- **R14-N10 (P3) C++: `std::getline(std::cin, s)` が「未定義の名前：cin」という虚偽原因で停止する**
  - 再現：`std::string s; std::getline(std::cin, s);` → 「NameError：未定義の名前：cin」。cin は未定義の名前ではない。兄弟洗い出し：`std::cin.get()` は「この関数は説明に対応していません：cin.get」と名前を挙げ、`std::cin >> x` は「未対応：…：>>」と宣言する。値位置で cin を参照する getline 形だけが虚偽原因になる。
- PowerApps はコントロール値（モデル具体値）で分岐が正しく決まり（Value(Input1.Text)=3 → "big"）、空データソースの LookUp → Blank → IsBlank 分岐も正しい。未設定変数の条件参照は NameError で正直に停止。

## 角度3：パス条件ラベルの正確性の全数点検

母数：全88テンプレート × 全パス（テンプレート固有モデルで実行し **94パス**、トップレベルエラー0件）。条件を引用する形式のエンジン（Python の条件「…」、ImageJ の条件（…））については、引用文がコード内の条件と一致するかを正規化して全件照合した。あわせて全トレースを内部トークン漏れパターン（false or／(model)／[object 等）で走査し、判定ステップ列が同一で結果が異なるパス対（ラベルで識別できないパス）がないかも確認した。

- 条件引用の不一致は1件のみ（下記 R14-N11）。判定ステップ列の重複（結果相違）は0件。
- 内部トークン漏れは vba/input の「false or」5件のみ ＝ **R4-N4 の再現**（新規でない）。
- 走査条件の教訓（再掲）：初回走査は種類デフォルトのモデルで実行したため、テンプレート固有モデルを持つテンプレート（AHK の event、js-build-summary の入力値 "7" 等）で見かけの異常（パス0件、NaN 表示）が出たが、いずれもテンプレート固有モデルでの再走査で解消した。js-build-summary の NaN はデフォルトモデルの入力値「学習者」を Number 化した私の走査起因であり、テンプレート本来のモデルでは合計12が正しく出る。
- **R14-N11 (P3) ImageJ: 括弧なし組み込み呼び出しの条件ラベルに、コードに無い `()` が付く**
  - 再現：テンプレート ij-4 のコードは `if (nImages == 0)` だが、トレースは「条件（nImages() == 0）は偽 → else 側を実行します」と表示する。
  - 兄弟洗い出し（新規プローブ6件）：`nResults == 0` → 「nResults() == 0」、`nSlices > 1` → 「nSlices() > 1」と、括弧なし組み込み呼び出しは一貫して () 付きで表示される。関数形 `getWidth() > 100`、文字列比較 `getTitle() == "demo.tif"`、変数条件 `x == 5` はコードどおり正確に引用され、真偽の判定自体も全て正しい。ラベルの引用形だけが元のコードとずれる。

## 角度4：パスごとの最終状態の正直さ

母数：角度3と同じ全88テンプレート × 94パスで、「いずれかのパスで代入される変数」の集合をパス横断で取り、各パスの最終状態（vars と表示 groups の両方）に、その変数が「値／未設定の明示／不在」のどれで現れるかを全件分類した。加えて、片側分岐でのみ代入される変数を持つ対象プローブを7種類（Python／VBA／JavaScript／C#／R／ImageJ／AutoHotkey）で実行した。
