## 2. 契約の要点（正本は advanced-interface.md）

- エンジンは単一。モードで変わるのは参照カバレッジ／名前解決カタログ／テンプレート・用語集の表示範囲のみで、同じコードの実行結果はモードで変えない。IPA擬似言語は両モード同一・完全実装済みとして差分対象外。
- 高度項目は `status`（supported／unsupported／unverified）の明記が必須。状態はデータの単一フィールドを正とし、全表示面はそこから描画する。未検証は原則として正直に停止し、ラベルのみ未対応と区別する。「未確認」の範囲には項目を作らない。
- 差分は種類ごとの `reference-advanced*.js`（分割可、manifest で列挙）／`templates-advanced.js`／`glossary-advanced.js`。既存項目の変更は `referenceOverrides`（name 照合）経由でのみ行う。name／id の重複と存在しない override は契約違反として problems に記録され、違反のある差分は出荷しない。
- 高度差分は precache に入れず、種類を高度モードで開いたときに遅延ロードし、SW ランタイムキャッシュでオフライン再訪にも使えるようにする。
- モード開示文は計画書 1.2 の文面を一字一句そのまま常時表示する。リファレンス先頭の件数表示（対応／未対応／未検証）と状態フィルタが開示を裏づける。到達性（F-02）は全状態の項目に適用される。

## 5. コーディネーター判断（計画書の文面と確定仕様の差異）

契約文書の「未決・留保」R-1／R-2 に記録したとおり、計画書 1.3 の文面と本機構の確定仕様に2点の差異があり、確定仕様を採用した。いずれも計画の趣旨（誤りゼロ・正直な開示）の範囲内の精密化であり、判断としてここに明記する：

- **R-1**：計画書は「名前の重複時は高度側が優先」とするが、本契約では「既存項目の変更は referenceOverrides 経由でのみ行い、素の重複は契約違反として記録する」とした。理由：重複を黙って上書きすると、意図した変更とデータ事故の区別がつかなくなり、F-02 の機械照合で検出できなくなるため。
- **R-2**：計画書は「エンジン拡張は種類の index.js が両テーブルを合成」とするが、本契約では `applyAdvancedEngine` フック経由に一本化し、index.js の静的 import で高度テーブルを常時読み込まない形とした。理由：静的合成は遅延ロード（A-11）と両立しないため。具体的な使い方の初例は B1 ブロックで確定する（留保 R-3）。
