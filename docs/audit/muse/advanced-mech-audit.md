## 2. 指摘一覧

### D-1（P2）failed 時も部分合成される ― 契約 §7.1「基礎カタログのみで動作」と食い違い

- 根拠：`js/app.js` の `applyCatalog()` は `loaded.failed` が非空でも `mergeCatalog` の結果を採用し、`catalogFailed` で注記を出すだけである。契約 §7.1 は「manifest に明示されたファイルの読み込み失敗は failed に入る。この場合、アプリは**基礎カタログのみで動作**しつつ、モード開示行に読み込み失敗の注記を出す」と定める。
- 再現：uivision に manifest（referenceParts に不存在ファイル `reference-missing-fx.js` を明示）＋正常な reference-advanced.js を置き高度へ切替。開示行に「（高度データの一部を読み込めませんでした）」は正しく出るが、件数表示は合成後（全28件）になり、読み込めた側の高度項目が表示される（基礎のみなら全25件のはず）。
- 判定：実装の挙動（部分合成＋注記）自体は「高度のふり」をしておらず正直だが、契約文面とは明確に異なる。ブロックチームが契約を正として差分を作る以上、どちらかに統一が必要。契約を正とするなら実装を基礎のみへ、部分合成を正とするなら契約 §7.1 の改訂が必要（コーディネーター判断事項）。

### D-2（P2）manifest がフィールドを省略した場合、既定ファイルの不存在が failed に誤分類される

- 根拠：`js/core/advanced-loader.js` の `importClassified` は、manifest が読めたかどうか（`explicit` フラグ）だけで missing／failed を振り分ける。manifest に `templatesFile`／`glossaryFile` を書かなかった場合も既定名で import を試み、失敗すると **failed** になる。契約 §7.1 の区別は「manifest に**明示された**ファイルの失敗＝failed／既定ファイルの不存在＝missing」であり、省略された区分の既定ファイルは明示されていない。
- 再現（Node プローブ）：manifest `{ referenceParts: [] }` のみを置いた一時ディレクトリで `loadAdvanced` を呼ぶと、実在しない `templates-advanced.js`／`glossary-advanced.js` が `failed` に入る（`missing` は空）。
- 影響：契約 §5.2(a) の形式どおり「referenceParts だけ書いた manifest」を出す種類では、高度テンプレート／用語集が無いだけなのに失敗注記が出て利用者に誤報する。D-1 の取扱い次第では基礎のみ動作に落ちるおそれもある。

### D-3（P3）内容不正の part ファイルが loaded と failed の両方に入る

- 根拠：Node プローブで、export を欠く reference part は `loaded: ["part.js"]` かつ `failed: ["part.js"]` になった（`importClassified` が loaded へ積んだ後、内容検査で `failOnce` する）。契約は3リストの重なりを禁じていないが、消費側が「loaded＝成功」と解釈すると誤る。現行の利用側は `failed.length` のみを見るため利用者影響はない。

### D-4（P3）status 導出が表面ごとに不一致（不正 status の場合）

- 根拠：`catalog.js` の `itemStatus`／`countByStatus` は不正な status を `"supported"` に倒す。一方 `js/app.js` の `renderRefs`／`fullRefs` 内のフィルタ述語は `r.status` の生文字列をそのまま比較するため、不正 status の項目は「全て」以外の全フィルタで消えるのに件数では対応に数えられる（Node プローブで導出値の相違を確認）。契約違反データ（problems で出荷抑止）でのみ到達可能だが、機構の表面間で導出規則が二重になっている。

### D-5（P3）precache／SW の除外正規表現が契約の文面より狭い

- 根拠：契約 §7.2 は「ファイル名に `-advanced` を含む .js ファイル」を除外対象とするが、実装の正規表現 `-advanced(-[^\/]*)?\.js$` は `reference-advanced2.js` のような「-advanced の直後に英数字が続く」名前に一致しない（実測で false）。そのような命名の高度ファイルを置くと precache に混入する。契約の例示名（reference-advanced.js 等）は全て一致するため現行命名では問題は出ないが、命名規約として契約と実装のどちらかに寄せるべき。

### D-6（P3）SW がステータスを問わず応答をランタイムキャッシュへ保存する

- 根拠：`sw.js` の network-first 実装は `response.ok` を確認せずに `cache.put` する。実ブラウザで、404 の `advanced-manifest.js` 応答が `programming-practice-advanced` に保存されていることを確認した。オフライン時に import は再び失敗し missing 扱いになるため機能影響は実質ないが、エラー応答をキャッシュする作法としては不適切。

### D-7（P3・観察）不存在ファイルへの import 試行によるコンソール 404 と、ローダーキャッシュの失敗固定

- 高度差分の無い種類を高度で開くと、既定ファイルへの動的 import 試行が 404 となり、コンソールにリソースエラーとして記録される（uivision では advanced-manifest.js の1件、種類切替を含む操作では種類ごとに最大4件）。**ページエラー・JS 例外は全実測を通じて 0 件**であり、missing 判定の仕組み上の帰結だが、D-16 の「コンソールエラー 0 件」を厳密に読むと抵触する。設計上の受容か、manifest 先行確認などの回避策を採るかは判断事項として記録する。
- あわせて、`advanced-loader.js` のキャッシュは種類 id のみをキーとし、failed を含む結果がセッション中固定される（再試行はリロード時のみ）。契約は再試行を定めていないため違反ではないが、一時的なネットワーク失敗が回復後も注記に出続ける点は観察として記録する。
