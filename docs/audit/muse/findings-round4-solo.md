## 角度3：ファズ第2弾＋境界入力（work/r4-fuzz.mjs 93件、r4-fuzz2.mjs 39件、本ラウンドで再確認プローブ追加）

### 総括
- **ハングなし**（最長でも約1.9秒）。**無言の打ち切りは R4-N1 以外に見つからなかった**：Python の逐次二分岐2,048通りは1,740パスで打ち切り＋理由（reasons）明示、VBA の長大な ElseIf 連鎖は「条件の探索上限で説明を停止しました」と明示停止、JavaScript の独立 if 100連も打ち切り＋理由明示で停止した。
- 空コード・空白のみ：全種類で暴走せず、種類ごとに妥当な空結果または明示エラー（CloudFormation「テンプレートはオブジェクトで指定してください」、Power Automate／UI.Vision「JSONの値が不正です」等）。
- 超長行（1万字）・式の連鎖（5,000項）・深い入れ子：処理可能。JavaScript の深すぎる括弧は「式の入れ子が深すぎます」と明示停止。
- ソース上限：100,000文字超は「コードは100000文字以内にしてください」と明示。
- Unicode：絵文字・サロゲートペア・結合文字・RTL は全種類で処理可能。長さの意味論は言語仕様どおり（Python の len はコードポイント数=2、JavaScript の length は UTF-16 ユニット数=2）。
- 壊れた入力（未閉文字列・ゴミトークン・不正 JSON 等）：全て行・原因つきの明示エラー。
- AutoHotkey の意味論の正確さを確認した点：`1/0` → ZeroDivisionError（v2 の実挙動どおり）、`"2" + "3"` → 5（数値文字列の強制変換どおり）、`1e3` → 1000、ToolTip の文形式は「このAutoHotkey関数は未対応です：ToolTip」と正直な未対応宣言。
- ファズ第1弾の Part A（AutoHotkey）は、デフォルトモデルの event が設定された状態で実行されたため全件が event 不一致エラーになり無効だった。第2弾（fuzz2 の A2、event=null モデル）で再実施され、本ラウンドの解釈は A2 に基づく。

### R4-N1（P2・新規）：else-if 連鎖と深い入れ子でパスが無言欠落する（共有スクリプトエンジン）
再現（work/r4-reprobe.mjs、r4-reprobe2 の詳細確認）：
- JavaScript：`const c = prompt("q"); let x = 0;` に else-if を65条件つなぎ、最後に `else { x = -1; }` と `console.log(x);` を置いたコード。正しくは66パス。実測は **65パス、truncated=false、reasons=[]（打ち切りの告知なし）**。内訳は、条件1〜64の成立パスは正しいが、(a) 65番目の条件の成立パス（x=65）が欠落し、(b) 全条件不成立→else のパスが「ブロックの入れ子が深すぎます」というエラーパスに化ける（x=0 のまま、console.log も未実行）。
- 境界：64条件までは完全（65パス・else 到達・出力 -1）。
- 既知条件でも発火する：AutoHotkey で c が既知値の65連 else-if は、1パスだけが同エラーになり、正しい結果が一切得られない。R（未知条件）でも65パス中1件が同エラー。
- 真に入れ子にした if 70段（別変数）でも、深さ64を超えた先のパスが同じ形で欠落する（この場合「入れ子が深すぎます」の文言自体は的外れではないが、欠落は無言）。
- 機構：else-if は otherwise 内の入れ子 if として実行され、エンジンの深さ上限（LIMITS.depth=64）を1条件ごとに消費する。上限超過はパス内のエラーに変換されるため、truncated フラグや reasons に反映されない。
- 対照（正しい実装）：VBA は同じ形の100条件を101パス正しく列挙する。Python は上限到達時に truncated＋reasons を明示する。PowerApps の深い If 入れ子は解析時点で「式の入れ子が深すぎます」と明示エラーで停止する（正直な停止）。
- 判定理由：要件第4章「未表示のパスがある場合はその旨を表示」に反する無言の欠落であり、第1ラウンドで Codex が CFN について P1 とした CX07 と同種。表示されるパス自体の値に誤りはないこと、発火に65連以上の連鎖・入れ子を要することから P2 とする。平坦な else-if に対する「入れ子が深すぎます」は原因表示としても誤り。

### R4-N2（P3・新規）：基数付き整数リテラル（0x／0b／0o）が Python 以外で虚偽の原因表示で停止
再現（work/r4-reprobe2.mjs）：
- JavaScript `console.log(0x10);` → 「) が必要です」で停止（実 JS では 16）。`0b101`、`0o17` も同様。
- R `print(0x10)` → 「) が必要です」（実 R では 16）。
- C／C++／C# `int x = 0x10;` → 「未定義の名前：x10」（gcc／g++ では 16 で正常な基本構文）。
- AutoHotkey `x := 0x10` → 「未定義の名前：x10」、`MsgBox(0x10)` → 「) が必要です」。
- 正常な対照：Python は 0x10→16、0b101→5、1e3→1000.0、1_000→1000 の全てが正しい。JavaScript／C の 1e3 は正常（1000）。
- 判定理由：明示停止ではあるが原因表示が虚偽であり、第2ラウンド R2-N3（キャスト構文＋誤導的エラー）と同じ欠陥類型。16進リテラルは各言語の基本構文で、AutoHotkey では色・フラグ指定でも用いる。
- 参考：VBA の `&H10` 記法も未対応だが、「式を解釈できません：&」という停止で原因表示は虚偽ではないため、本件には含めない。

### 既知残件 R3-N1 の範囲確認（新規欠陥として数えない）
fuzz2 の A2 で横断した結果、R3-N1（AutoHotkey 文形式・単項符号引数の誤原因表示）の再現範囲は当初の想定より広かった：単項 +／− で始まる引数の全形式（数値・小数・変数・文字列・括弧式・空白を挟む形）、ToolTip -3、Sleep -1 でも同じ「未定義の名前：＜関数名＞」になる。さらに引数なしの文形式 `MsgBox` 単独行も、同じ文形式パーサの経路で同じ誤原因表示になった。これらは同一根（文形式呼び出しの認識に失敗し名前参照に落ちる）のため、R3-N1 残件の再現範囲として記録し、新規欠陥とは数えない。

### 観察（欠陥でない）
- Python の elif 連鎖（1,999／2,000条件）は手順上限のため25パスで打ち切られたが、truncated＋reasons の明示あり。2,000パスの列挙には届かない形状だが、告知は正直である。
- JavaScript の switch は「この構文は説明に対応していません：{」と未対応を明示して停止する（末尾の「：{」は簡素だが虚偽ではない）。
- エンジン API を model=undefined で呼ぶと種類により挙動が違う（Python は例外が外へ出る、JavaScript は TypeError 文面がエラーとして返る）。UI は常にモデルを渡すため到達不能で、観察に留める。

  - 入れ子の型不一致：code が数値（S1）・オブジェクト（S2）、model が文字列（S3）・null（S4）、draft 自体が文字列（S5）、freeDraft.code が数値（S6）、pathId／sort／auto の異常値（S9）、active が数値（S10）、VBA モデルの入れ子オブジェクト（S11）、modelText がオブジェクト（S12）のいずれでも、例外なく操作を継続できた。
