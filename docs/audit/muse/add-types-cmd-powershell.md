## 0. 前提と全体ルール

- 対象：新規に2種類を追加する。**コマンドプロンプト（cmd）** と **PowerShell**。種類の id は既存の命名規則に合わせて `cmd`／`powershell` とし、表示名は「コマンドプロンプト」「PowerShell」とする。

- 進行順序：ローカルで2種類の実装と再検証を終える → 節目の1回で配信する。配信ルールの詳細は §7 に従うこと。
- `PROGRESS.md` は節目コミットの中に同梱して更新すること（単独 push 禁止）。対象を「全15種類」に更新し、2種類の状態行を追加すること。監査対応レポートは `docs/audit/CODEX-R6.md` に新規作成し、種類ごとの実装範囲（対応した／正直な未対応とした構文・コマンドの一覧）と検証結果を具体的な数値で示すこと。ユーザーが自分で検証する必要のない形で報告すること。
- 対応・未対応の宣言は `docs/DEVELOPMENT.md` に2種類分を追加し、実装と一致させること。
- フロントエンドの実装に触れる場合は Modern Web Guidance（GoogleChrome 公式スキルパック）の導入を試み、関連ガイドを参照すること。導入の成否（環境制約で不可の場合を含む）を報告に含めること。ただしベンダー実施ベンチマーク由来のガイドであり、従来の監査基準・共通UIルール（スクロールを減らす／文字の切れを作らない／説明文は下の方へ）が優先する。

## 1. 実装の大原則

1. **既存の枠組みに乗せる。** 「定義データ＋種類ごとのモジュール」（`js/types/<id>/` ＋ `registry.js` への登録）で追加し、共通基盤（パス列挙・trace・最終状態・使用中チップ・ファイル取り込み・テンプレート／リファレンス／用語集の各画面）を再利用すること。共通基盤の拡張が必要な場合は、既存13種類の挙動を変えない形で行い、その旨を CODEX-R6.md に明記すること。
2. **誤った値の捏造と、虚偽の原因表示は不可。** 実装できない構文・コマンドは、構文名・コマンド名を挙げた「未対応」の正直な宣言で停止し、宣言（DEVELOPMENT.md の対応・未対応リスト）を実装と一致させること。正直な未対応化は劣化ではなく、受理可能な実装として扱う。
3. **仮想マシンは作らない。** シミュレーションは、変数・出力・仮想的な現在フォルダとファイル一覧の範囲で完結させる。実ファイル操作・実プロセス実行は行わない。実環境でしか決まらない値（実ファイルの内容、実コマンドの成否など）は捏造せず、入力モデル（実行時に決まる値）として扱うこと。
4. **表示は各シェルの正規表記に合わせる。** trace・出力・最終状態の3表面で矛盾させない。実在しない表示形式を作らない（例：PowerShell のオブジェクトはプロパティを持つ形で示し、内部表現の生JSONや `[object Object]` のような表示を出さない）。

## 2. 共通要件（既存13種類と同一の利用体験）

- **4画面**：コード練習／リファレンス／テンプレート集／用語集。リファレンスには §3 に挙げたコマンド／コマンドレットと構文要素を、既存種類と同程度の粒度で収録すること。用語集には2種類の基本用語（環境変数、終了コード、パイプライン、オブジェクト等）を追加すること。
- **テンプレート**：種類ごとに基礎〜応用まで学習に使えるテンプレートを複数用意し、種類ごとの偏りがないこと（既存種類と同程度の本数が目安。具体的な本数は CODEX-R6.md に種類別に明記）。テンプレート解説は実行シミュレーションの下に全展開表示とし、解説から用語・リファレンスへ飛べること。
- **コード説明／実行シミュレーション2モード**：実行ボタン式と、コード更新時に常時表示が追随する式の両方。エラーは行と原因を示すこと。説明文クリックで該当行へジャンプ＋自動スクロールすること。
- **分岐パスの全列挙とナビゲーション**：if／for 等の分岐から取りうるパスを全部表示し、左右切替・件数表示（n/N）・ソート・先頭／末尾ジャンプ・番号指定ジャンプを提供すること。**パスの上限は2,000件** とし、上限に達した場合はその旨を告知して打ち切る（無言で欠落させない）こと。条件ラベルは、学習者がコードと対応づけられる表記にすること。
- **使用中チップ**：コードで使用しているコマンド／コマンドレット・組み込み要素を、使用中パネルにパス連動で表示し、押すとリファレンスの説明が開くこと（既存種類の「使用中の関数」チップと同じ仕組みに、コマンド／コマンドレットを載せる）。
- **終わったときの状態**：変数は右パネルに出さず、下部の「終わったときの状態」に表示すること。cmd は環境変数の一覧と ERRORLEVEL、現在フォルダを、PowerShell は変数とパイプライン最終値、現在フォルダを、それぞれ含めること。
- **入力モデル**：実行時に決まる値（ユーザー入力、実環境依存の結果）は値を捏造せず「実行時に決まる」ものとして扱い、入力候補の列挙・組み合わせの剪定は既存種類の入力モデルと同じ規則で行うこと。
- **ファイル取り込み**：ドラッグ＆ドロップでコードに反映できること。拡張子は cmd が `.bat`／`.cmd`、PowerShell が `.ps1`。
- **共通UIルール**：スクロールはなるべく減らし主要コンテンツと操作を一画面に収めること、文字の切れ・はみ出し・実質縦書き崩れを作らないこと（375px 幅を含む）、免責・説明のような恒常文は画面の下の方に置くこと。

## 3. シミュレーション範囲の目安

範囲の正本は一次情報とする。cmd は Microsoft Learn の Windows コマンドリファレンス、PowerShell は Microsoft Learn の PowerShell ドキュメント。ここに挙げた範囲を超える実装をしてよいが、挙げた範囲は原則として対応し、それ以外は §1-2 の正直な未対応とすること。対応範囲の最終的な線引きは CODEX-R6.md と DEVELOPMENT.md に明記すること。

### 3.1 コマンドプロンプト（cmd）

仮想ファイルシステム（以下「仮想FS」）は、固定のサンプルツリー（現在フォルダとその配下のフォルダ・ファイル数件）をモデルとし、画面・最終状態で学習者が確認できること。

- `echo`（文の出力、`echo.` の空行、`@echo off`／`echo off` の扱い）
- `set`（文字列代入、`set /a` の算術、環境変数の一覧表示としての素の `set` は最終状態で代替してよい）
- 変数展開：`%VAR%` 展開、未定義変数の扱い、遅延展開の基礎（`setlocal EnableDelayedExpansion` と `!VAR!`、ループ内での違いが分かること）、`%ERRORLEVEL%`、`%CD%`、部分文字列・置換などの展開修飾は任意（対応する場合は宣言に明記）
- `if`：数値・文字列の比較（`==`、`EQU`／`NEQ`／`LSS`／`LEQ`／`GTR`／`GEQ`）、`if exist`（仮想FSで判定）、`if errorlevel`、`else`、括弧ブロックと1行形
- `for`：基本形（リスト列挙、仮想FSのファイル集合 `*.txt` 等へのマッチ）、`for /L`（数値範囲）。ループ変数 `%%i` の展開
- `goto` とラベル（`:label`）、スクリプト末尾への到達
- `call`（ラベル呼び出しと別バッチの代用としての同一ファイル内サブルーチン）と引数 `%1`〜`%9`、`%~1` 等の基本形、`shift` は任意
- `rem`（コメント）
- `pause`：入力モデルで表現する（キー入力待ちでパスを分岐させず、入力があったものとして読み進める。表示は実cmdの「続行するには何かキーを押してください . . .」に合わせる）
- 仮想FSの操作：`cd`／`chdir`（現在フォルダの移動。存在しないフォルダはエラーとして停止）、`dir`（仮想FSの一覧出力）、`type`（仮想ファイルの内容の出力。内容はサンプルツリー側に持たせる）、`md`／`mkdir`、`rd`／`rmdir`、`del`／`erase`、`ren`／`rename`、`copy`、`move`（すべて仮想FSの中だけ。実ファイルには一切触れない）
- リダイレクトとパイプ：`>`／`>>`（仮想ファイルへの書き込み・追記）、`2>` は任意、`|`（前段の標準出力を次段の入力にする基本形。対応は宣言したコマンド同士の範囲）
- `exit`／`exit /b`（終了コードの設定を含む）、`cls`（出力のクリアとして扱うかどうかを宣言に明記）
- 終了コードと `ERRORLEVEL` の更新規則：成功で0、失敗で1を基本とし、コマンドごとに実cmdの規則と矛盾させない。実環境でしか決まらない成否は捏造せず入力モデルにする
- 文字コード・ロケール依存の表示（日本語ファイル名の化け等）は扱わない

### 3.2 PowerShell

仮想FSは cmd と同じサンプルツリーの考え方で、PowerShell 側の現在フォルダと連動させる。

- 出力：`Write-Output`（パイプラインへ流す）、`Write-Host`（画面表示のみ）の違いをシミュレーションと解説の両方で区別する。暗黙の出力（式の値がそのまま出力される規則）も扱う
- 変数と型の基本：`$x = 値`、数値・文字列・真偽値、配列 `@(...)`、ハッシュテーブル `@{...}` とキーアクセス、`$true`／`$false`／`$null`、自動変数 `$_`／`$PSItem`（パイプライン内）、`$LASTEXITCODE` と `$?` は扱う範囲を宣言に明記
- 文字列：二重引用符での変数展開と部分式 `$(...)`、単一引用符では展開しないこと、エスケープ（バッククォート）の基本、書式演算子 `-f` は任意
- パイプライン（最重要）：オブジェクトが流れるモデルを実装する。対象コマンドレットは `Get-ChildItem`（仮想FS）、`Where-Object`、`ForEach-Object`、`Select-Object`（プロパティ選択と `-First` 等の基本）、`Sort-Object`、`Measure-Object` の基本形。スクリプトブロック `{ ... }` の基本形（比較演算子 `-eq`／`-ne`／`-gt`／`-ge`／`-lt`／`-le`／`-like`／`-match` を含む）。オブジェクトの表示はプロパティを持つ形（表形式の近似でよい）とし、生の内部表現を出さない
- 制御構文：`if`／`elseif`／`else`、`foreach`、`for`、`while`、`do-while` の基本、`switch` の基本形。`break`／`continue`
- 関数：`function` の定義と呼び出し、`param(...)` の基本、戻り値は「出力されたオブジェクトが返る」という PowerShell の規則どおりに扱う
- ファイル系コマンドレット：`Set-Location`／`Get-Location`、`Get-Content`、`Set-Content`／`Add-Content`、`New-Item`、`Remove-Item`、`Rename-Item`、`Copy-Item`、`Move-Item`、`Test-Path`（すべて仮想FSの中だけ）
- 入力：`Read-Host` は入力モデルで表現する
- エラー：存在しないパス等はエラーとして停止し、理由を示す。終了コードではなくエラーとして扱う PowerShell の基本に合わせる

## 4. 実装の進め方

- 順序は cmd → PowerShell の順に1種類ずつ完成させる（基盤の共通化が見えた時点で共通化してよいが、既存13種類の挙動を変えないこと）。
- 各種類ごとに：定義データ → シミュレータ → テンプレート／リファレンス／用語 → テスト の順で進め、種類の途中で節目を切らない。
- 既存テストを壊さないこと。新規テストを種類ごとに書き、全件の実行結果（件数と成否）を CODEX-R6.md に数値で示すこと。
- precache の再生成は最後に行い、`node scripts/precache.mjs --check` を通してから配信すること。

## 5. 検証

- 一次情報（Microsoft Learn の Windows コマンドリファレンス／PowerShell ドキュメント）との照合を種類ごとに実施し、根拠にしたページの URL を CODEX-R6.md に挙げること。
- 対応／未対応の最終的な線引きは、実装・DEVELOPMENT.md・CODEX-R6.md の3者で一致させること。
- 実ブラウザでの表示確認（375px 幅・オフライン再訪を含む）は Muse 側の監査で行う。Codex 側は単体検証まででよいが、可能な範囲で確認した結果は報告すること。

## 6. 監査への協力

- 配信後、Muse 側が角度カタログによる全角度監査を行う。指摘は台帳（RG）形式で渡すので、各指摘を一次情報で裁定し、対応する場合は修正、しない場合は理由を添えて報告すること。

## 7. 配信ルール

- 配信は節目の一括のみ：書き込みは push-files 1回（全ファイル）を基本とし、必要な場合のみ PR 作成1回・マージ1回を追加する。付随書き込み（PR本文・タイトルの編集、状態変更、余分なブランチ操作、コメント連投）はしない。
- 報告には「使った書き込みコール数：N件」を必ず明記すること。
- `PROGRESS.md` の更新は節目コミットに同梱すること（単独 push 禁止）。
- 2種類の完了後は待機すること。次の監査・修正は Muse 側で行い、その後に Codex へ一周監査（報告のみ）を依頼する予定である。
