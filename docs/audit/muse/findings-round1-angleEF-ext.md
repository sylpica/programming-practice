## 作業2：角度F（保存データ保全）の実地確認

### 実装の読み取り（前提）

保存は `js/app.js` 冒頭に集約されている。

- 現行キー `programming-practice-v3`：読み込み時に JSON パース＋形状検証（オブジェクトであり、`drafts` が配列でないオブジェクト）を行い、不正なら生文字列を `programming-practice-recovery-v3` へ退避して空の下書きで開始する（app.js:11-35）。
- 旧キー移行：v3 の下書きが空の場合に限り `macro-practice-v2` を読み、`drafts` と `active` を引き継ぐ（app.js:38-48）。さらに `drafts.vba` が無ければ `vba-practice-v1` の内容を VBA の下書きとして取り込む（app.js:50-56）。移行元キーは削除されない。
- 保存 `save()`（app.js:119-156）は種類別に `drafts[active.id]` を分離して `{active, drafts}` を v3 へ書き込む。書き込み失敗時は `#storageNotice` を表示する。

### 実地結果（ブラウザ、19項目中17合格）

| 項目 | 内容 | 結果 |
|------|------|------|
| F-A1a〜e | v3 = 壊れた JSON 文字列で起動 | 起動OK／生データが recovery へ退避／退避後は新規入力が v3 に正常保存される／保存保護通知は出ない／ページエラーなし |
| F-A2 | v3 = `{"drafts":42}`（型違い） | 起動OK、recovery へ退避 |
| F-A3 | v3 = `[1,2,3]`（配列） | 起動OK、recovery へ退避 |
| F-B1a〜d | 旧キー `macro-practice-v2` のみ（python の下書き＋active=python） | 種類と下書きが復元される／移行元キーは削除されない／復元内容が v3 へ保存される／エラーなし |
| F-B2 | 旧キー `vba-practice-v1` のみ | VBA の下書きが復元される |
| F-B3 | v3 破損＋v2 有効の併存 | 破損 v3 は recovery へ退避しつつ、v2 から移行・復元される |
| F-C1a〜d | 種類別下書きの保持 | python と javascript に別々のコードを入力→種類切替で保持→ページ再読み込み後も保持→v3 内で種類別に分離保存されていることを確認 |
| F-X1 | 旧キー v2 の `drafts` が**文字列** | **不合格**（欠陥 F-D1） |
| F-X2 | 旧キー v2 の `drafts` が**配列** | **不合格**（欠陥 F-D2） |

### 欠陥（角度F）

- **F-D1（P2）旧キー移行分岐に形状検証がなく、破損した旧データで保存機能が全面喪失する**
  - 再現：`macro-practice-v2` に `{"drafts":"oops-string"}` を置いて起動すると、起動時と入力のたびに `TypeError: Cannot create property 'vba' on string 'oops-string'` が発生し（実測2回）、v3 への保存は一切行われない。画面上は起動して実行もできるため、利用者は保存が壊れていることに気づかず、入力したコードは再読み込みで全て失われる。保存失敗時に出るはずの `#storageNotice` も、例外が `save()` の try の外（app.js:135 の代入）で発生するため表示されない。
  - 根因：v3 読み込み分岐（app.js:15-22）は形状検証＋recovery 退避を行うのに対し、v2 移行分岐（app.js:40-48）は `drafts = interim.drafts || {}` と無検証で取り込む非対称さ。移行分岐でも同等の検証（不正なら recovery 退避して空で開始）を行えば解消する。
  - 発生条件は旧キーの保存データが破損・改変されている場合に限られるが、「破損した保存データでも起動でき、作業を継続できる」という角度Fの要件そのものへの違反であり、v3 側では同種の破損を正しく処理できている。
- **F-D2（P3）旧キー移行分岐の型異常（配列）で下書きが黙って失われる**
  - 再現：`macro-practice-v2` に `{"drafts":[1,2]}` を置いて起動し、コードを入力すると、例外は出ないが入力内容は v3 に残らない（配列への名前付きプロパティ代入が `JSON.stringify` で脱落し、v3 は `{"active":"vba","drafts":[1,2]}` と保存される。実測）。次回起動時にはその v3 自体が自らの形状検証で「破損」扱いとなり recovery へ退避され、入力したコードは完全に失われる（二次影響まで実測で確認）。
  - 根因・修正見込みは F-D1 と同じ（移行分岐の検証欠如）。F-D1 の修正で同時に解消する見込み。

### 未実施・範囲外

- localStorage 自体が例外を投げる環境（プライベートモード等での getItem/setItem 失敗、`storageBlocked` 経路）は、ブラウザ実地では再現手段がなく未実施（コード読み取りのみ：外側 catch で `storageBlocked` を立て、保存時に通知を出す設計であることは確認）。
- Service Worker 更新をまたいだ下書き保持は角度E（オフライン／PWA）の領域として本作業では未実施（本検証では SW をブロックした）。
- ファイル取り込み経由で復元される下書きの保全は未実施（角度C/D の領域）。
