## §4 検証結果

- 全テスト：**4,597件**（ベースライン4,304＋新規回帰286件＋データ駆動の自動増減の純増7件）、最終実行で**全件合格**。パスキャップ系の時間予算テスト（tests/engine.test.js、cmd.test.js、powershell.test.js）は当VMのCPUスロットリングで間欠失敗する既知の環境要因であり、失敗時は単体再実行とベースツリー対照で切り分け、回帰と混同していない。
- 統合後に判明した回帰1件（RG-56）：既存テスト「RG-56 代入文経由の深い式でも深さが原因として表示される」の内包表記形が無エラーで完走するようになった。当初は環境間欠とみなされたが、コーディネーターのベースツリー対照（pristine では合格・統合ツリーでは恒常失敗）で実回帰と確定した。根本原因は、深さ上限が明示チェックではなく再帰下降パーサのスタック溢れ（RangeError）の変換だけに依存する非決定的な仕組みで、R7-151 の analyzeCode 新設がパーサ実行回数を増やして最適化を進め、溢れが起きなくなったこと（pristine でもパーサを温めると再現する潜在欠陥）。式の再帰が必ず通る parseOr に決定的な深さカウンタ（上限100）を新設して根治し、全式位置（内包表記の反復対象・条件・要素、ジェネレータ式を含む）が同じ検査を通るようにした。回帰テスト3件を追加。詳細は `~/workspace/programming-practice-audit/findings-fix13-rg56fix.md`。
- native-audit：exit 0、**all_passed、356チェック**（C# 59/59 を `~/dotnet` で実走、Python 実走217件）。なお当VMの exec 環境では標準入力を開いたまま渡すと、従前からある stdin を読む実例が3秒制限でタイムアウトする（pristine な HEAD e3c3348 でも同一に再現する環境要因で、本バッチの変更とは無関係）。標準入力を閉じて実行した結果が上記の全合格である。
- precache：最終ファイル変更の直後に `node scripts/precache.mjs` で再生成し、`--check` の通過を確認した。
- 独立検証（統合ツリーの別コピー `work/verify-b13/`、3チーム・独自プローブ＋変形／兄弟形。詳細は `~/workspace/programming-practice-audit/verification-batch13.md`）：対象215件のうち初回で **214件解消確認・差し戻し1件**（R7-27 の兄弟形 `data.frame(1 + 1)` の列名）。差し戻しは差し戻し修正チームが deparse 再構成を R 公式 deparse.c の空白規則へ一致させて是正し、コーディネーターの再プローブで解消を確認した。最終の差し戻し残りは **0件**。
