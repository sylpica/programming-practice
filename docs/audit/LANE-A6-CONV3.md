## 2. RG-676 修正の統合後成立確認

一次実測（gcc 13.3.0 -std=c11／g++ 13.3.0）：C の NULL 等価6形 `NULL==0, NULL!=0, p==0, 0==NULL, strchr戻り==0, 代入形` は **1 0 1 1 1 1**。g++ の nullptr 5形は 1 0 1 1 1。

アプリ側（nullcheck N-01〜18＋nullcheck2 X-01〜17／CPP-01〜05）で再実測し、次を確認した：

- 6形全てが gcc と一致する（第2回で JS 緩い等価に落ちて誤値だった形が解消）。
- 境界形（関係演算・真理値文脈・`NULL==1` 等）および従来一致していた表面は不変。
- 残る停止は修正前後不変の正直な停止のみ：`NULL + 0` の CompileError、`printf("%d", NULL)` の UB 名指し停止、`(long)NULL` の名指し停止。
- **C++ への波及なし**：nullptr 比較は不変。新規スクリプト nullcheck3 で `std::cout << std::NULL;` と `std::NULL == 0` の両方が「std::NULL は未対応です」で名指し停止することを確認し、バッチ18の A8 是正（std::NULL 名指し停止）が無傷であることを確認した。
- **C# 経路は不変**：バッテリー CS-01〜10 は統合前（4f41e11）・統合後（f486c8b）でバイト同一。統合前後で差分が出たのは C++ 側 CPP-S3 の1行のみで、これは RG-676 修正そのものである。CS-04〜07 の nullable／object 名指し停止、CS-08 `null == 0`→False は両ビルド共通の従来挙動。

補足（第2回報告書の文面訂正）：`NULL == 0.0` は glibc の C では（void* NULL のため）警告ではなくハードエラーである。第2回報告書の「gcc 警告つき」という表現は緩かった。当該形は6形に含まれず、アプリが 1 を返す点の扱いは第2回の記録どおり維持する（欠陥には数えない）。

## 6. ゲート（全スイート 7,548件）

自ツリー（正本 f486c8b とバイト同一）での実測：

- UTC 全体実行：7,548件中 7,544 通過・4 失敗。
- JST 全体実行：7,548件中 7,547 通過・1 失敗。
- precache --check：合格（exit=0）。

失敗は両環境とも次のタイミング系4件の部分集合のみで、全て**環境フレークと裁定**する（テスト期待値は変更していない）：

1. `audit nested macro cross product reports the 2000 path cap`（tests/audit.test.js:87）
2. `cmd path cap is explicit and never exceeds the common 2000 paths`（tests/cmd.test.js:134）
3. `default maximum is exactly 2000 paths`（tests/engine.test.js:364、JST では 1024 !== 2000＝実時間予算で列挙が途中で切れた形）
4. `powershell path explosion emits a notice at the shared 2000 path cap`（tests/powershell.test.js:102）

裁定の根拠：

- **ベース対照**：統合前ビルド 4f41e11（git archive 展開）でも、同じ負荷条件で同じ4件が同じ署名（約10.0〜10.8秒の実時間打ち切り／CFn は約2.5秒で探索上限停止）で失敗した。バッチ19起因ではない。
- **同一ツリーでの反転**：再起動後の単体再実行で、テスト1は「失敗→通過→通過」と連続実行で結果が反転し、テスト3・4も実行ごとに通過／失敗が入れ替わった。決定的な欠陥ではあり得ない。
- **機構の特定**：テスト1の停止理由「変換の探索上限で停止しました」は `js/types/cloudformation/index.js` の `++ops > 10000 || performance.now() - start > 1200`（1,200ms の実時間予算）に由来する。テスト2〜4も経路列挙の実時間予算（約10秒）で打ち切られる形であり、いずれも CPU スロットリング下で実時間予算が先に尽きる既知の型である。バッチ19はこれらのコード経路（cloudformation／cmd／engine／powershell）に一切触れていない。
- **静穏条件での基準線**：親が同一ツリー f486c8b を静穏条件で独立実測し、UTC／JST 両環境 7,548件全通過を確認済みであることと整合する。

なお JST 初回実行は VM 再起動に伴う SIGTERM で途中終了した（テスト失敗ではない）ため再実行し、上記の完走結果を得た。
