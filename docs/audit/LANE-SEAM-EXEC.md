## 0. 実施体制と障害の記録

- 当初4チーム体制（Node 機械照合／実ブラウザ1 モード・保存・競合／実ブラウザ2 遅延ロード・SW／実ブラウザ3 種別・表示）で開始したが、インフラ障害（DB プールタイムアウト等）により Node 照合チームとブラウザチーム1が開始直後にエラー終了し、再起動も2回失敗した。ブラウザチーム3は起動待ち（pending_init）のまま1時間以上進まず、終了させた。

(a) **getResult のタイトル形と名前付き結果表の不整合**。再現（高度合成状態）：`Table.create("Data"); Table.set("X", 0, 42);` の後に `getResult("X", 0, "Data")` を実行すると「getResult で指定された結果表「Data」が見つかりません」で停止する。一方 `Table.get("X", 0)` は同じ表から 42 を正しく返す。根本原因：基礎エンジンの結果表は `S.results`（タイトル "Results" の単一表）だけであり、高度側 Table.* の名前付き表は別ストア `S.__tables` に保持される。基礎 getResult は `S.__tables` を参照しない。エラーメッセージの理由文「このモデルにある結果表は「Results」だけです」は簡易モードでは正しいが、高度モードでは事実と異なる（表は存在する）ため、誤った停止理由の表示にあたる。簡易モードでは Table.create 自体が未対応で停止するので矛盾は表面化しない。対照確認：既定表への `setResult`／`getResult`（タイトル形 "Results" 含む）は基礎のみで正常動作する。修正方向の私案：基礎 getResult がタイトル形で `S.__tables` に存在する表を参照できるようにするか、最低限、高度有効化時は理由文を実態に合わせる。開示：この制約を述べる項目文・注記は見当たらず、未開示の不整合として扱うべきである。

(b) **Color.getLut が設定した LUT を返さない**。再現（高度合成状態）：`Color.setLut(r, g, b)`（r[100]=7）後に `Color.getLut(r3, g3, b3)` を実行すると r3[100] は 100（恒等 LUT）になる。一方、無修飾の `getLut` は高度レジストリ側に LUT 対応の実装があり、setLut で保持した値 7 を正しく返す。根本原因：高度レジストリ（engine-advanced-state.js）は `"getLut"` のみを上書きし、`"Color.getLut"` は基礎ハンドラ（engine.js、常に恒等 LUT を書き込む）に落ちる。簡易モードでは setLut 自体が未対応のため、恒等 LUT が唯一の LUT であり矛盾は表面化しない。高度モード内でのみ、setLut／getLut の組と Color.setLut／Color.getLut の組で結果が食い違う。

### 5-3. B7 標準ライブラリ項目のコードからのリンク到達性（A7 班／親工程への材料）

B7 項目は実行意味論は正しい（例：`import math` 後の `math.sqrt(4)` は 2.0、`math.sqrt(81)` は 9.0 と表示される）が、コードから項目へのリンク（scan／トレース参照）が付かない。層化サンプル実測（example を持つ B7 項目 5,664 件から、モジュール先頭セグメントごとに最大3件、122 モジュール・365 件）：**scan 到達 67/365、トレース到達 33/365、どちらか到達 67/365**。未達には対応（supported）の通常関数も多数含まれる（math.factorial、math.gcd、copy.copy、fnmatch.filter、shlex.split、glob.escape 等）。対照的に os.getcwd は scan で解決される。切り分け所見：実行レジストリは B7 フックで拡張されているが、scan／名前解決側のモジュール表は拡張されていない種別がある、という継ぎ目である。定数・クラス・例外等の項目は性質上コード形の到達を意図しないものも混ざるため、未達 298 件全てが欠陥とは言えないが、supported のモジュール関数については項目の example 自身でも到達しない点で SP-36 と同型の問題である。

### 5-4. V-18 C++ 名前空間スコープ名の scan 解決（A8 班／親工程への材料）

高度項目は `std::acos` のように `std::` 付きの名前で登録されているが、コード scan は修飾名を解決しない。実測：`std::vector<int> v;` → ["int"]、`std::cout << 1;` → ["cout"]（無修飾の基礎項目へ）、`std::sort(v.begin(), v.end());` → []。簡易・高度で同一。検索ボックス経由の到達（SP-42）は成立しているため、問題はコードビュー側の名前解決に限られる。

### 5-5. complex.conjugate の scan 到達性の後退（A6 班／親工程への材料）

統合第1弾時点のスナップショット（49034f2）へ同一プローブを適用した対照実測で、scan 到達は 223/291（申告と一致）であり、`complex.conjugate` は到達側に含まれることを確認した。現行ツリーでは 222/291 で、同項目が未達側に移っている。現行での未達の形：`print((3+4j).conjugate())` の scan は ["print", "object.__add__"] となり、BinOp の結果型（complex）が推論されず属性呼び出しが解決されない。第1弾と現行の間に Python エンジンへ触れた統合は第2弾の三方向マージ（RG-624）のみであり、同マージに伴う回帰と判定する。トレース到達の総数も対照実測で 218→217 と同方向に動いている（第1弾報告書の 215 とは測定法の差があるため、総数の厳密な対応は scan 側を正とする）。

### 5-6. 高度モードで基礎の scan 解決が失われるケース（A6／A7 班／親工程への材料）

SP-09 の機械比較から切り分けた。基礎カタログの example で、簡易状態では解決される scan が高度状態では失われるケースを確認した（いずれも合成カタログへの差し替えだけで再現し、エンジンフックの適用有無に依存しない。実行結果には影響しない）。

- 基礎項目 math の example `import math\nprint(math.sqrt(81))`：簡易 scan は ["print", "math.sqrt"]、高度 scan は ["print"]。
- 基礎項目 numpy.array の example：簡易 ["print", "sum", "numpy.array"] → 高度 ["print", "sum"]。
- 基礎項目 list.copy の example（`ys = xs.copy()` 後に `ys.append(3)`）：簡易 ["print", "list.copy", "list.append"] → 高度 ["print", "list.copy"]。なお `xs.append(3)` の直接形は高度でも ["print", "list.append"] と解決される。
- 基礎項目 set.copy の example も同型（set.add が喪失）。

候補となる機構（未検証の仮説として記録する）：合成カタログでは同名メソッドを持つ項目が大量に増えるため、メソッド名だけに頼る曖昧な解決が抑制される、あるいは基礎項目が宣言していた scan トークン（math.sqrt 等）が合成後の索引で stdlib 項目側に影になる、等。根本原因の特定と処置は Python の scan／名前解決を所有する A6／A7 班の範囲とする。本件は §5-3（stdlib 項目への到達不可）と表裏の関係にあり、高度モードのコードビュー連携が簡易モードより弱くなる表面がある、という点が学習者影響である。
