## 1. 実装方式（指示1：CP932対応）

取り込みの読み取り経路は従来から単一である：ドラッグ＆ドロップとインポートボタンの両方が `js/app.js` の `importFile` → `js/import.js` の `decodeFile(buffer, name, extensions)` を通る。モード（簡易／高度）で分岐はなく、種別ごとの差は `extensions`（受付拡張子）だけである。本対応はこの `decodeFile` のデコード段だけを変更した（`app.js` は無変更）。

変更後の判定順序：

1. 拡張子チェック（従来どおり、種別ごとの一覧に一致しない場合は明示エラー）
2. バイト上限 `MAX_FILE_BYTES`（R7-130 の導出値、従来どおり）
3. BOM付き UTF-16LE／BE（従来どおり fatal デコード）
4. NUL バイトを含む場合はバイナリとして拒否（従来どおり）
5. UTF-8 として fatal デコードを試行（BOM付き UTF-8 はここで読まれ、 BOM は従来どおり除去）
6. 失敗したら CP932 経路：`TextDecoder('shift_jis', {fatal:true})`。これも失敗した場合に限り、下記「救済デコード」で再試行する
7. 制御文字チェック（R7-131：VT／FF は受理、その他は拒否）、文字数上限 100,000（デコード後に検査、従来どおり）、CRLF 正規化（従来どおり）

判定表示ラベルは、CP932 経路で読めた場合に確認ダイアログ・取り込み完了表示へ `CP932（Shift_JIS）` と出すよう変更した（従来は `Shift_JIS`）。判定失敗時のエラーメッセージも `CP932（Shift_JIS）を使用してください` に更新した。

### 1.1 ブラウザの 'shift_jis' が CP932 をどこまでカバーするかの実測

実装に先立ち、実ブラウザ（Chrome for Testing、chromium-1255）の `TextDecoder('shift_jis')` と Python の `cp932` コーデック（Windows CP932 と同一の写像を正とした）を全域照合した。

- 対象：単独バイト 256 通り＋2バイト組 11,280 通り（リード 0x81–0x9F／0xE0–0xFC × トレイル 0x40–0x7E／0x80–0xFC）＝計 11,536 バイト列
- **写像が食い違う組は 0 件**。有名な差異行も全て CP932 側に一致した：0x8160 → U+FF5E（全角チルダ）、0x815C → U+2015、0x8161 → U+2225、0x817C → U+FF0D、0x8191 → U+FFE0、0x8192 → U+FFE1、0x81CA → U+FFE2
- NEC 拡張・IBM 拡張（リード 0xFA／0xFB の全 188 組ずつ、0xFC は 0xFC40–0xFC4B の 12 組）も全て一致。ユーザー定義文字（外字、リード 0xF0／0xF5／0xF9 で各 188 組）も私用領域 U+E000–U+E757 へ一致
- 0x5C → U+005C（バックスラッシュのまま）、0x7E → U+007E、半角カタカナ 0xA1–0xDF → U+FF61–U+FF9F も一致
- **ブラウザが受理しないのは、CP932 で私用領域に写る単独バイト 4 つだけ**：0xA0 → U+F8F0、0xFD → U+F8F1、0xFE → U+F8F2、0xFF → U+F8F3。これらを含むファイルは、従来実装（fatal デコードのみ）では丸ごと取り込み拒否になっていた

### 1.2 救済デコード

上記 4 バイトを含む CP932 ファイルを取り込めるよう、fatal デコード失敗時に限り CP932 のバイト構造で走査する救済経路を `js/import.js` に実装した。

- 2バイト文字の第2バイト位置にある 0xA0 等は通常の組として扱う（位置ベースの走査のため誤認しない）
- 標準部分は区間ごとにまとめて fatal デコードし直すため、構造的に不正な並び（末尾のリードバイト単独、不正な第2バイト、未割当の組）は従来どおり判定エラーになる（単体テストで確認）
- 4 バイト以外の写像は一切自作していない（全て TextDecoder の結果を用いる）

### 1.3 境界の確認（単体テスト＋既存テスト）

- UTF-8 BOM付き：BOM を除去して取り込み（ラベルは UTF-8）
- ASCII のみ：UTF-8 として取り込み（内容は CP932 でも同一）
- 空ファイル：空テキストとして取り込み
- CP932 の CRLF：`\n` に正規化
- CP932 で VT／FF を含むソース：受理（R7-131 の回帰防止を Shift_JIS 経路でも単体テスト化）
- CP932 の 100,000 文字ちょうど：受理。100,001 文字：拒否（上限はデコード後の文字数で従来どおり検査）
- 自アプリ保存ファイル（BOM付き UTF-8・上限内）の再取り込み保証（R7-130）：既存テストで継続確認
- 判定不能なバイト列（末尾リードバイト単独 0x82、不正トレイル 0x82 0x20、未割当組 0xFC 0x50）：拒否

## 2. 拡張子の洗い出しと実測（指示2）

受付拡張子は種別定義の `extensions` が正本であり、ファイル選択ダイアログの `accept` 属性も同じ一覧から生成される（`js/app.js`）。今回、実態に合わせて次の拡張子を追加した（いずれも保存時の既定拡張子＝一覧の先頭は不変）。

| 種別 | 追加した拡張子 | 根拠 |
|---|---|---|
| Excel VBA | .cls / .frm / .vba | .cls（クラスモジュール）と .frm（フォーム）は VBA エディタ公式のエクスポート形式。.vba は VBA ソースの事実上の標準拡張子 |
| C++ | .h | C と共用されるヘッダの代表的拡張子（.hpp は既存） |
| PowerShell | .psm1 | モジュールファイルの公式拡張子（スクリプト本体と同じ言語） |
| JavaScript | .mjs / .cjs | Node.js 公式のモジュール／CommonJS 拡張子 |
| Python | .pyw | Windows 向けウィンドウなし実行スクリプトの公式拡張子（言語は同一） |

検討したが採用しなかったもの：PowerShell .psd1（スクリプトではなくデータファイル形式）、Python .pyi（宣言のみのスタブで実行コードではない）、C# .csx（特定スクリプトホスト専用）、R .Rmd（Markdown 文書）、CloudFormation .template（旧式で少数派）、C++ .hh／.hxx（少数派）、cmd .btm（サードパーティ製シェル専用）。

### 2.2 自然なコードファイル拡張子がない種別の扱い

- **Power Automate（デスクトップ）**：フローの実体は JSON であり、単独のコードファイル拡張子は存在しない。現行の .json／.txt を「拡張子なし種別としての扱い」とする（変更なし）
- **Power Automate（クラウド）の WDL 式**：式そのものにファイル形式はなく、フロー定義は JSON。現行の .txt／.json が実態に即した扱い（変更なし）
- **Power Apps（Power Fx）**：式はアプリのソース（YAML）内に埋め込まれるもので、単独の式ファイル拡張子は標準化されていない。現行の .fx／.txt／.json を実態として維持（変更なし）
- **UI.Vision RPA**：マクロの実体が JSON ファイルそのものであり、.json が正規の取り込み形式。.txt を併せて受理（変更なし）
- **IPA擬似言語**：試験用の記述形式でありファイル拡張子の慣習がない。.txt のみが実態（変更なし）

### 2.3 種別に合わない拡張子を落とした場合の振る舞い

現行どおりで、方針として明記する：**表示しない**。理由は、他種別のコードを現在の種別のエディタへ黙って流し込むと、実行モデル（モデルシートや入力前提）が種別と食い違い、誤った学習結果を招くため。振る舞いは明示的で、全種別で実測した：

- アラート「.bas / .cls / … ファイルを選んでください。」のように、その種別で受理できる拡張子の一覧を提示して拒否する
- エディタの内容は変更されない
- ファイル選択ダイアログでも同じ一覧が `accept` 属性に設定される

## 3. CP932 検証の実測記録（実ブラウザ）

環境：Playwright＋Chrome for Testing（`tools/browsers/chromium-1255/chrome-linux/chrome`）、対象ツリーをローカル HTTP で配信し、実物のドラッグ＆ドロップ（DataTransfer 経由）とファイル選択の両経路を操作した。検証項目は合計 **104 件、全件 OK**。

内訳：

- CP932 ドラッグ（簡易モード 16 種別）：日本語コメント入りの CP932 ファイル（各種別の代表拡張子）が文字化けなくエディタに表示され、完了表示に「CP932」が含まれることを全種別で確認。Python と cmd は CRLF の CP932 ファイルで改行正規化も確認
- 拡張子スイープ：17 種別×全受付拡張子（計 49 件）のドラッグ表示、全種別で他種別拡張子（.exe）の明示拒否＋エディタ不変を確認
- インポートボタン経路：Python／VBA／PowerShell の CP932 ファイルで表示を確認
- 特殊ケース（Python）：NEC 拡張＋ユーザー定義文字（外字 U+E000）入り CP932、単独 0xA0 を含む CP932（救済経路）の両方が正しく表示されることを確認
- 高度モード：Power Automate（クラウド）の CP932 ドラッグ＋全拡張子、Python の CP932 ドラッグを高度モードでも確認（モードで取り込み挙動が変わらないことの実測）

単体テスト：`tests/muse-cp932-import.test.js` を新規追加（13 件）。全スイート **5,408 件全合格**（ベースライン 5,395＋13）。パス上限系タイミングテストのフレークは今回発生しなかった。precache は再生成し `--check` 合格。

## 4. 残存・未確認

- **EUC-JP は対象外（未対応）**：自動判定は行わない。EUC-JP のファイルは判定エラーになるか、バイト並びによっては CP932 として誤って読まれる可能性がある（誤読の範囲は未実測＝未確認）。必要になれば別途対応する
- BOM のない UTF-16／UTF-32 は判定しない（従来どおり、対象外）
- バイト列として偶然 UTF-8 としても成立する CP932 ファイルは UTF-8 として読まれる（理論上の境界。日本語を含む CP932 テキストが全体として UTF-8 妥当になることは実質ない）
- 全域照合は Chromium 系で実施。Node の TextDecoder は単体テストで使う全ベクタ（NEC 拡張・外字・救済 4 バイトの fatal 可否を含む）で Chromium と一致した。iOS Safari 等の他エンジンでの TextDecoder の CP932 写像は未実測（WHATWG 仕様準拠が前提）
- 救済経路で私用領域（U+F8F0–U+F8F3）に写した文字は、元の環境の外字フォント等がなければ画面上は代替表示になりうる。これは CP932 の仕様どおりの写像であり、文字化け（別字への化け）ではない
