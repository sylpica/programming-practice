## 2. 機構契約（advanced-interface.md）への整合

整合済み：
- (a) 高度項目は `status` 一本化（`supported` 併記なし。第3章3.2）
- (b) 基礎項目の複製・素の名前重複なし。基礎項目の変更は行わず `referenceOverrides` は空（第5章(b)、第6章）
- (c) ファイル配置と形式：`advanced-manifest.js`／`reference-advanced.js`／`templates-advanced.js`／`glossary-advanced.js`／`advanced-engine.js`（第5章）。項目形状は第4章の正規形（追加フィールドなし）
- (d) テンプレートは未対応項目に黙って依存しない（第9章、チェックリスト (f)）。高度テンプレート6件は基礎モデルの defaults で trace が完結する
- (e) モードで実行結果は変えない（単一エンジン。モード分岐はエンジン内に存在しない。第1章）
- (f) 擬似言語は差分対象外（B1 の範囲外として不変）

差異（統合時に引き継ぐ事項）：
- **D-1 エンジン合成の形**：契約 第5章(e) は `applyAdvancedEngine` フック経由のみを定めるが、B1 のエンジン拡張は基礎エンジン（index.js／engine.js）からテーブルを静的に参照する形で合成した。`applyAdvancedEngine(definition, merged)` は advanced-engine.js に実装済みで、同じテーブルを `definition.advancedEngine` へ登録する（機構側がフック経由で受け取る初例として提示する。契約の未決・留保 R-3 への B1 側の落とし込み）。モードによる条件分岐は存在せず、第1章の不変条件（単一エンジン・結果不変）は満たす。
- **D-2 precache の範囲**：契約 第7章のパターンは `advanced-engine.js`／`advanced-manifest.js` も除外するが、B1 では静的合成のため両ファイルを precache に含めている（除外したのはデータ6ファイルのみ）。統合時にフック経由の遅延ロードへ移す場合は、precache パターンを契約どおりに広げ、B1 エンジンの静的参照を外す作業が併せて必要になる。
- **D-3 scan の名前解決**：現行ビルドでは高度名も基礎 scan が静的に解決する。統合時は、名前解決の対象を有効なカタログ（簡易＝基礎、高度＝合成後）に連動させる必要がある（契約 第1章1-2、第8章8.3）。高度名のテーブルは `advancedEngine` 経由で機構側から参照できる。

## 4. コーディネーター裁定

- **verifyAlert／verifyConfirmation／verifyPrompt**：公式ドキュメントが「Ui.Vision 本体は提供していない」と明記する3件は、契約の対応リストに従い対応として収載し、各項目の caution に公式明記と「モデルでは学習用に verify の意味論で扱う」旨を明示した（虚偽の説明にはなっていない）。
- **RG-10 既存テスト（forEach）**：高度モードで forEach を実装したため、簡易モード時代の「未対応として報告される」前提のテストを新仕様（ループ実行＋End 欠落時の原因表示）に更新した。
- **round3 ブラインドフィクスチャ（executeScript）**：executeScript を部分集合で実装したため、`window` アクセスの期待を「未定義の名前：window」（部分集合内での正直な停止）に更新した（2行のみの変更）。
- **別名停止 import／route**：文脈つき見出し項目の到達性のため、実行名の停止を本体と分離して追加し、整合性テストで対応関係を固定した。

## 5. 残存・未確認（統合工程への引き継ぎ）

1. **cmd /c の入れ子で引用符を多重に含む形**：基礎パーサの構文停止になり、製品相当の引用符処理との切り分けができなかったため未確認のまま残す（単純形・単純入れ子は正常動作を実測済み）。基礎パーサ側の範囲であり、B1 の差分では扱わない。
2. **cmd /c 内の素の exit**：モデルではバッチ全体が終了する制限が残るが、リファレンス cmd 項目の caution で開示済み（B1A-05 の処置）。
3. **ブラウザ実操作系の角度（D-01／D-02 等18角度）**：モード機構未統合のため本ブロックでは対象外。統合監査で実施する。あわせて第1回監査の申し送り：advanced データは precache 外＋ランタイムキャッシュ配信のため、モードローダーのオフライン動的 import の可否は統合時に確認が必要。
4. **pushd 一覧の表示順**：保存順（古い順）で表示する。実物の表示順との厳密な一致は一次情報で確定できなかった。
5. **基礎コマンド側（index.js の store／type 等）の未確定値の扱い**：高度エンジン外の基礎層の範囲であり、本ブロックでは変更していない（簡易モード監査で確立した扱いのまま）。

## 6. 統合時の接続手順（機構コーディネーター向け）

1. 両種類の `advanced-manifest.js` が構成を宣言している。ローダーは manifest の `referenceParts`／`templatesFile`／`glossaryFile`／`engineFile` を読めばよい。
2. 合成は基礎カタログ＋ `referenceAdvanced`（overrides は空）の単純追加で足りる。名前重複・id 重複は整合性テストでゼロを固定済み。
3. エンジンは §2 の差異 D-1〜D-3 の扱いを決めてから接続する（現行の静的合成のまま取り込むか、フック経由へ移すか）。
4. 検証は `node --test tests/muse-adv-b1-*.test.js`（132件）と全量テストで再現できる。
