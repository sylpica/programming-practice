3. **括弧なし `return 1, 2;` のカンマ**：バッチ11 §5-5 から継続。
4. **変換が存在しない組合せの C# foreach の受理の緩さ**：バッチ11 §5-6 から継続し変更していない。
5. **JS 前置 `++`／`--` の全位置未対応**：既存候補。後置形とは別系統の字句・文法制約として記録する（本バッチでは不変更）。
6. **R の data.frame オブジェクトの列長不揃い**：RG-372 の入口検証は形状（オブジェクト性・列の配列性）までで、列長の一致は検証しない（裁定範囲外として記録）。
7. **R の `a::`＋改行＋名前の形**：実 R の継続規則との突合が未了のため、現行の名指しを維持した。
8. **C# Main 引数位置の属性**：既存の無検証の読み飛ばし経路で黙って読み飛ばされる（RG-365 の範囲外として記録。属性つき引数リスト自体は受理される）。
9. **C++ の既存観察3件**（文字列配列に固有ではない）：`std::string` 配列全体の `sizeof` が "nan" を返す点、参照エイリアス初期化子に配列要素を指定できない点（int 要素でも同限界）、不確定文字列（getline 由来）への文字書込みの停止文言がスカラー文字列と同一である点。
10. **RG-379 の観察 D1**：C++ の for 本体最外ブロック（括弧なし本体含む）でのループ変数再宣言は実 g++ では redeclaration エラーだがアプリは受理する。是正には共有スコープ機構への「for 本体最外」の識別追加が要るため、別台帳項目として切り分けることを提案し、本バッチでは現行挙動をテストで明示して固定した。
11. **RG-379 の観察 D2**：C／C++ の大域変数と同名を main 直下で宣言する形は実物では合法だが、アプリはパーサの入口ブロック平坦化のため同一スコープとして停止する。表明文に例外を明記済みであり虚偽表示ではない。パーサ構造の変更を伴うため別項目として記録する。
12. バッチ11 §5-3（C++ `std::string` 配列要素）と §5-4（C# `Func` ジェネリック）は、本バッチの RG-376／RG-369 で閉じた。
