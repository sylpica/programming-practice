- muse-adv-b7-g5.test.js／muse-adv-b7-u.test.js： backlog.json の候補未解決で例外になっていた各1件を理由明示スキップ化した。

## 3. グループ2：ホスト未実装機能（CI失敗5件）

tests/adv-b5-javascript.test.js の5件は、Node 24 の V8 にはあるが Node 22 の V8 にはない新機能（Math.f16round、RegExp.escape、Float16Array）を前提に「動作する」側だけを期待していた。アプリは JS-B5-09 の設計どおり「<name> は未対応です：ホストに実装がありません」と名指しで正直に停止しており、アプリ側の欠陥ではない。

是正はホスト能力での分岐である： 機能があるホストでは従来の計算結果を、ないホストでは名指し停止（カテゴリ未対応）を、それぞれアサートする。同ファイルの FIX2a JS-B5-09/10 テスト（子プロセスでホスト機能を消して停止を固定する既存テスト）と文面・正規表現の作法を揃えた。対象5箇所：

1. Math.f16round（"B5-JS Math: host-delegated functions match Node" 内。従来の複合行から f16round だけを分離し、他は不変）
2. RegExp.escape（"B5-JS RegExp construction, exec/test, flags" 内）
3. Float16Array.from／.of（FIX2a JS-B5-01。全12種の一括ループから分離）
4. Float16Array インスタンスの BYTES_PER_ELEMENT（FIX2a JS-B5-02。静的読み取りの12種一括行はアプリ自身の表で答えるためホスト非依存であり不変。インスタンス生成を含む行だけを分離）
5. Float16Array の Symbol.toStringTag（FIX2a JS-B5-03。他12値は不変、Float16Array 分だけ分離）

なお CI 失敗として挙がっていた Math.sumPrecise は、アプリが BigInt による自前実装（sumPreciseImpl）を持つため両ホストで合格しており、失敗の実物は f16round であった（§6 参照）。同ファイル内の他の ES2025 世代機能（Object.groupBy、Set 集合演算、Uint8Array Base64、JSON.rawJSON、Error.isError、Promise.try 等）は横断精査の結果、いずれもアプリ側の自前実装または名指し停止を期待する形でホスト非依存であることを確認した。

## 4. グループ3：正規表現インラインフラググループ（CI失敗1件）

tests/muse-adv-b7-g3.test.js の re.inline-flag-scoped は、Python のスコープ付きインラインフラグ `(?i:abc)d` を JS の `(?i:abc)d`（du フラグ）へ翻訳するケースである。Node 24 の V8 はこのグループを受け付けるが Node 22 の V8 は Invalid group で拒否し、アプリは PatternError で停止する（翻訳結果が不正な場合の正直な停止であり、アプリ側の欠陥ではない）。

是正： ホストが `new RegExp('(?i:abc)d', 'du')` を受け付けるかを実測で判定し、受け付けるホストでは従来の実行結果を、受け付けないホストでは PatternError による停止をアサートする分岐を、当該ケースにのみ追加した。

## 5. グループ4：NaN の符号ビット（CI失敗1件、CF-01 裁定への注記）

tests/muse-lane-a6-exec.test.js の CF-01 テストは、`printf("%d", signbit(pow(-1.0, 0.5)))` の期待値を glibc 実行時実測の '1' に固定していた。NaN の符号はホストの pow 実装に依存する（実測： glibc 実行時＝1、Node 22 の V8＝0、Node 24 の V8＝1）。アプリの pow はホストへ委譲するため、CI（Node 22）では '0' が正しい出力であり、期待値の固定が過剰適合だった。

是正： pow 行に限り、期待値をホストの `Math.pow(-1.0, 0.5)` が返す double の実際の符号ビット（DataView で抽出）から導出し、アプリの signbit 出力と一致することをアサートする形に改めた（アサーション自体は維持・強化される）。他の行（atanh／tgamma／0.0÷0.0 等）は glibc 実行時と Node 22／24 の V8 のいずれでも符号が一致することを実測済みのため、従来どおり glibc 実行時表で固定する。CF-01 裁定の記録（当該テスト内の裁定コメントと台帳 RG-684）に、NaN 符号のホスト依存を注記した。

## 6. 総数差（7,553 vs 7,498＝55件）の内訳

全236テストファイルを個別に実行して登録数を数える実測を2環境で実施した：

- 環境A'： ツリーのコピーに監査ワークスペースの外部データ（advanced-inventory／adv-b7-tools）を配置し、Node 24 で実行 → 合計 **7,553件**（ローカル検証と完全一致。失敗0件）
- 環境C： 素のコピー（外部データなし）を Node 22 で実行 → 合計 **7,498件**（CI と完全一致。失敗12件で、その内訳も CI と一致： powerapps 1／r-data1 2／adv-b5-javascript 5／g3 1／g5 1／u 1／a6 1）

ファイル別に差分を取ると、登録数が変わったのは **tests/adv-b2-powerapps.test.js の1ファイルだけ** で、56件 → 1件（差55件）だった。他の235ファイルは両環境で登録数が不変である。機構は、モジュール読み込み時に棚卸しファイルの未解決で例外となり、ファイル全体が「読み込み失敗の1件」として数えられ、残り55件が登録自体されなかったことによる。生成型テストの登録数がデータ量で変わるといった要因は、今回の差には存在しなかった。

あわせて判明した事実として、adv-b2-powerapps.test.js の登録数は56件であり、そのうち外部データに依存するのは実物照合の2件のみ（残り54件は埋め込みデータで完結する）。
